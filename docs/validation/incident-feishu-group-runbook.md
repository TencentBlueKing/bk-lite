# Incident 飞书协作群真实验证 Runbook

## 1. 目的与边界

本 Runbook 用于在专用飞书测试租户中验证 Incident 一键建群、部分映射、持续增员、暂停恢复、失败重试和解绑的完整闭环。首期只验证飞书；不得使用生产租户、生产应用、真实事故或真实用户数据。

自动化测试通过不替代本 Runbook 的 12 个真实场景。12 个场景全部完成、证据脱敏且测试对象清理后，才能给出真实租户 `Pass` 结论。

## 2. 安全要求

- 只使用专用测试租户和专用自建应用，应用名称建议包含 `BK-Lite Incident Test`。
- `app_id`、`app_secret` 等凭据只允许在 BK-Lite「系统管理」UI 中输入，由运行环境加密保存；不得写入命令、终端历史、截图、日志、本文档、Issue 或 Git。
- 截图必须遮蔽手机号、邮箱、外部用户 ID、完整 `chat_id`、访问令牌和凭据。
- 证据中只记录外部 ID 或 `chat_id` 的末 4 位，例如 `***7a9c`。
- 服务端 request ID 可完整记录；若日志同时包含用户标识或令牌，先脱敏再保存。
- 测试应用只开放给测试成员，验证结束后撤销应用可见范围并轮换或删除测试凭据。

## 3. 测试租户与应用准备

### 3.1 测试人员

准备 4 个 BK-Lite 测试用户：

| 角色 | BK-Lite 状态 | 飞书状态 | 用途 |
|---|---|---|---|
| Operator A | Incident `operator` | 已映射 | 创建人、默认群主 |
| Operator B | Incident `operator` | 已映射 | 负责人权限与持续增员 |
| Collaborator C | Incident `collaborators` | 已映射 | 初始协作人 |
| Collaborator D | Incident `collaborators` | 故意未映射 | 部分成功和映射补齐 |

另准备一个可查看 Incident 但不在 `operator` 中的用户，用于验证管理接口返回 403。所有测试用户不得复用生产账号。

### 3.2 飞书应用条件

在专用测试租户创建自建应用并启用机器人能力。应用需具备且仅具备完成以下操作所必需的权限：

- 获取应用可见范围内的测试用户，用于用户同步和映射；
- 创建群、查询群；
- 向应用创建的群增加成员；
- 以 `chat_id` 向群发送 Incident 摘要；
- 机器人留在群内并具备后续增员所需的群管理能力。

应用可见范围只包含上述测试用户。发布应用版本后，用飞书开放平台调试或权限页确认权限已生效。

### 3.3 BK-Lite 准备

1. 在系统管理 UI 创建飞书 IntegrationInstance，只在 UI 输入凭据。
2. 创建并启用 IMNotificationChannel，选择与测试账号一致的映射策略。
3. 执行用户同步，确认 A、B、C 唯一映射，D 保持未映射。
4. 创建一个可重复关闭/重开的测试 Incident：
   - `operator`: A、B；
   - `collaborators`: C、D；
   - 状态为可处理状态；
   - 标题和内容不含真实客户、主机、IP 或告警数据。
5. 开启服务端 request ID 日志，并确认日志不会输出 token、secret、完整用户快照或完整请求体。

## 4. 证据记录模板

每个场景必须记录：

```text
执行时间：
执行人：
Incident ID：
Channel ID：
Group binding ID：
Chat ID 脱敏尾号：***____
BK-Lite request ID：
飞书 request ID：
BK-Lite 页面证据：
飞书客户端/开放平台证据：
服务端状态/日志证据：
结果：Pass / Fail / Not Run
缺陷编号（Fail 时必填）：

```

同一次验证另建对象清单，至少包含 Incident ID、channel ID、binding ID、Outbox key、脱敏 chat ID、测试群名和创建时间。不得复制数据库凭据或飞书凭据。

## 5. 十二个真实场景

### 场景 1：用户同步与创建预览

1. 在系统管理执行飞书用户同步。
2. Operator A 打开 Incident 协作区并点击「一键拉群」。
3. 选择测试通道，检查成员预览。

预期：A、B、C 显示已映射；D 显示未映射；A/B 可选为群主；非负责人看不到通道选项和映射预览。证据需包含同步状态、预览页面和对应 request ID。

### 场景 2：单次建群

1. 由 A 选择测试通道、A 为群主并提交。
2. 等待状态从创建中进入 `active` 或 `active_partial`。
3. 在飞书检查群名、群主、机器人和实际成员。

预期：只创建一个群；A、B、C 入群，D 不入群；本地保存唯一 binding 和脱敏 chat ID。

### 场景 3：部分映射

1. 保持 D 未映射，观察建群结果和成员 Drawer。
2. 刷新页面并重新打开 Drawer。

预期：建群不被 D 阻断；群状态为部分成功；D 明确显示待映射，其他成员为已加入；页面给出可行动提示。

### 场景 4：Incident 摘要消息

1. 打开新建飞书群。
2. 检查首条 Incident 摘要。

预期：摘要只出现一次，包含测试 Incident 标题、级别、状态、负责人和可访问详情链接；不包含凭据、token、完整外部用户 ID 或未授权数据。

### 场景 5：重复提交与任务重投

1. 在创建响应延迟或刷新页面的情况下重复点击/重复提交。
2. 在测试环境按既定运维方式重投同一 create/summary Outbox。
3. 检查 binding、飞书群和摘要消息数量。

预期：重复创建请求返回既有绑定或 409；稳定 UUID 被复用；飞书只有一个群，摘要不重复；request ID 可串联两次请求。不得通过直接修改生产数据库制造重投。

### 场景 6：补齐映射后自动入群

1. 在系统管理为 D 补齐正确映射并重新同步。
2. 保持持续同步开启，等待周期对账或触发允许的对账。
3. 检查 Drawer 和飞书群成员。

预期：D 自动加入且只加入一次；成员状态变为 joined；群回到 active（若无其他 gap）。

### 场景 7：新增协作人自动入群

1. 准备另一个已映射测试用户 E。
2. 在 Incident 中新增 E 为协作人。
3. 观察页面同步状态和飞书群。

预期：同一事务产生对账任务；E 自动加入一次；已有成员不重复处理。

### 场景 8：移除人员不退群

1. 从 Incident 移除 Collaborator C。
2. 确认前端提示「不会自动从飞书群移除」。
3. 检查飞书群成员和后续对账。

预期：C 仍留在飞书群；系统不调用任何移除成员接口；已移除但未入群的人不会被旧任务继续拉入。

### 场景 9：Incident 关闭与重开

1. 在持续同步开启时关闭 Incident。
2. 关闭期间新增一个已映射人员或保留待加入人员，等待超过一个调度周期。
3. 重开 Incident 并等待对账。

预期：关闭时暂停，不再外呼增员/摘要；群不删除；重开后按关闭前配置恢复，遗漏人员补入；旧 Outbox 不得覆盖暂停状态。

### 场景 10：手工暂停与恢复

1. Operator A 手工暂停持续同步。
2. 新增一个已映射协作人，确认不会入群。
3. 恢复同步并等待对账。

预期：暂停原因显示为 manual；暂停期间旧事件不能越过状态外呼；恢复后只补入当前 Incident 期望成员。

### 场景 11：权限、非法用户与可重试网络失败

1. 使用非 operator 用户请求查看可选通道、创建、重试、暂停或解绑。
2. 让预览包含未映射/无效测试用户。
3. 使用可控测试代理或飞书测试设施制造一次超时/429，再恢复网络。

预期：非 operator 管理操作为 403；非法用户不阻断其他成员且错误码明确；临时错误按有界退避重试，终态错误不无限重试；日志和响应不泄漏凭据。网络故障注入不得影响生产网络。

### 场景 12：解绑保留外部群并允许新绑定

1. 输入完整群名确认解绑。
2. 检查旧飞书群仍存在，等待一个调度周期确认不再增员。
3. 对同一 Incident 重新选择通道创建新绑定。

预期：旧 binding 变为 unlinked、`active_slot` 清空；旧群保留且停止管理；同一 Incident 允许建立新的唯一 active binding；旧任务不得作用于旧群。

## 6. 失败判定

出现以下任一情况，验证报告必须为 `Block`：

- 产生重复飞书群或重复摘要；
- 用户被拉入错误群、已移除且从未入群的人员仍被拉入；
- Incident 关闭、手工暂停或解绑后继续自动增员；
- 非 operator 可以管理群或读取通道/映射预览；
- 凭据、token、完整外部用户 ID 或敏感用户快照出现在日志、响应或截图；
- 外部调用成功后，本地重试创建第二个群；
- 迁移不兼容 PostgreSQL、MySQL 或 SQLite 的既定模型约束。

其他失败也不得写成 Pass，必须记录缺陷编号、原始 request ID 和复现步骤。

## 7. 清理与复核

1. 先在 BK-Lite 执行解绑，确认旧群不再受管理。
2. 在飞书客户端由群管理员手工解散所有测试群；解绑本身不会删除群。
3. 删除测试 Incident 中新增的协作关系和测试通知通道。
4. 禁用或删除测试 IntegrationInstance；在飞书后台撤销测试应用版本、可见范围并轮换/删除 secret。
5. 删除只为验证创建的测试用户 E；A–D 若为共享测试账号，恢复原始映射状态。
6. 核对对象清单，确保没有残留 active binding、待投递 Outbox 或测试群。
7. 在验证报告记录清理时间、执行人、残留对象；无法清理的对象必须列为风险，不得省略。

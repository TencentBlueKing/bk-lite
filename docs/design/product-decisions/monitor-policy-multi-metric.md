# 监控多指标条件策略产品决策记忆

- 最近更新：2026-10-21
- 当前规格：`specs/changes/monitor-policy-multi-metric/spec.md`

## 产品定位

多指标条件是监控策略的第三种指标模式，表达「几个指标同时过线才算故障」。它与计算指标（公式）并列：
公式把多个指标算成一个数再比一组阈值，多指标条件让每个指标各比各的阈值再取「且」。原生条件不写表达式。
2026-10-21 起，多条件里的单条可以改成计算指标（`source: formula`），表达式只活在该条件内；组合、对齐和 `${ref_value}` 仍按本决策。见 `specs/changes/monitor-policy-condition-source/spec.md`。

## 已确认范围

- 一条策略 2～5 个条件，组合方式只有「全部满足」。
- 每个条件自带指标、过滤、分组聚合、维度、汇聚方式、单位和阈值阶梯；可标记为前置条件（单阈值、无级别）。
- 扫描、预览、试跑、快照、告警详情、策略组阈值编辑、模板导入导出都支持该模式。
- 单指标、手写查询、公式策略行为不变。

## 已确认设计决策

- 走「条件列表 + 全部满足」，不走布尔表达式，也不做基于已有策略告警状态的复合策略。原因：符合「用户不写 PromQL / Zabbix 表达式」的既有立场；复合策略需要先建子策略并新增一层状态合成引擎，与策略组「不新做检测引擎」冲突。
- 策略级别 = 各条件命中级别中的最低者；任一条件未命中任何级别则不触发。原因：这是业界唯一有明确文档的多条件 × 多级别语义（Datadog `&&`），并与现有逐级判定算法同构。
- 前置条件是独立角色，只做门槛，不参与级别合成。原因：「错误率高且流量够大」「排除刚开机主机」是门槛语义，用阶梯表达会污染级别。
- 维度对齐沿用公式规则：第一个条件为锚点，锚点维度含实例身份，其余条件维度是锚点的子集并按锚点广播。计算条件的维度是它第一个操作数的维度；其余操作数可以是这个维度的子集。
- 条件级字段全部放在 `query_condition.queries[]`，不新增模型列；策略级单值字段从锚点镜像，只为满足既有校验，不作判定依据。
- 多指标模式锁定比较基准为「当前值」，不开放恢复阈值（滞回）；汇聚周期、连续 N、恢复 N、无数据沿用策略级配置。
- 无数据检测与基线只看锚点条件；非锚点条件不产生无数据告警。
- 非锚点条件在某行缺数据时，活动告警本轮保持：不触发、不恢复、不计入恢复次数；试跑显式报 `missing_condition_data`。原因：缺数据不等于不满足，误恢复比多挂一轮更危险；与现有缺对照「本轮不触发也不恢复」同一语义；悬挂风险由锚点条件自身的无数据告警兜底。不采用 Azure「任一条件不成立即恢复」的语义。
- 逐条件独立编译查询，Python 侧按锚点维度 join；不引入新的 MetricsQL 形态，逐序列算法允许逐条件使用。
- 告警 `value`、`${value}`、快照 `current_value` 取第一个常规条件；新增 `${<ref>_value}`、`${<ref>_metric_name}`；`metric_name` 与告警中心 `item` 用结果名称。
- 策略组「只改阈值」扩展为按条件变量改阈值；多指标规则要求全部条件的指标都在当前插件下才算有数据。
- 表单模式选择显式化（单指标 / 计算指标 / 多指标条件），多条件阈值按级别分行编辑，一行 = 一个级别 × 全部常规条件；前置条件单独一段；组合方式只显示「全部满足」，不做置灰占位。
- 已有策略允许在编辑时切换到多指标模式；`query_condition.type` 变化时保存同时结束该策略下全部未恢复告警。原因：锚点维度变化会改变告警身份键，沿用策略组改阈值结束旧告警的处理。
- 不随版本带内置多指标模板，用户自建。

## 明确后置

- 组合方式「任意满足」与复合表达式；基于策略状态的复合策略。
- 条件级比较基准、条件级或策略级滞回、OR 下的级别合成。
- 专家布尔表达式入口。
- 非锚点条件的无数据告警。
- APM、Log 的多条件告警。

## 已替代决策

- 计算条件的操作数共用卡片顶部一个维度（2026-10-21 当日曾落地，同日改回）。原因：分组和 `by` 是同一句话，引擎也按操作数各自的 `group_by` 做子集广播；顶部一个下拉把这种算法从界面拿掉了。
- 按条件堆叠的阈值卡（2026-10-21 替换）。原因：级别是跨条件合成的，每个条件各放一套三级阶梯看不出合成关系，也能配出某一条件没有、引擎永远不会命中的死等级。

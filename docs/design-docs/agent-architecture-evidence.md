# Agent 使用模块架构证据指南

本指南供设计、重构、修复和排障流程按需读取，不是每个任务的默认上下文。架构图用于
降低代码导航成本、选择验证 Seam 和形成待证假设；当前代码、配置、测试与运行证据始终
是最终事实。

## 何时读取

处理 `server/` 时，出现以下任一信号再使用模块架构产物：

- 设计、重构或扩展涉及模块职责、Interface、Adapter、依赖方向或事实所有权；
- 修复或排障涉及跨模块调用、异步/并发、性能与容量、数据一致性、状态流转或外部副作用；
- 实际执行路径不清晰，需要确定测试、插桩或回放的 Seam。

已由紧凑局部复现完整证明、且不改变上述架构事实的简单修改可以跳过。不要无差别读取
全部模块图件。

## 选择证据

1. 从 [Server 后端模块架构分析路线图](./server-module-analysis-roadmap.md) 的
   “已完成模块与产物索引”定位受影响模块及直接相邻模块。
2. 判断现状 Module、Interface、Adapter 和依赖时，读取模块报告与
   `<module>-current.architecture.json`。
3. 追踪执行、数据、状态、并发或外部副作用时，再读取该模块的核心 `workflow`、
   `dataflow`、`sequence` 或 `lifecycle` JSON。
4. 只有问题确实跨越多个模块时，才读取 `server-overall.architecture.json`。

JSON 是供 Agent 检索的可维护规格；HTML 是相同规格生成的人工交互视图，不需要同时
读取两者。

## 设计与修复的不同用法

### 设计、重构与扩展

- 先用现状架构和核心链路核对已有 Interface、事实源、调用顺序与容量约束。
- `<module>-target.architecture.json` 只是已有演进候选，不是既定方案。选择 Seam 或
  Interface 前，至少与一个独立推导的方案比较并重新论证取舍。

### 修复与排障

- 先建立能命中用户症状的反馈循环，再用现状架构和核心链路选择观测点、缩小路径。
- 在反馈循环和当前路径被理解前不要读取目标架构，避免被未来设计锚定。
- 图上的边只是需要验证的线索，不是根因结论，也不能替代可变红的测试或复现命令。

## 证据与同步规则

- 重要节点和连线必须回到当前代码、配置、测试或运行证据验证；尤其不能仅凭图件断言
  import、运行时调用、事务、顺序保证或事实所有权存在。
- 图件与当前实现冲突时，明确记录过期或缺失的断言，不得为了迎合图件修改正确实现。
- 代码变更直接改变已记录的模块职责、依赖方向或核心数据流时，同步更新对应报告与
  Archify JSON/HTML；小范围修复不要顺带重画无关模块。

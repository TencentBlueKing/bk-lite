# 多 Tab 登录过期静默恢复设计

## 背景

用户同时打开多个 BK-Lite 页面时，任一 Tab 遇到受保护接口的 `401` 会显示
“登录已过期”弹窗。当前在一个 Tab 内重新登录后，其他 Tab 会通过 NextAuth
Session 刷新恢复认证。刷新期间根布局进入全屏 loading，业务页面 React 树可能被
卸载，导致已打开的业务弹窗、未提交表单、滚动位置和页面局部状态丢失。

## 目标

- 任一 Tab 重新登录成功后，当前 Tab 和其他同源 Tab 都静默恢复认证。
- 恢复期间不导航、不刷新页面、不卸载业务页面 React 树。
- 其他 Tab 中已打开的弹窗、表单输入、路由和滚动位置保持不变。
- 恢复后的请求使用最新登录 Token。
- `460` 强制退出和用户主动退出仍维持现有跳转行为。

## 非目标

- 不为每个业务表单增加草稿持久化。
- 不改变后端 JWT、Cookie 或登录接口协议。
- 不改变正常首次登录页面的跳转行为。
- 不把真正无效或恢复失败的 Session 伪装为认证成功。

## 设计

### 认证恢复消息

扩展现有 `authRecoveryChannel` 消息，使登录成功的 Tab 发布一次带恢复标识的事件。
事件只作为“服务端认证已经更新，可以静默同步”的信号，不在
`BroadcastChannel` 或 `localStorage` 中传输 Token。

### 当前 Tab

登录过期弹窗中的 `SigninClient` 完成后：

1. 后端已经设置新的 HttpOnly Cookie。
2. 当前 Tab 更新 NextAuth Session 和 AuthContext 中的认证快照。
3. 重置 session-expired 状态并关闭登录过期弹窗。
4. 发布认证恢复事件。
5. 不执行 `window.location`、`router.refresh` 或页面导航。

### 其他 Tab

收到认证恢复事件后：

1. 通过不会切换根布局 loading 状态的认证恢复接口取得最新认证快照。
2. 原子更新 AuthContext 中的 Token 和用户认证状态。
3. 重置 session-expired 状态并关闭登录过期弹窗。
4. 保持现有 React 子树挂载，不改变路由和页面局部状态。

同一事件使用 `eventId` 去重；同一 Tab 同时只允许一个恢复 Promise，避免多个
401 或多个广播导致并发恢复。

### 失败处理

- 静默恢复失败时保留“登录已过期”弹窗，不刷新页面。
- 不清除业务页面状态，不自动跳转登录页。
- 用户可在弹窗中再次登录。
- `460` 和主动登出继续使用现有强制退出流程。

## 测试

### 单元测试

- 相同恢复事件只处理一次。
- 多个并发恢复事件复用同一个恢复 Promise。
- 恢复成功后关闭 session-expired 状态并更新认证快照。
- 恢复失败时弹窗保持打开且不调用任何导航 API。

### 多 Tab 行为测试

1. Tab A、Tab B 使用同一账号登录。
2. Tab B 打开业务弹窗并填写未提交内容。
3. 两个 Tab 分别触发受保护接口 `401`。
4. 在 Tab A 的过期弹窗中重新登录。
5. Tab B 收到恢复事件并静默更新认证。
6. 断言 Tab B URL 不变、页面未 reload、业务弹窗仍打开、表单值和滚动位置不变。
7. 断言 Tab B 后续受保护请求成功。

## 验收标准

- 登录恢复过程中没有 `window.location.*`、`router.refresh()` 或等价整页导航。
- 其他 Tab 的业务组件不因认证 Session 的 loading 状态而卸载。
- 截图场景中的“添加”弹窗和名称输入值在另一 Tab 登录后保持原样。
- 恢复后的 API 请求使用新认证信息且不再返回 `401`。

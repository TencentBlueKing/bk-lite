# ADR 0004：领域 App 拥有自身告警生命周期

Status: accepted

## Context

Monitor、Log、APM 是同级产品域。策略评估产生的事件和告警是来源 App 的领域事实，需要在告警中心未安装、未迁移或不可用时仍能查询和维护。若来源 App 直接读取告警中心模型，或把生命周期交给告警中心持久化，会形成数据库迁移、部署和可用性耦合。

领域告警发生后，用户可以选择系统管理中配置的邮件、机器人、Webhook、NATS 等通知渠道。通知只是领域事件的投递副作用，渠道配置和传输实现由系统管理拥有，来源 App 不应直接读取系统管理或告警中心模型。

告警中心仍需要接收不同来源的标准事件副本，用于跨源聚合与事故协同。系统管理中的 `nats + receive_alert_events` 是这种事件副本投递的一个特殊渠道，但 NATS 类型本身不等同于告警中心，其他通知渠道也不需要经过告警中心。

## Decision

- Monitor、Log、APM 等同级产品域各自拥有策略产生的事件、告警与生命周期数据，并通过本 App 接口查询和处置。
- App 之间禁止直接引用对方的模型、表或内部实现。
- 系统管理拥有通知渠道目录、渠道能力和传输适配。来源 App 只保存用户选择的渠道 ID 与接收人配置，并通过系统管理公开接口查询和投递；接口必须返回渠道的接收人模式与投递模式，避免来源 App 依赖渠道私有配置。
- 普通渠道接收面向人员或外部系统的通知内容；只有投递模式为 `alert_event_copy` 的渠道接收标准告警事件副本。当前 `nats + receive_alert_events` 映射为该特殊模式。
- 通知渠道投递发生在领域事务提交后，并使用来源 App 自有投递箱进行有界重试。投递失败、渠道删除或告警中心不可用不得回滚或隐藏已经产生的领域告警。

## Consequences

- 任一业务 App 不依赖告警中心的安装状态、数据库迁移或运行可用性。
- 告警中心中的事件是来源事件的副本，不能作为来源 App 的查询或生命周期事实。
- 来源 App 需要维护自己的事件、告警和投递补偿模型，但不拥有渠道配置或具体传输协议。
- 系统管理的公开渠道接口需要稳定表达 `delivery_mode`、`recipient_mode` 和可重试错误，不再要求调用方根据 `channel_type` 或 `config.method_name` 猜测行为。
- 跨源聚合与事故协同仍可通过标准 NATS 事件契约实现。

## Why

默认 Celery 队列由同一线程池消费，CMDB 关联、监控扫描、通知和节点状态收敛相互争抢执行槽位。2026-10-30 线上截图显示基础队列积压 11,072 条，头部 500 条中两类节点收敛占 94.2%。需要在整机 16–32GB、全部组件同机的约束下，通过运行架构保留关键任务的执行机会；业务任务的去重、计算和处理流程由业务开发人员独立治理。

## What Changes

- 建立上线前事实核对：线上版本、真实任务注册/路由、头尾样本、入队/完成速率和整机内存。当前本地 88 项清单不能覆盖截图中新增的七个任务名。
- 在公共配置层建立 `critical`、`notification`、`state`、`background` 四个逻辑队列，按准确任务名路由；节点状态收敛从告警检测执行池隔离。
- 采用一套通用弹性配置：四个独立 prefork worker，各自配置最小/最大执行进程数，通过 Celery 原生 autoscale 在范围内伸缩，不设置按内存划分的部署档位。
- 最小并发是保底容量，最大并发是峰值边界，两者均须按负载和内存测定，不把各池并发 1 或总并发 4 当成已验证推荐。所有实例的各池最大并发之和不得超过部署总预算。
- 当前 threads 不支持原生 autoscale，因此将 prefork 兼容性、空闲子进程缩容、缩容等待及全池同时到达上限的内存验收纳入架构实施。保留 ACK/重试策略；不因切池隐式启用强杀或频繁回收。
- 建立总并发上限、显式消费队列、基础运行指标、只读诊断、存量队列排空和回滚流程。原 `celery` 队列由后台池承接迁移存量及未映射任务，并对未映射任务告警。

本变更严格限定架构层：不修改任务业务函数、触发频率、参数契约、计算逻辑、业务状态机、去重策略、补算方式、通知流程、业务数据库模型及远端执行语义。业务优化不是本变更的实施任务或完成条件；无法由架构消除的风险通过运行指标交给业务团队处理。

已进入架构实施，尚未部署生产。实施不统一改变 ACK/自动重试/远端取消语义，不清空消息，不新增隐式消息丢弃策略，不把同步 CMDB 导出杜撰为现有异步任务。

## Capabilities

### New Capabilities

- `celery-workload-isolation`: 公共任务路由、四个逻辑队列、独立执行池弹性上下限、总并发预算和配置校验。
- `celery-capacity-operations`: 线上基线核对、任务生命周期观测、16–32GB同机容量验收、灰度迁移与回滚。

### Modified Capabilities

无。当前主规格未包含上述完整能力；既有安装、作业、权限、告警生命周期要求继续有效。

## Impact

- 异步基础设施：`server/config/components/celery.py`、`server/apps/core/celery.py`、新增公共路由/观测/诊断工具、`server/support-files/release/startup.sh` 与 supervisor 配置。
- 测试与运维：公共路由/运行配置测试、架构负载测试、`docs/operations.md`、配置样例和迁移运行手册。
- 线上专有任务须取得实际注册与源码证据后补充路由，不依名称猜测职责；不借本变更修复业务任务名或业务实现。
- 依赖：复用现有 Celery、Beat、消息代理、日志和运行环境，不新增调度平台、业务数据表、公开 API 或常驻观测服务。

# ITSM 新环境初始化

## 首次安装会得到什么

下表是空 PostgreSQL 库执行系统管理和 ITSM 初始化后的实测值。ITSM 命令写入默认域 `domain.com`。[基础数据命令](../../server/apps/itsm/management/commands/init_itsm.py) · [ITIL 预置命令](../../server/apps/itsm/management/commands/init_itsm_itil.py)

| 类别 | 初始内容 | 使用条件 |
| --- | --- | --- |
| 菜单和权限 | 系统管理加载 71 项 ITSM 菜单操作和 1 个默认菜单组 | 正式用户仍需分配角色和操作权限 |
| 工单状态 | 7 个状态、18 条流转 | 草稿、新、处理中、挂起、已完成、终止、撤销 |
| 数据字典 | 优先级、紧急度、影响度共 3 本，10 个字典项 | 可直接用于表单选项 |
| 站内通知 | 待办、催办、退回、完成共 4 份模板 | 初始化不生成 IM 账号映射或渠道 |
| ITIL 服务 | 1 个目录、请求／事件／问题管理 3 个流程及服务，每个流程 1 个 V1、3 个业务阶段 | 新服务默认停用。首次安装连接引擎可部署 V1，管理员选择有效处理组并启用后，可见范围内的用户才能在门户提单 |
| 基础表单 | 3 个独立的表单模型，各有已发布 V1。标题必填，另有描述、优先级、影响度 | 后两项从本域字典取值。每个流程版本保存自己的表单快照 |
| SLA | 1 个工作日历、6 条策略 | 默认上海时区，周一至五 09:00–18:00。请求和问题的响应／解决目标为 60／480 分钟，事件为 30／240 分钟；预警提前量默认为 0，升级人员为空 |
| 运行时默认展示 | 门户九组件布局、列表默认列、基础设置、统一打印版式 | 从代码读取默认值。无需为每位用户复制布局或预建打印模板。[门户布局](../../server/apps/itsm/views/portal_workbench.py) · [打印实现](../../server/apps/itsm/services/ticket/printing.py) |

## 流程设计员

系统管理初始化 ITSM 权限时会创建应用角色 `designer`。在系统管理的应用角色授权中，将该角色分配给需要设计流程的账号。设计员可以新建流程和表单、编辑草稿、预览、复制流程。单独的 `workflow-Draft` 允许保存流程草稿，服务目录、运行状态和 SLA 的管理仍使用原有授权。

如需发布，可另建一个自定义角色并叠加授权。独立表单发布需要 `form-Publish`，流程设计器联合发布表单和流程需要同时具备 `form-Publish` 和 `workflow-Publish`。再次初始化会同步内置角色的菜单清单，因此额外授权应配置在自定义角色中。

## 可复现的验证

在已注入平台数据库、应用启动配置和初始化管理员凭据的**空环境**中，从 `server/` 执行以下命令。平台管理员凭据由部署方提供，Flowable REST 连接参数见[配置定义](../../server/config/components/itsm.py)。

```sh
uv run python manage.py migrate --noinput
uv run python manage.py createcachetable django_cache
uv run python manage.py batch_init --apps system_mgmt,itsm
uv run python manage.py showmigrations itsm
```

### 开通第一个服务

1. 在「管理设置 → 处理组」中选择本域的实际办理账号作为组成员。至少一名成员须为有效账号，并为实际办理人分配平台 ITSM 办理权限。
2. 在「流程设计」查看当前版本。首次安装成功部署后为 V1。未配置引擎口令时只创建草稿。配置了口令但部署失败时，安装在失败的流程处中止；恢复连接后由管理员核对并发布该草稿，再运行初始化补装余下流程。
3. 在「服务门户 → 服务管理」编辑服务，选择「服务处理组」并启用。分派和处理节点从这个组取人。「可见范围」单独决定谁可以在门户看到服务。
4. 提单人打开服务，填写基础表单并提交申请，在自己的提单节点提交。处理组成员从「工单中心 → 我的待办」进入分派节点，审批后在处理节点提交完成。普通提单角色可以提交自己负责的提单节点，审批及处理仍要求办理权限。

### 重跑与升级

安装命令按域和流程标识识别已存在的预置流程。只在首次创建时生成基础表单、V1、服务、阶段和策略，并尝试部署本次新建的 V1。再次执行时跳过整个已有流程，即使它只有未发布的 V1，或有管理员正在编辑的 V2。已编辑或主动删除的预置配置由管理员维护。

迁移 `0029_service_handler_group` 为服务增加处理组关联，停用默认域中仍以系统预置示例账号办理的旧 V1 服务。管理员应建立新草稿，补充表单，将分派与处理节点的处理人来源改为「使用服务处理组」，发布后绑定实际处理组并启用服务。迁移保留历史版本、工单和已有草稿。[服务迁移](../../server/apps/itsm/migrations/0029_service_handler_group.py)

### 空库实测

2026-11-25 使用独立 PostgreSQL 15 业务库和 Flowable REST 7.1.0 引擎库，基于 `724ab18b7d` 加本轮改动验证。

| 场景 | 验收结果 |
| --- | --- |
| 联机首次安装 | 应用 29 项 ITSM 迁移。生成 3 个流程、3 份基础表单、3 个已部署的 V1、3 个停用服务、9 个阶段和 6 条 SLA 策略 |
| 浏览器开通服务 | 管理员创建办理组并选择实际用户，3 个服务均需先选有效处理组才能保存启用 |
| 管理员草稿与重复初始化 | 在浏览器为请求管理新建 V2 草稿，连续两次执行基础及 ITIL 初始化。V1 仍为当前版本，V2 仍为草稿。流程、版本、表单、服务、策略、阶段各行内容及更新时间均相同，引擎部署数相同 |
| 普通账号浏览器办理 | `fresh_requester` 填写标题、描述、优先级 P2 和影响度「高」，并提交本人的提单节点。`fresh_worker` 在「我的待办」中完成分派和处理。两个账号分别打开详情均显示已完成 |
| Flowable 对账 | 事件 `REQ20261125035442507255`、请求 `REQ20261125040125031672`、问题 `REQ20261125040135747461` 均有实例结束时间，运行时待办均为 0。每单 3 条已完成历史任务与 ITSM 的节点、办理人及操作日志相符 |
| 首次安装未配置引擎口令，随后连接引擎 | 在另一个空库生成 3 个 V1 草稿及 3 个停用服务，修改其中一个草稿，连上真实引擎再初始化。草稿内容保留，新增部署为 0 |

批量入口捕获 ITIL 初始化的部署异常并输出警告。应同时检查流程当前版本、Flowable 部署和服务启用状态。[批量入口](../../server/apps/core/management/commands/batch_init.py)

本轮在真实引擎开启时运行隔离环境的 ITSM 后端回归，737 项通过。另有 3 项依赖独立集成运行环境的测试跳过，涉及 Python 执行器和外部待办。对应的回归覆盖[预置安装](../../server/apps/itsm/tests/test_itil_presets.py)、[服务处理组](../../server/apps/itsm/tests/test_service_handler_group.py)和[提单人权限](../../server/apps/itsm/tests/test_applicant_submission.py)。

前端 ITSM 回归 261 项通过，类型检查和 lint 通过。全仓后端门禁复跑时，Django 套件在告警分派的组织目标归一化断言处停止（`test_organization_target_is_normalized_and_clears_legacy_personnel`）；独立 PPT 工具套件 742 项通过、3 项跳过。

## 哪些内容适合进一步内置

| 优先级 | 建议 | 理由与启用边界 |
| --- | --- | --- |
| P1 | 丰富内置站内待办文案，带上单号、流程、当前节点和详情链接；提供可选 IM 模板样例 | 现有待办正文仅展示标题。模板本身可复用，发送渠道、接收人映射和站点地址由各环境配置；已有管理员模板应保留 |
| P1 | 提供可选满意度问卷、停用的 SLA 预警／触发器示例 | 新环境无问卷模板、触发规则或定时建单任务。可以示范配置，启用前须选择范围、日历、阈值及接收人 |
| 演示环境 | 按需装入表单测试数据、Python 示例和样例工单 | 已有显式的表单演示命令。演示数据适合独立域；真实工单、可执行定时任务和外部通知不宜默认生成 |
| 租户自行配置 | 实际人员与班表、代理、飞书等渠道及手工映射、外部 API 凭据、组织权限、升级接收人和可用服务范围 | 这些配置决定谁能看到工单、谁会收到消息或哪个外部系统会被调用，无法从空库可靠推断 |

# 事故影响拓扑增强：关联对象告警与应用系统影响面

Status: 已确认

本文是这次需求的口径。实施步骤见同目录 `implementation.md`。已落地的 `specs/changes/incident-impact-topology/spec.md` 仍描述上周那张基础图，本文件描述在它之上的增强。

上周的影响拓扑保持原入口：事故详情 → 告警 Tab → 影响拓扑。这次只在这张图上加两层信息，不另起页面，不把关联告警写进事故。

## 产品判断

一线要回答的是两句话：

1. 事故对象沿它所属模型的全部关系再向外一层，那些实例自己现在有没有告警。
2. 这些对象落到应用拓扑后，所属应用、应用系统现在是单点还是已经在告。

图仍然是分析视图。关联对象上的告警、应用下的告警都只展示，不自动并入本事故，也不做「父红压子」。

## 仓库里已经成立的事实

- 页面：`web/src/app/alarm/(pages)/incidents/detail/` 的表格、甘特、影响拓扑共用当前事故告警列表。拓扑请求是 `POST /alerts/api/incident/{id}/impact_topology/`，种子是当前列表里的 `monitor_objects[].cmdb_id`。
- 告警服务不引用 CMDB 服务。`apps/alerts/service/incident_impact_topology.py` 只通过 `CMDB.incident_impact_topology` 取关系。没有 NATS 订阅者是 `not_purchased`，超时或失败是 `unavailable`，两种都是 HTTP 成功。
- CMDB 侧 `apps/cmdb/services/incident_impact_topology.py` 只查 `run` / `connect`。两端都是种子的边直接保留。上一跳只有在至少两个种子共用时才作为 `bridge` 拉入。单个种子不拉上一跳。种子的下级、非种子的基础设施层不拉入。`belong`、`group`、`install_on`、`contains` 不参与穿线。去重种子超过 200 不查图。
- 节点颜色和条数由页面用**本事故告警列表**合成。CMDB 不返回告警。侧栏只展示标题，不跳到告警详情。桥接是绿色虚线，未绑定是灰色孤立点。
- 应用归属投影是 `cmdb_ci_context`。`lookup_ci_context` 按组织点查，不扫图。成员口径在 `ci_context_policy.py`：应用经 `run` / `connect` 到一层成员，一层成员再经 `run` 到二层成员；`system contains application` 写成成员行上的 `system_uuid`（多个系统时取最小 UUID）。告警丰富用的就是这个函数，再按投影去补应用、系统实例。
- 应用模型默认落在应用拓扑的服务层，应用系统模型落在系统层。
- 「当前未关闭告警」在告警模块里是 `AlertStatus.ACTIVATE_STATUS`：未分派、待响应、处理中。已处理、已关闭、自动关闭、自动恢复不算。
- 告警详情定位已经是 `/alarm/alarms?alert_id=<alert_id>`。

## 这次相对上周多出来的行为

上周「只有一个告警对象时图上只有这个点」对这张视图不再成立。单个种子也会带出一层关联实例，以及命中的应用、应用系统。

这一层的关系不限于 `run` / `connect`。`run` / `connect` 只是举例。种子模型上配置的每一种关系、这些关系下和种子直接相连的实例，都进入这一层。

上周桥接固定绿色。桥接对象如果自己有未关闭告警，颜色改跟级别走，虚线和「桥接」角标保留。没有未关闭告警时，仍是现在的桥接样式。

种子节点的主颜色和主条数仍是**本事故里、当前用户看得见的告警**。不改事故成员列表的含义。

## 图上有哪些点

起点仍是当前事故告警列表里的 CMDB 对象（种子）。搜索、关联、解除改变列表后，按新种子重查。这是上周的行为，继续沿用。

从种子向外只走一层，不从对端再向外。这一层取种子模型上的全部模型关系，再取这些关系下、一端是该种子的实例。模型作为源或作为目标都算。内置的属于、组成、运行于、安装于、包含、关联，以及模型上后来加的关系，都在内。`run` / `connect` 只是其中两类，不是白名单。

因此主机关联的网卡、属于的机柜、安装于其上的组件，只要是这一层的实例，就进入候选。不再因为对端落在基础设施层就丢掉。看不见的实例不给名称、不进图。同一条边按源、目标和 `model_asst_id` 去重。对端已经在图上时只补边，不复制节点。

上周种子之间的 `run` / `connect`，以及至少两个种子共用的上一跳桥接，仍然保留。其他关系如果正好连着两个种子，也补上这条边，关联名用关系自己的名称。桥接角标仍只给上周那种共用上一跳，不把每一种关系都标成桥接。

无告警的关联对象保留在图上，并标明已经查过。不把「没画出来」和「查过了、没有告警」混成同一种灰色。

应用和应用系统另外按 `ci_context` 点查：所属应用和 `system_uuid`，再补这两个实例的名称。直接的包含、运行于等边如果已经把同一个实例带进这一层，就合并，不画两个点。一个对象可以挂多个应用。对象、应用、应用系统三层都画在同一张图上：

```text
应用系统
   │ 所属系统
应用
   │ 所属应用
对象（种子 / 桥接 / 一跳关联对象）
```

应用自己就是种子或关联对象时，不复制节点，只补它的系统。系统已经在图上时同样合并。`ci_context` 没有命中时，对象留在图上，不编造应用。投影可能落后于实时改图，这和告警丰富是同一口径：打开事故时不重算整张应用图。

没有 `cmdb_id` 的告警仍是未绑定灰点，不连线，不进应用拓扑。

## 告警怎么贴到节点上

告警只在告警服务里查。CMDB 回的是结构和归属，不带级别和条数。

| 节点 | 主展示 | 颜色 |
|---|---|---|
| 种子 | 本事故可见告警的条数和最严重级别 | 现有级别色 |
| 种子上还有事故外的未关闭告警 | 主条数不变，副文案写「另有 N 条未入本事故」 | 仍按本事故 |
| 桥接 / 一跳关联对象 | 该对象当前未关闭告警 | 有告警用级别色；查过且为 0 用「无告警」 |
| 应用 | 自身，加上 `root_uuid` 等于该应用的上下文成员上的当前未关闭告警 | 同上 |
| 应用系统 | 自身，加上其下应用成员的当前未关闭告警 | 同上 |

「其下」用来区分单点和应用级故障，所以应用节点统计的是这个应用在 `ci_context` 里的成员，不限于图上画出来的那几个对象。同一条告警在一个应用节点上只计一次。对象节点仍显示它自己的条数，不因为上层是红的就被改色或藏掉。

当前未关闭只含未分派、待响应、处理中。已关闭和已恢复不算。观察中的会话告警（`is_session_alert` 且 `session_status=observing`）还没转正，不计入。

用户看不见的告警不计数。因此一个对象在别的组织里有告警、当前用户看不到时，图上是「无告警」，不是「没采到」。

查告警失败时，节点不是「无告警」。状态是「告警情况暂时查不到」，避免把故障画成正常。

## 后端链路

一次打开拓扑，仍然是一次事故接口。告警进程不 import CMDB 服务。

```text
页面
  POST /alerts/api/incident/{id}/impact_topology/
    种子 = 当前列表 UUID ∩ 这起事故里当前用户可见的告警
告警服务
  NATS CMDB.incident_impact_topology
CMDB
  1. 原逻辑：种子、种子之间的 run/connect、共用上一跳桥接
  2. 种子模型的全部关系，各取直接相连的一层实例
  3. 对看得见的对象点查 ci_context，带上应用和系统实例
告警服务
  4. 在候选里挑选要画的关联对象
  5. 按对象、应用成员统计当前未关闭告警的条数、级别和状态
  6. 条数贴回节点；明细不放进这张图
页面
  种子颜色仍用已加载的事故告警
  关联对象、应用、系统用节点上的条数和级别
  点开节点后再按页拉取告警列表，每页 20 条
```

这一层按种子 UUID 批量查实例关联的源端和目标端，只保留种子模型上已定义的 `model_asst_id`。不按 `asst_id` 开白名单，也不扫整张图。模型关系目录查失败时，不退回成只查 `run` / `connect`，整次关系记为 `unavailable`。

CMDB 扩展现有 NATS，不新开第二个方法，这样未购买、超时、图库失败仍是现在的两种结果。上下文查询失败不把整张关系图打成 `unavailable`：关系照常返回，`context_status=unavailable`，页面不画应用层，并说明应用归属暂时查不到。

告警查询用 ORM，限定在调用者有权查看的告警上，状态为未关闭，并排除观察中的会话告警。先用成员事件上的 `cmdb_id` 收到候选告警，再用这些告警的 `monitor_objects[].cmdb_id` 复核。和拓扑种子是同一身份。不扫全表 JSON，不建新的告警成员表，不写事故关联。

日志沿用现有事件名风格：一条失败一个边界，带 `incident_id`、`failed_stage`、`error_type`。不写种子 UUID、不写告警正文、不写 RPC 返回体。

### 数量边界

| 边界 | 值 | 超过之后 |
|---|---|---|
| 去重种子 | 200，沿用上周 | `truncated`，不查边、不展开、不查上下文 |
| 一跳候选 | 300 个未在基础图里的对象 | `related_truncated`，只处理这 300 个 |
| 画出来的有告警关联对象 | 40 | 按级别更严重优先，同级按 UUID 稳定排序 |
| 画出来的无告警关联对象 | 20 | 按 UUID 稳定排序。其余记入 `quiet_omitted` |
| 应用成员参与计数 | 全部命中应用合计 1000 个成员 UUID | 该应用 `member_truncated`，条数是下限，页面写「至少 N 条」 |
| 节点告警列表 | 侧栏每页 20 条 | 总数仍显示在节点上。翻页继续向后取，不截断成只能看前 20 条 |

有告警的关联对象优先留下。无告警对象被折叠时，页面写明「还有 N 个关联对象当前无告警未画入，入画请点击。」点击后这些对象全部画入。不能静默消失。

桥接即使超出无告警名额也保留。它解释种子为什么连在一起，上周已经承诺会画。

应用和系统只挂到最终画出来的对象上，不给被折叠的候选再长出一串应用节点。应用节点的告警计数仍按成员全集算，所以没画出来的成员如果在告，应用节点上看得到。

## 接口

路径、方法和权限不变：`POST /alerts/api/incident/{id}/impact_topology/`，`Incidents-View`。请求体仍是可选的 `inst_uuids`。服务端继续与事故可见种子求交。

`relation_status` 的三种值不变。新增字段只在 `ok` 时有意义。

```json
{
  "relation_status": "ok",
  "context_status": "ok",
  "alert_status": "ok",
  "message": "",
  "truncated": false,
  "related_truncated": false,
  "quiet_omitted": 0,
  "nodes": [
    {
      "inst_uuid": "",
      "inst_name": "",
      "model_id": "",
      "model_name": "",
      "layer": "host",
      "role": "related",
      "found": true,
      "alert_state": "clear",
      "alert_count": 0,
      "level": "",
      "status_counts": { "unassigned": 0, "pending": 0, "processing": 0 },
      "outside_incident_count": 0,
      "member_truncated": false
    }
  ],
  "links": [
    {
      "src_inst_uuid": "",
      "dst_inst_uuid": "",
      "model_asst_id": "",
      "asst_id": "run",
      "asst_name": "运行于",
      "parent_inst_uuid": "",
      "origin": "relation"
    }
  ]
}
```

`role`：`seed`、`bridge`、`related`、`application`、`system`。同一个 UUID 只有一个节点。又是种子又是应用时，`role` 保持 `seed`。

`alert_state`：

| 值 | 含义 |
|---|---|
| `incident` | 种子。页面用事故列表画主颜色和主条数 |
| `active` | 查到了当前未关闭告警 |
| `clear` | 查过，条数为 0 |
| `unknown` | 告警查询失败，不能当成无告警 |

`origin`：`relation` 是模型关系上的实例边，`asst_id` / `asst_name` 用这条关系自己的类型和名称；`ci_context` 是合成边。合成边的 `asst_id` 用 `context_application`（所属应用）和 `context_system`（所属系统），`parent_inst_uuid` 指向上层。

`context_status` 或 `alert_status` 为 `unavailable` 时，`relation_status` 仍可以是 `ok`。`message` 只在需要给人看的降级里出现，走告警现有文案。

CMDB 的 NATS 回包不含告警。告警服务只把条数、级别和状态分布贴到节点上。单条告警不进这张图的响应。

点开节点后的列表是另一次请求，权限与拓扑相同：

`POST /alerts/api/incident/{id}/impact_topology_alerts/`

```json
{ "inst_uuid": "", "page": 1 }
```

每页固定 20 条。请求里不接受更大的 `page_size`。`page` 从 1 开始。

```json
{
  "count": 45,
  "page": 1,
  "page_size": 20,
  "items": [
    {
      "id": 1,
      "alert_id": "ALERT-...",
      "title": "",
      "level": "",
      "status": "pending",
      "in_incident": false
    }
  ]
}
```

`inst_uuid` 必须是这一次拓扑会画出来的节点。不在图上的 UUID 不返回告警。排序先把本事故的放前面，再放未入本事故的；同一组里级别更严重的在前，然后按告警 id。种子的列表包含打在该对象上的事故告警，以及未入本事故的当前未关闭告警。关联对象只含它自己的当前未关闭告警。应用和系统含自身及其下成员的当前未关闭告警。`count` 与侧栏能翻到的总数一致。节点上的 `alert_count` 仍是该节点的主条数，种子的主条数不把事故外告警算进去。

## 前后端交互

画布仍是一次 `getImpactTopology`。节点上的条数来自这次响应。告警明细在点开侧栏和翻页时再请求，每页 20 条。

- 种子：继续用已加载的事故告警决定颜色、级别名和主条数。`outside_incident_count > 0` 时副标题加「另有 N 条未入本事故」。
- 有告警的关联对象、应用、系统：颜色用现有级别色，副标题是「级别 · N 条告警」，N 是当前未关闭条数。应用在 `member_truncated` 时写「至少 N 条」。
- 无告警：实线节点，文案「无告警」。不用未绑定那种灰，避免看成没采到。桥接且无告警保持现在的绿色虚线，角标仍是「桥接」。
- 告警未知：不涂成无告警，文案「告警情况暂时查不到」。
- 未绑定：逻辑不变，本地从没有 `cmdb_id` 的事故告警生成，不发给 CMDB。
- 图例增加「无告警」。级别色、桥接、未绑定保留。

布局仍按应用拓扑层级从上到下：系统、服务、主机、应用服务、基础设施。应用默认在服务层，应用系统在系统层，所以会自然落在对象上面。未绑定单独一排。拖动单个节点会挪开这个对象，连线跟着拉开；松开鼠标后节点停住，不再跟着指针。指针没有移动的点击仍打开右侧栏。空白处拖动仍平移整张图，滚轮和右下角按钮仍缩放。拓扑可以进入浏览器全屏，再按一次或按 Esc 退出。

点击节点仍打开右侧栏，不跳资产详情。侧栏可以手动关掉。侧栏上方是对象名称和关系，下面用表格展示告警：级别、状态、标题，以及「本事故」或「未入本事故」。多于 20 条时在侧栏分页，每页 20 条，翻页保留当前节点。应用和系统的侧栏写明「含其下对象的当前未关闭告警，未并入本事故」。每条链到 `/alarm/alarms?alert_id=`，新开标签，事故页留着。没有告警时，无告警和未知两种空态文案分开。列表请求失败时侧栏说明暂时查不到，节点不改成无告警。

刷新拓扑、关联告警、解除告警后的重查沿用现在的 effect。接口失败时页面仍把结果收成 `unavailable`，用事故告警把种子画出来，不弹错误。

## 权限

- 打开接口：事故查看权限，和现在一样。
- 种子求交：只能使用这起事故里当前用户可见的告警。
- 实例和名称：沿用 CMDB 拓扑查看权限。看不见的不进关联对象，也不进应用节点。
- 上下文：沿用 `lookup_ci_context` 的组织过滤，组织来自这次调用的用户身份。组织为空则没有应用层，不因此失败。
- 告警计数和摘要：告警查看权限内的未关闭告警。侧栏里的 `alert_id` 也必须落在这个范围内，避免凭拓扑接口摸到无权告警。

这条查询不进 OpenAPI。

## 降级

| 情况 | 页面 |
|---|---|
| 未购买 CMDB | 和现在一样，只说明未购买，不画图 |
| 关系超时或失败 | 和现在一样，只画事故告警快照，提示关系暂时查不到 |
| 种子超过 200 | 和现在一样，不展开 |
| 上下文失败 | 对象和已查到的实例关系仍在，没有应用层，提示应用归属暂时查不到 |
| 告警查询失败 | 关系和应用层仍在，相关节点是「未知」，种子仍按事故列表着色 |
| 一跳或成员被截断 | 图仍可用，提示还有对象未展开，或条数是下限 |

任何降级都不写事故、不改告警状态。

## 验收

1. 打开已有事故的影响拓扑，能看到种子沿模型全部关系向外一层的实例。属于、包含、安装于的对端和运行于、关联一样能出现。有未关闭告警的对象带级别、状态和条数；没有的标成无告警，而不是未绑定。
2. 这些对象能连到所属应用和应用系统。应用节点的条数包含其下成员的当前未关闭告警，用来区分只有这一个对象在告，还是应用已经在告。
3. 点击节点能看到告警列表，并能打开对应告警详情。超过 20 条时按页翻，每页 20 条。无 `cmdb_id` 的告警仍是孤立灰点。
4. 看完拓扑后，事故的告警成员集合不变。没有因为上级是严重就把下级从计数或列表里拿掉。
5. 未购买、关系失败、上下文失败、告警查询失败四种情况可以区分，且都不是报错弹窗。
6. 单个种子的事故也会出现一跳对象和应用层。两个种子共用的上一跳仍在，有告警时不再固定绿色。

测试锁定对外结果，不锁图库内部遍历。CMDB 用假边和假上下文行。告警侧断言只通过 CMDB RPC 客户端调用 `incident_impact_topology`，并断言事故成员关系没有写入。页面纯函数覆盖节点合成、无告警和未绑定的区别、未知状态不会画成无告警。

## 明确不做

- 不自动把关联对象或应用下的告警并入本事故。
- 不做「父红压子」，不隐藏、不降级下级告警。
- 不替换事故告警表格和甘特。
- 不从这一层的对端再展开，不以单台为中心再铺资产拓扑。
- 不在打开事故时重算应用归属，也不用现场扫图代替 `ci_context`。
- 不新增对外 OpenAPI，不新增第二张拓扑。

## 已确认

种子向外的一层，取该模型下全部关系的直接实例。`run` / `connect` 只是举例。

节点上的告警变多时，侧栏分页，每页 20 条。节点上的条数是总数。

1. 应用、应用系统的告警按 `ci_context` 成员全集统计当前未关闭告警，不只汇总图上已经画出的点。成员合计超过 1000 时条数是下限。
2. 单个告警对象也会展开一跳，并挂上命中的应用和应用系统。这覆盖上周「只有一个点」的展示。
3. 一跳对象太多时，有告警的优先留下，最多 40 个；无告警的最多再留 20 个，其余用「还有 N 个无告警关联对象未画入，入画请点击」说明。点击后全部画入。桥接始终保留。

# Mobile 运维微场景 MVP 实施计划

## 目的

本文把 [产品规格](./spec.md) 拆成可排期、可验证、可独立交付的工程任务。规格描述必须实现的用户行为；本文描述推荐的实施顺序、模块接口和完成门槛。

任务状态约定：

- `[ ]` 未开始
- `[~]` 进行中
- `[x]` 已完成并通过该任务验证
- `[!]` 因事实冲突暂停，等待产品确认

## 当前基线

- Mobile 当前一级壳只有 `apps | profile` 两个 Tab，实现在 `mobile/src/components/mobile-tab-shell/`。
- 登录成功和根路由当前固定进入 `/workbench`，分别位于 `mobile/src/context/auth.tsx` 与 `mobile/src/app/page.tsx`。
- 当前已有 `MobileNavigationProvider`、页面头、下拉刷新和主题模块，可扩展复用。
- `/conversation` 已有独立抽屉手势，必须保留为导航特例。
- Mobile 当前没有 Web 等价的应用许可与菜单权限解析模块。
- 语言已进入认证状态，但账号时区尚未形成统一状态和日期格式化入口。
- 告警、监控和 CMDB 在 Server/Web 已有能力；本计划默认复用，不默认新增数据库迁移。

## 模块设计

### 1. 平台可用性模块

在认证完成和业务页面之间建立一个深模块，隐藏许可、静态菜单、用户菜单、自定义菜单和路由回退的组合复杂度。

建议接口只暴露调用方真正需要的结果：

```ts
type MobileModuleKey = 'todo' | 'monitor' | 'assets' | 'apps' | 'profile';

interface MobileAvailability {
  status: 'loading' | 'ready' | 'error';
  visibleModules: MobileModuleKey[];
  canAccess(module: MobileModuleKey, capability?: string): boolean;
  resolveSafeRoot(preferred?: MobileModuleKey): string;
  refresh(): Promise<void>;
}
```

实现内部负责：

- 拉取和合并 Web 当前许可、静态菜单、用户菜单、自定义菜单事实；
- 复用 Web 的目录、父级、非菜单项及 operation 解析语义；
- 固定 Mobile Tab 顺序；
- 加载/失败时关闭业务入口；
- 按账号记忆最近一级 Tab；
- 失权时计算安全回退。

业务页面不得直接各自拼许可和菜单请求。生产环境使用 HTTP adapter，模块接口测试使用内存 adapter；不要再额外暴露传输层响应结构。

### 2. 账号偏好模块

建立统一账号偏好模块，向页面提供规范化后的语言、时区和时间格式化能力：

```ts
interface AccountPreferences {
  locale: string;
  timezone: string;
  formatDateTime(value: ApiDateValue, options?: DateTimeDisplayOptions): string;
  update(input: { locale?: string; timezone?: string }): Promise<void>;
  refresh(): Promise<void>;
}
```

- 语言和时区来自账号服务，并保留 Mobile 当前已有的语言和时区更新能力。
- 主题继续由现有本地主题模块负责，不得与账号偏好合并为同一种持久化。
- 时间解析、规范化和格式化在一个模块内完成，页面不再直接使用设备时区、硬编码 locale 或手写偏移。
- 更新成功后同步认证用户状态；更新失败不保留伪成功值。

### 3. 导航壳模块

`MobileTabShell` 只消费平台可用性模块给出的可见 Tab 和安全路由，不理解 Web 菜单树。

- 一级根页是返回栈边界。
- 详情页通过现有导航模块声明安全父页。
- 原生返回手势的启用规则集中在导航模块，不分散到页面。
- `/conversation` 明确保持禁用原生返回手势。

### 4. 四个业务模块

待办、监控、资产、智能应用各自拥有业务类型、请求 adapter、状态解析和页面。不得建立跨四个业务的“通用资源详情”或“通用列表仓库”；只有已有至少两个真实使用方的稳定触摸交互才进入共享模块。

## 路由建议

具体命名可在实现前按现有 Next.js App Router 约定微调，但父子关系不得改变：

| 模块 | 一级根页 | 子页 |
|---|---|---|
| 待办 | `/todo` | `/todo/search`、`/todo/alerts/[id]`、处理人选择浮层/页面 |
| 监控 | `/monitor` | `/monitor/objects/[objectId]`、`/monitor/objects/[objectId]/instances/[instanceId]` |
| 资产 | `/assets` | `/assets/search`、`/assets/models/[modelId]`、`/assets/models/[modelId]/instances/[instanceId]` |
| 智能应用 | `/workbench` | 保留 `/search`、`/workbench/detail`、`/conversations`、`/conversation` |
| 我的 | `/profile` | 保留并扩展 `/profile/accountDetails` |

动态段路由用于表达层级，不要求把业务对象缓存进导航壳。

```text
 待办      监控      资产
   \        |        /
    \       v       /
     阶段 5 回归收口
             |
             v
     阶段 6 综合质量
```

- 关键路径是 `事实核验 -> 平台事实 -> 任一业务纵向切片 -> 综合质量`。
- 待办、监控、资产只在阶段 1 接口稳定后并行，避免各自复制权限、时间和导航实现。
- 第一轮可演示版本建议按“平台壳 + 待办”形成完整纵向闭环；监控和资产随后并行接入同一壳。

## 预期文件影响

以下是模块落点建议，不是要求预先创建所有目录：

- `mobile/src/platform/availability/`：平台可用性模块与 HTTP adapter。
- `mobile/src/platform/preferences/`：账号偏好和时间格式化模块。
- `mobile/src/navigation/`、`mobile/src/components/mobile-tab-shell/`：壳与返回接口。
- `mobile/src/features/todo/`、`monitor/`、`assets/`：各业务实现与内部类型。
- `mobile/src/app/`：保持薄路由页面，只组装对应业务模块。
- `mobile/src/api/`：仅保留真正跨调用方的传输工具；不要把各业务的响应解析堆进通用 request。
- `mobile/src/locales/zh.json`、`mobile/src/locales/en.json`：同步新增文案。
- `mobile/scripts/` 或适合当前测试体系的位置：行为契约与核心流程测试。

只有出现经产品确认的现有接口缺口时，才新增 Server/Web 变更任务；届时必须单独补充服务端权限、数据范围、测试和是否迁移的影响说明。

## 每个任务的完成定义

一个任务只有同时满足以下条件才能标记 `[x]`：

1. 用户可观察行为符合 `spec.md`，没有以原型 mock 数据替代真实事实。
2. 权限、许可、账号范围和错误状态在模块接口处有覆盖。
3. 新逻辑有与风险相称的自动化验证，且测试通过模块接口观察结果，不依赖实现内部状态。
4. 中文、英文、亮色、暗色和适用屏宽已检查。
5. 没有跨模块入口、未授权直达、Mobile 专属业务模型或未确认的接口绕行。
6. 新鲜执行与影响范围匹配的 lint、类型检查、测试和构建，并在交付说明中记录结果。

# 运营分析报表表格构建器

Status: implemented

## Problem Statement

运营分析已经有一等的 `report` 画布类型，但变更前报表页只是占位骨架：页面只能读取
`view_sets.sections` 并展示统计信息，正文固定提示报表编辑能力待完善；
没有编辑态、添加组件、组件渲染、排序、删除、保存或未保存变更状态。

本期需要交付报表构建器的第一个可用纵向切片，使用户能够在报表中添加和查看组件。
当前只开放普通表格 `table` 与事件表格 `eventTable`，但“当前只开放两类”不能被
固化成“报表永远只能包含表格”的数据模型，也不能让选择器、配置器、渲染器、保存
和导入各自维护一份容易漂移的白名单。

## Solution

报表采用纵向组件列表。产品界面只呈现“组件”；底层 `section` 是一个不可见的稳定
容器，一个 `section` 恰好承载一个组件，负责组件身份和顺序，不提供独立的章节标题、
描述或设置。

普通报表默认以查看态打开；具备编辑权限的用户进入编辑态后，可添加、重新配置、拖拽
排序和删除组件，最后统一保存或取消。当前报表 surface 只注册 `table` 与
`eventTable`，选择、配置、渲染、保存和导入都通过集中的报表组件能力 seam 判断当前
支持集合。持久化结构对未来类型开放，未注册类型在当前版本中明确拒绝。

报表复用仪表盘的统一筛选语义。筛选控件不默认出现；只有搭建者从当前组件声明为
`filterType=filter` 的可绑定参数中配置了全局筛选字段，查看态才展示对应控件。组件通过
`filterBindings` 选择是否参与联动，查询参数统一由既有 Widget 请求转换链路注入。

## User Stories

1. 作为报表搭建者，我希望进入明确的编辑态并添加表格组件，从而把已有数据源组织成
   一份纵向报表。
2. 作为报表搭建者，我希望添加组件时只看到支持普通表格或事件表格的数据源和类型，
   而不是看到当前不能添加的图表或场景组件。
3. 作为报表搭建者，我希望重新配置、拖拽排序或删除已有组件，并在保存前统一预览草稿，
   从而避免每个操作立即破坏已保存报表。
4. 作为报表查看者，我希望只看到搭建者配置过的全局筛选字段，并让参与联动的表格按
   相同条件查询；日期范围、相对时间和字符串筛选均遵循数据源参数声明。
5. 作为报表查看者，我希望一张表查询失败时仍可阅读其它表格，并能单独重试失败组件。
6. 作为维护者，我希望未来开放新报表组件类型时只扩展集中的能力声明和对应实现，
   而不需要修改报表页面每一条调用链。
7. 作为并发编辑者，我希望别人的新版本不会被我的旧草稿静默覆盖，并且冲突时本地草稿
   仍然保留。

## Implementation Decisions

### 产品模型与布局

- 报表是纵向组件列表，不采用 Dashboard 式自由网格布局。
- 产品界面统一使用“组件”，不展示“章节”“新增章节”或“章节设置”等概念。
- `section` 只作为持久化容器：一个 `section` 恰好承载一个组件，保存稳定 `id` 和
  `valueConfig`。
- 组件名称与描述只存在于 `valueConfig`。`section` 不重复保存 `title` 或
  `description`，组件标题栏直接读取 `valueConfig.name`，描述直接读取
  `valueConfig.description`。
- 所有组件使用统一标准高度。组件内容在自身内部滚动或分页；本期不允许拖拽调整高度。
- 组件之间按 `sections` 数组顺序纵向排列。编辑态通过组件标题栏的拖拽手柄排序；
  重排只改变数组顺序，不改变 `section.id` 或组件配置。
- 不设置组件数量硬上限。组件按滚动视口延迟激活，并复用现有运行时请求调度控制并发；
  不允许长报表在首次打开时无界并发请求所有组件。
- 已加载组件保留当前展示结果。执行全局筛选搜索时，参与联动的组件按运行时调度顺序刷新。

### 查看态与编辑态

- 报表默认进入查看态。
- 非内置报表且用户具备现有 `EditChart` 权限时，才显示并允许进入编辑态。
- `is_build_in=true` 的报表保持只读，隐藏编辑入口，不允许添加、配置、排序或删除组件。
- 编辑态提供：添加组件、组件配置、拖拽排序、删除、保存、取消。
- 添加、配置、排序和删除只修改本地草稿，不逐项写入服务端。点击“保存”后一次性持久化
  完整报表配置；点击“取消”恢复最后一次成功保存的状态。
- 点击删除先显示简短二次确认。确认后从本地草稿移除；只有保存成功后删除才持久化，
  取消编辑可恢复。
- 已添加组件允许通过标题栏“配置”入口重新打开现有组件配置界面。配置提交只更新本地
  草稿，报表保存成功后才持久化。
- 本期不提供复制组件。
- 存在未保存改动时，切换报表、切换其它画布类型或离开页面，统一触发现有未保存变更
  确认。只有明确放弃后才允许离开。
- 保存失败时保持编辑态并保留完整草稿，不回滚、不退出。

### 添加组件流程

- 复用现有运营分析组件选择器与组件配置能力，不建立报表专用的数据源或表格配置器。
- 组件选择器新增 `report` surface 语义：
  - 隐藏“场景组件”分类；
  - 只展示至少支持一个当前已注册报表组件类型的数据源；
  - 数据源卡片只展示其声明类型与报表当前支持集合的交集；
  - 选择数据源后，配置界面只展示交集中的图表类型。
- 当前 `report` surface 注册的类型只有：
  - `table`：普通表格；
  - `eventTable`：事件表格。
- 未注册类型不以禁用项或占位项出现，而是从选择与配置入口隐藏。
- 组件配置继续使用现有 `valueConfig` 合同，包括数据源、数据源参数、名称、描述和
  表格专有配置；报表不得复制或分叉普通表格与事件表格的配置模型。

### 报表组件能力 seam

- “报表当前开放哪些组件”是一个集中、可扩展的能力策略，不是永久的封闭类型定义。
- 前端扩展现有 `chartTypeSurface` seam，使其支持 `report` surface。报表选择、配置和
  渲染必须查询同一个能力目录；报表页面不得散落
  `chartType === 'table' || chartType === 'eventTable'` 判断。
- 数据源 `chart_type` 表示“数据源能够提供什么”；报表能力目录表示“报表当前开放什么”。
  可添加类型始终是两者交集，二者不能合并为同一个概念。
- 后端提供单一的报表 `view_sets` 校验/规范化入口。Report 创建、更新及 YAML 导入都
  必须复用该入口，不能分别维护白名单或不同错误语义。
- 前后端各自拥有其运行时所需的集中支持集合，并通过契约测试保证当前注册类型一致。
  不引入后端动态下发 React 配置器或渲染器的协议。
- 未注册类型在新增入口中不可见；保存、创建或导入遇到未注册类型时明确拒绝，并返回
  可定位到 `sections[index].valueConfig.chartType` 的校验错误。禁止静默删除、降级或
  转换未知类型。
- 持久化字段 `valueConfig.chartType` 保持可扩展字符串，不定义为仅含 `table` 与
  `eventTable` 的永久封闭枚举。
- 将来开放新类型时，先在前后端能力目录登记并补齐配置、渲染、校验及契约测试。只有
  当真实的新类型需要不同配置流程、渲染策略或默认值时，才把能力目录深化为类型
  Adapter 注册表；本期不预先建立通用插件生命周期。

### 持久化合同与版本

报表 `view_sets` 从本期开始使用显式结构版本：

```ts
interface ReportViewSetsV1 {
  schema_version: 1;
  filters: UnifiedFilterDefinition[];
  sections: ReportSectionV1[];
}

interface ReportSectionV1 {
  id: string;
  valueConfig: ValueConfig;
}
```

- `schema_version` 当前固定为 `1`。
- 旧的无 `schema_version` 报表按版本 1 读取；现有报表尚无可编辑组件，因此兼容路径不得
  凭空制造组件。
- `sections` 必须是数组；每个条目必须有非空且在报表内唯一的稳定 `id`，以及合法的
  `valueConfig`。
- 添加组件时生成新的稳定 `section.id`；重新配置和排序不得更换该 ID。
- `valueConfig.chartType` 必须是当前已注册的报表组件类型，且配置必须满足该类型现有的
  提交归一化与持久化合同。
- 保存采用整个 `view_sets` 的原子替换，不提供逐 section 的独立增删接口。
- YAML 导入先完成数据源等引用重写，再走同一个报表结构与组件能力校验；非法导入整体
  拒绝，不产生残缺报表。
- YAML 导出保留 `schema_version`、`filters`、section 稳定 ID 与完整
  `valueConfig`。

### 报表统一筛选

- 报表不默认显示独立时间控件，不按参数类型自动接管组件时间。
- 编辑态复用现有“配置全局筛选字段”入口，从报表当前组件数据源中扫描
  `filterType=filter` 且类型可绑定的参数；普通参数和固定参数不进入候选。
- 画布级 `filters` 保存筛选定义、显示名称、类型、默认值、顺序和启用状态；组件级
  `valueConfig.filterBindings` 保存该组件是否参与某个定义的联动。
- 定义与参数按 `key + type` 严格匹配。只有定义启用、组件绑定启用且存在本次搜索值时，
  才由既有 `buildWidgetRequestParams` 链路注入；绑定或定义关闭时明确不传该参数。
- 查看态修改筛选值只在当前会话生效，点击搜索后才成为各组件的 applied values 并触发
  参与联动的组件刷新，不写回 `view_sets`。
- 编辑态修改筛选定义属于报表草稿，随完整 `view_sets` 一起保存或取消；筛选值本身不作为
  查看态状态持久化，只有定义中的默认值持久化。
- `dateRange` 使用日期范围控件，`timeRange` 使用相对时间控件，字符串等其它可绑定类型
  使用其已有输入模式；控件类型来自参数声明，不能统一伪装成时间范围。
- 旧 V1 的 `time_range` 只作兼容读取并在下次保存时移除；由于它没有目标参数 key，禁止
  猜测或自动绑定到任意组件参数。

### 组件运行时状态与错误隔离

- 表格运行时的分页、列排序、列筛选、关键字搜索和事件详情展开状态只在当前查看会话
  生效，不写入报表 `view_sets`。
- 只有通过组件“配置”入口修改的列定义、默认排序、筛选字段等设计态设置才进入草稿并
  随报表保存。
- 每个组件独立拥有 loading、empty、ready 和 failed 状态。一张表查询失败不得使整份
  报表空白、失败或阻断其它组件继续加载。
- 失败组件在自身固定高度区域内显示可读错误状态和单组件重试入口；重试只请求该组件。
- 延迟激活前的组件不得显示为查询失败；进入预加载视口后才进入既有组件请求生命周期。

### 并发编辑

- 进入编辑态时记录当前服务端报表版本。具体使用显式 revision 或现有更新时间作为条件
  token 属于实现选择，但比较必须由服务端完成，不能只在前端猜测。
- 保存时携带该版本条件；若报表已被其他请求更新，服务端拒绝旧版本覆盖并返回稳定的
  并发冲突错误。
- 冲突后保持编辑态与本地草稿，提示用户刷新后重试；不得自动覆盖服务端新版本，也不得
  静默丢弃本地草稿。
- 正常保存成功后，用服务端返回的 canonical `view_sets` 与新版本 token 更新本地基线，
  并清除 dirty 状态。

## Testing Decisions

测试只断言可观察合同，不锁定具体 DOM 层级、拖拽库、IntersectionObserver 封装或请求
调度实现。

### 前端能力与选择流程

- `report` surface 当前只支持 `table` 与 `eventTable`；Dashboard 与 Screen 现有能力
  不因新增 surface 回退。
- 数据源候选按“数据源声明类型 ∩ 报表注册类型”过滤；不支持两种表格的数据源不出现。
- 场景组件入口在 report surface 不出现。
- 配置界面只显示当前数据源支持的普通表格/事件表格，不显示其它类型。
- 前端能力目录与后端注册集合有契约测试，防止一端能添加而另一端拒绝。

### 草稿与编辑状态机

- 默认查看态；有权限的非内置报表可进入编辑态；无权限或内置报表没有编辑入口。
- 添加、配置、排序、确认删除只修改草稿；取消恢复保存基线；保存成功才更新基线。
- 拖拽排序只改变 section 顺序，稳定 ID 与 `valueConfig` 不变。
- 删除取消确认时不改变草稿；确认删除后取消整次编辑仍能恢复组件。
- 保存失败、并发冲突均保留草稿和编辑态。
- dirty 时切换报表、画布类型或离开页面触发确认；无 dirty 时不阻断。
- 空报表编辑态提供可发现的添加组件入口，保存空 `sections` 仍是合法状态。

### 数据合同与后端校验

- 新保存结构写出 `schema_version: 1`、合法 `filters` 和只含 `id`、
  `valueConfig` 的 sections。
- 缺少版本的旧空报表按版本 1 读取。
- 非对象 `view_sets`、非数组 `sections`、缺失/重复/空 section ID、缺失
  `valueConfig`、缺失或未注册 `chartType` 均明确拒绝，并返回字段路径。
- `table` 与 `eventTable` 的合法配置可创建、更新、导入、导出并回读。
- 未注册类型在创建、更新和导入中都拒绝；不得静默删除或转换。
- 导入引用重写完成后仍经过同一校验入口；失败时不落入部分报表数据。
- 前后端均不把持久化 `chartType` 类型声明封闭为永远只有两种。

### 统一筛选

- 无筛选定义时不显示筛选栏；不得默认显示时间控件。
- 只有 `filterType=filter` 的可绑定参数进入配置候选，控件类型与参数类型一致。
- 保存/取消筛选定义遵循报表草稿边界；查看态搜索值不持久化。
- 定义和组件绑定均启用时，搜索值按 `key + type` 注入请求；未绑定或关闭时不传。
- `dateRange` 能驱动日期参数，`timeRange` 能驱动相对时间参数；不得把日期范围误当成
  `timeRange`。
- 旧 `time_range` 不产生隐式绑定，下一次保存 canonical 结构时移除。

### 渲染、错误与性能

- 普通表格与事件表格都能在固定高度容器内渲染，超出内容在组件内部滚动或分页。
- 组件分页、搜索、筛选、排序和事件展开不会使报表变 dirty，也不会写回
  `view_sets`。
- 单组件失败不影响其它组件；单组件重试不重拉整份报表。
- 视口外组件不会立即发起数据请求；进入预加载范围后才激活。
- 大量组件的首次加载使用受控并发，不出现与组件数量等量的无界并发请求。
- 筛选搜索后的刷新继续遵守受控调度和最新请求生效语义，旧响应不得覆盖新筛选结果。

### 并发

- 两个客户端基于同一版本编辑时，第一个保存成功并获得新版本，第二个旧版本保存被拒绝。
- 冲突响应不修改服务端新版本，不清空第二个客户端草稿。
- 成功保存后客户端基线与服务端 canonical 响应一致，dirty 状态清除。

## Out of Scope

- 普通表格和事件表格之外的报表组件类型。
- 完整的通用组件插件系统或由数据库、环境变量动态开放图表类型。
- 显式章节概念、章节标题/描述、章节目录、一章节多组件、正文或富文本。
- Dashboard 式自由网格、横向并排、组件尺寸调整或用户自定义高度。
- 复制组件。
- 报表组件数量硬上限。
- 把分页、搜索、筛选、排序、事件展开等查看态状态持久化。
- 报表分享、PDF 导出、报告订阅、打印版式、周期刷新：本切片不做；后续由
  [`ops-analysis-report-canvas-toolbar`](../ops-analysis-report-canvas-toolbar/spec.md) 交付。
- 重构 Dashboard、Screen 或通用 Widget 全部类型为 Adapter 插件。

## Further Notes

- 本 spec 中“报表”指运营分析的一等 `report` 画布，不是 Dashboard 的 PDF 报告或
  “报告订阅”。
- `section` 是存储术语，不是第一阶段的产品术语。后续若引入正文、目录或一章节多组件，
  应通过新的 `schema_version` 明确迁移，不能在版本 1 字段上偷偷改变含义。
- “未知类型拒绝”与“未来可扩展”并不冲突：前者保护当前版本的数据完整性，后者由集中
  能力 seam 和开放的持久化判别字段保证。
- 已将稳定交付事实同步到
  `specs/capabilities/legacy-ard-modules-operation-analysis.md`；详细设计和测试边界继续由本
  change spec 保存。

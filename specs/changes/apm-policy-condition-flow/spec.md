# APM 策略条件按一句来填

Status: implemented（2026-10-29）

## 实现偏差

- 比较基准下拉直接列出「N 小时前同窗」和「N 天前同窗」，不再先选「同窗」再选对照方式。已保存的 `offset_1h` / `offset_24h` 打开时仍回填为 N 小时前同窗。
- 检测频率和汇聚周期放在级别表下面、触发条件上面。告警条件读成：级别，然后每 N 分钟看最近 M 分钟，再接触发方式和连续恢复。
- 单条件的比较基准、小时数、天数、最低请求数仍用原来的无字母标签，这样一条条件时读起来没有「条件 a」。
- `slo_burn_rate` 仍不展示汇聚周期，也不展示「每 N 分钟评估一次最近 M 分钟」。评估窗是燃烧长短窗。
- 验收：`apps/apm/tests/test_policy_conditions.py` 27 通过。策略编辑器 vitest 中与本批相关的用例通过，含单条件比较基准、多条件上限、最后一条常规不能改成前置、第一张卡改成前置后顺序不变。编辑器文件 eslint 无告警。`tsc -p tsconfig.build.json` 在本批文件上无新增错误；`policyFormUtils.ts` 的两条既有类型错误不在本次改动里。

## Problem Statement

配置 APM 策略时，一条条件不是顺着读完的。只配一条时，「指标条件」卡里通常只有指标，外加一行不能改的「类型：常规」；比较基准和阈值在下一步。加上第二条之后，新卡里突然有比较基准和最低请求数，第一条仍然没有。

「添加条件」在常规条件满 3 条之前一律加常规条件，满了就静默加前置条件。把常规改成前置会丢掉已填的比较和级别，并把门槛写成 200，而且这个数不在这张卡上。第一条不能改成前置，所以「先看请求数够不够，再看错误率」排不出来。检测频率在「基本信息」，汇聚周期在条件卡下面，连续几次在「告警条件」。

监控多指标已经是一个「添加条件」，类型写在卡上。APM 不该再做两个添加按钮。

## Solution

一条条件时，条件卡写完「看哪个数、相对谁、够不够数」。级别、检测频率、汇聚周期和触发次数放在旁边。不显示字母，也不显示类型。

出现第二条之后，每张卡都有类型「常规」或「前置条件」，并显示字母。添加仍然只有一个按钮，新条件默认常规。改成前置后，只属于告警线的控件消失，门槛写在这张卡上。卡片留在原来的位置。恢复阈值和详情图跟着列表里的第一条常规条件。

判定语义不变：常规条件全部满足，级别取最轻的一档；前置条件是绝对门槛，不满足走恢复。

## User Stories

1. 作为配置策略的人，我只配一条条件时，想在同一张卡上选完指标、比较基准和最低请求数，并在旁边写下级别和「每 N 分钟看最近 M 分钟」，这样不用在两个步骤里找同一句话。
2. 作为配置策略的人，我想用一个「添加条件」加上下一条，再在卡上把类型改成常规或前置条件，这样和监控多指标的加条件方式一样。
3. 作为配置策略的人，我想把第一张卡改成前置条件并留在上面，让下面的常规条件成为告警线，这样可以按「先看请求数，再看错误率」来读。
4. 作为配置策略的人，我想在前置条件上只填一个门槛；如果这个指标是慢请求或 Apdex，还能填它自己的慢阈值或 T，这样门槛用的定义不会错用到告警线上的那个数。
5. 作为配置策略的人，我想保存后再打开时，卡片顺序和我摆的一样，这样排在上面的前置条件不会被挪到告警线后面。

## Implementation Decisions

- 能力边界不动。仍是命名指标和下拉，不做查询语言。最多 3 条常规条件，必须全部满足，级别取最轻的一档。最多 2 条前置条件，只做绝对门槛。每条常规条件仍可有自己的比较基准，一条策略里不同对照窗不超过 2 个。没有汇聚方法，没有策略级无数据开关。无流量和 SLO 燃烧率仍是单条件类型。
- 编辑器用一份按显示顺序排列的条件列表。策略行上的指标、比较基准、阈值等镜像列，保存时仍取列表中第一条常规条件。只有一条常规条件且没有前置条件时，可以继续不提交条件列表，沿用镜像列，避免单条件策略改写成新的存储形状。
- 一条条件时不显示字母，也不显示类型。卡上的顺序是：指标、这个指标自己的慢阈值或 Apdex T、比较基准、比较方式、最低请求数。比较基准是一个下拉：当前值、相对上一等长窗、N 小时前同窗、N 天前同窗、近 N 天同窗均值。后三项再出现数字。变化量和变化率在相对比较时出现。标准差只在「近 N 天同窗均值」且天数至少 3 时出现。最低请求数只出现在本来就受它约束的指标上。取值范围、对照长度不能短于汇聚周期、窗口不能短于检测频率，都沿用现有校验。
- 级别表留在「告警条件」。行是级别，列是常规条件。只有一条时，列上不显示字母。出现第二条条件后，常规条件的列和卡片一起显示字母。前置条件不进这张表。恢复阈值仍只有一组，写在级别表旁边，作用于第一条常规条件。卡片上不另加说明。
- 检测频率从「基本信息」挪到「告警条件」，汇聚周期从条件卡下方挪到同一处。三者读成：每 N 分钟看最近 M 分钟，再接现有的触发方式（连续 K 个周期，或在最近 N 个周期内命中 M 次）和连续恢复。作用范围、服务、端点、实例、目标类型留在「指标定义」，放在条件卡上面。通知步骤不动。
- 添加只有一个「添加条件」，加在列表末尾，默认常规，默认指标沿用现在新增常规条件的默认指标。常规条件已经有 3 条、前置条件少于 2 条时，新卡打开就是前置条件，类型直接显示为前置条件。两边都满了，按钮不可用。不做拖拽排序。
- 条件多于一条时，每张卡都有类型，包括第一张。选项与监控多指标相同：常规、前置条件。只剩一条常规条件时，不能把它改成前置条件。改类型不改变卡片位置，字母也不改。
- 常规改成前置：去掉比较基准、比较方式、最低请求数和级别。门槛留空，比较符默认「大于等于」，不预填 200。慢请求保留慢阈值，Apdex 保留 T，其他指标不显示这两项。前置改成常规：比较基准回到当前值，级别留空。指标若是请求数，改成一个常规条件允许的指标，因为请求数只能做前置条件。
- 前置条件的卡上只有：指标（比常规条件多「请求数」）、慢阈值或 T、比较符和一个门槛值。不显示比较基准和最低请求数。无流量和 SLO 燃烧率不能作为前置条件，也不能和别的条件并存。在会清掉其他条件的那张卡上选中它们时，沿用现在的行为：清空其余条件，回到对应的单条件表单。
- 保存时按编辑器顺序写入条件列表，不再重排成「常规在前、前置在后」。锚点仍是这条列表里的第一条常规条件，不是视觉上的第一张卡。已保存成「常规在前」的旧策略打开时顺序不变。
- 前置条件若是慢请求或 Apdex，慢阈值或 T 记在这条前置条件上，取值使用这条上的数。现在前置条件取值会把这两项清空，再落到策略镜像列，多条件时会用错告警线的定义。请求数前置条件仍读锚点同一次评估窗的请求数，不为此再查一次。
- 试算、快照和告警详情的判定结果不变。详情主趋势仍只画锚点。条件多于一条时，锚点不一定是字母 a。

## Testing Decisions

只锁从页面和保存接口能看到的行为。编辑器测试沿用现有策略编辑器测试：单条件没有类型和字母，比较基准在卡上，检测频率不在基本信息；添加第二条后两张卡都有类型和字母；把一张常规条件改成前置后，级别表少一列，门槛在该卡上且不是预填的 200；最后一条常规条件不能改成前置；已有 3 条常规条件时再添加，新卡是前置条件；把第一张卡改成前置后，提交的条件顺序仍是前置在前，镜像列来自后面的常规条件。

序列化测试沿用现有条件接口测试：提交「前置在前、常规在后」时原样保存，镜像列等于那条常规条件；前置条件携带自己的慢阈值或 T 时被接受，取值用的是这个数而不是锚点上的数；请求数前置条件仍不产生额外查询。单条件且没有前置条件的保存载荷保持现在的镜像列形状。

## Out of Scope

任意满足、查询语言、把三级阈值放进每张卡、拖拽排序、汇聚方法、策略级无数据开关、把触发条件改成「持续 N 分钟」、改监控或日志的编辑器。无流量和 SLO 燃烧率的单条件表单不改成这套多条件卡。

## Further Notes

第四批「整窗取值、去掉无数据开关」已实现。本规格从那个编辑器往下做，不把汇聚方法和无数据开关加回来。

同日曾考虑用两个按钮区分「再看一个指标」和「先满足一个门槛」。改为一个「添加条件」加卡上的类型，是为了和监控多指标一致。

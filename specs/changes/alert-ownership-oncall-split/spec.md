# 告警归属与值班分离

Status: implemented

## Completion Evidence

- HTTP 默认告警列表（活跃 / 历史）按「当前组织归属 ∪ 当前处理人」过滤；`my_alert=1/true/yes` 时只保留处理人是自己的告警；`org_only=1` 时只保留归属组织（显式 API 开关，Web 趋势图不再使用）。
- 当前处理人可打开详情、本条关联事件、认领/转派/关闭；邻近告警仍按当前组织归属裁剪。
- 手动分派/转派校验改为用户存在且未禁用，不再要求属于 `Alert.team`；转派替换处理人。
- OpenAPI / 绑定组织机器身份仍只按团队过滤，处理人身份不能读出其他组织告警。
- 前端趋势图与当前列表共用同一套过滤（含 `my_alert`），不传 `org_only`，保证图上的数据就是列表里看到的集合。
- 覆盖测试：`apps/alerts/tests/test_ownership_oncall_split.py`，以及 OpenAPI `test_list_alerts_does_not_include_operator_assigned_other_team`。
- 验证（2026-08-26，`uv run pytest ... --no-cov`）：**156 passed**，范围包括归属/值班拆分、处理人校验、自动分派、升级、OpenAPI 查询/操作、事故告警视图回归。

## Problem Statement

告警中心已经允许自动分派把处理人写成归属组织之外的用户（组织目标、升级链），但列表、详情和操作仍按 `Alert.team` 与当前组织 Cookie 隔离。结果是：值班人能收到通知，却进不了「我的告警」，也打不开、认领不了这条告警。手动分派和转派还额外要求处理人属于归属组织，人工无法把单交给共享 NOC / 二级值班。

## Solution

把「数据归属」和「值班处理」拆开。作业执行范围继续只看归属组织。告警列表与页面趋势按当前可见集合统计。当前处理人通过「我的告警」跨组织看见并处理自己的单。手动分派、转派、自动分派、升级都可以把单交给租户内任意有效用户。转派是交班（替换处理人），升级是加签（并入处理人）。

## User Stories

1. As a 归属组织成员, I want 告警列表展示本组织归属的告警以及处理人是我的告警, so that 我不必切组织也能看到代班的单，同时本组织未分派给我的单仍然在列表里
2. As a 跨组织值班人, I want 「我的告警」只列出处理人是我的告警而不受归属组织限制, so that 值班队列不被本组织其他人的单淹没
3. As a 跨组织值班人, I want 从「我的告警」打开详情并认领、转派、关闭, so that 分派不会停在一条看不了的通知
4. As a 能看见未分派告警的人, I want 把告警分给租户内任意有效用户, so that 本组织可以把单交给共享值班
5. As a 当前处理人, I want 把告警转派给租户内任意有效用户并立刻离开「我的告警」, so that 交班后队列里只剩我还负责的单
6. As a 升级链上的处理人, I want 升级后仍留在处理人列表, so that 链上任何人都还能认领
7. As a 未分派告警的归属组织成员, I want 未分派单只出现在组织列表而不是别人的「我的告警」, so that 组织外的人不能抢尚未分派的单

## Implementation Decisions

- 继续用 `Alert.team` 表示数据归属；分派、转派、升级不得改写归属，也不得扩大作业 / Action 的目标范围（仍为告警归属与规则组织的交集）。
- HTTP 告警默认列表（活跃、历史）按当前组织归属 **或** 当前用户是处理人；打开「我的告警」时只按处理人精确成员过滤。页面趋势与当前列表同一套过滤。用户仍须持有合法当前组织会话。
- 「我的告警」匹配必须是处理人集合的精确成员关系，不能把用户名当成 JSON 字符串的子串包含。
- 告警详情、本条告警关联的原始事件、认领、转派、关闭、处理：调用者满足「看得到归属」或「自己是当前处理人」之一即可进入对象；对象级动作仍遵守现有状态机（认领 / 转派 / 关闭仍要求当前处理人，未分派的分派仍要求能看见该归属告警）。
- 邻近告警、运营分析画布继续走归属组织范围，不因处理人身份放行其他组织的告警。告警中心页面趋势与当前列表一致。
- 手动分派、转派的处理人校验改为：同租户、用户存在、未禁用。不再要求属于告警归属组织。自动分派的用户目标与组织目标、升级写入处理人，与这条校验对齐。
- 转派替换处理人集合；被换下的人立刻从「我的告警」消失，也不能再认领 / 转派 / 关闭。升级继续把新一层并入处理人集合。
- 机器身份入口（OpenAPI 密钥绑定组织、NATS 显式团队上下文）仍只按绑定组织过滤，不按处理人补可见性。
- 前端「我的告警」从「当前组织内再筛我的」改为真正的跨组织入口；分派 / 转派选人不再暗示必须属于当前组织，以后端拒绝禁用或不存在的用户为准。
- 现有「处理人不在告警所属组织范围内即拒绝」的断言作废，改为覆盖跨组织处理人可见与可操作。

## Testing Decisions

- 只测对外行为：列表可见性、详情可达、分派 / 转派校验、转派后队列变化、升级后处理人累加、趋势与列表同过滤、作业范围不放大。不测内部函数如何拼 Q 对象。
- 优先复用告警列表 / 详情 ViewSet、处理人操作、自动分派链路、升级 BDD、权限范围、OpenAPI 操作人这些现有测试入口；在这些入口上改期望并补跨组织用例，而不是为可见性再开一套平行框架。
- 必测组合：
  - 归属组织成员看见组织列表中的告警，即使自己不是处理人。
  - 处理人不在归属组织时，默认活跃/历史列表和「我的告警」都看得到；未分派给自己的其他组织告警仍看不到。
  - 默认列表（即页面趋势所用查询）包含跨组织分派给自己的告警；显式 `org_only=1` 才只按归属。
  - 手动分派 / 转派接受归属组织外的有效用户，拒绝禁用或不存在的用户。
  - 转派后原处理人从「我的告警」消失且不能再操作；新处理人可以。
  - 升级后新旧处理人都在「我的告警」。
  - 打开「我的告警」时列表与趋势都只含处理人是自己的告警；邻近告警仍不暴露其他组织未分派给自己的告警。
  - OpenAPI 仍不能借处理人身份读出绑定组织之外的告警。
- 回归现有认领必须是处理人、跨组织不可操作自己不是处理人且看不见的告警、Action 目标求交。

## Out of Scope

- Incident 协同人跨组织可见、事故确认 / 关闭是否要求负责人。
- 把分派规则、屏蔽规则、未分派兜底通知改成按组织隔离。
- 转派后仍可见但不能操作的观察者角色。
- 把 `Alert.team` 从列表收成单值，或改写 Event 归属口径。
- 新的独立「值班队列」页面、导航信息架构大改。
- 为跨组织值班新增数据库字段或迁移。

## Further Notes

这是对「权限与 Incident 协同边界」里「Alert 是数据权限根、分派与归属解耦」的补完，而不是推翻归属模型。组织目标自动分派的既有规格仍然有效：组织成员变化只影响后续通知，不改已经写入的处理人快照。本期补的是快照写进去之后，这些人必须能看见、能处理。

# SNMP 固定 250 槽位、1000–6000 瞬时积压与调度量子压测报告

Date: 2026-08-27
Status: completed
Conclusion: 250 个在途槽位可以在 30 分钟 Run 周期内消费 6000 个全部耗尽 30 秒预算的目标；调度等待不侵蚀单目标预算；最终固定 `quantum=1`。

## 1. 正确的测试问题

本轮按以下生产语义测试：

```text
全局在途并发固定：250
瞬时到达目标数：1000 / 2000 / 3000 / 4000 / 5000 / 6000
单目标正式采集超时：30秒
Collection Run deadline：1800秒（30分钟）
调度量子候选：1 / 2 / 4 / 8
```

目标在等待 250 个槽位时不启动单目标 30 秒预算；获得槽位、进入正式采集后才开始计时。Run 的总墙钟仍受独立 1800 秒 deadline 约束。

一次瞬时提交 6000 个目标，并记录完成到 1000、2000……6000 时的累计里程碑。这样六档积压位于同一进程、同一负载条件，避免分开运行带来的机器状态差异。

## 2. 测试边界

### 2.1 纳入的生产代码

- `CollectionScheduler` 的真实流式取目标、250 槽位、Task、取消和关闭路径；
- `SnmpFacts.collect()` 的真实参数、OID、每目标 `SnmpEngine` 初始化和 `finally` 关闭；
- 与正式采集一致的 `asyncio.timeout(30)` 外层取消；
- 6000 目标排队、250 在途、超时释放槽位和补充下一目标的完整循环。

### 2.2 隔离项

`getCmd` 被替换为永不返回的本地异步函数，不向客户或公网设备发包，从而稳定制造“每一台都耗尽 30 秒”的最坏情况。

本轮负载循环直接验证调度排队、Engine 同步初始化和外层超时边界，不包含 Redis、NATS、HTTP 入口、结果发布以及真实 SNMP `timeout=10s, retries=1` 的网络报文。表中 callback error=0 仅代表该负载循环没有事件循环异常，不能单独证明 pysnmp 回调取消安全。另有不替换 `getCmd` 的 32 路本地真实 pysnmp 并发取消回归，验证 dispatcher 关闭后没有迟到 callback error。真实设备成功响应后还会执行接口 WALK 和结果解析，因此不能用本报告否定生产环境中 250 并发已经压满 CPU 的既有证据。

### 2.3 环境

- Apple Silicon macOS；
- 8 logical CPU、16 GiB RAM；
- Python 3.12、pysnmp 5.1.0；
- 四个量子顺序执行，避免多个压测进程争抢 CPU。

## 3. 判定门槛

- 6000 个目标必须全部形成终态，且总墙钟 `<1800s`；
- Engine 与 asyncio Task 峰值必须受 250 槽位约束；
- callback error 必须为 0；
- event-loop lag P99 `<500ms`；
- timeout overshoot P99 `<1s`；
- 较 `quantum=1` 没有稳定且可重复的 `>=3%` 吞吐提升时，保留 `1`。

## 4. quantum=1：1000–6000 积压里程碑

| 瞬时积压目标数 | 累计完成时间 | 累计 timeout overshoot P99 | 30分钟内完成 |
| ---: | ---: | ---: | --- |
| 1000 | 126.44s | 337ms | 是 |
| 2000 | 247.26s | 392ms | 是 |
| 3000 | 367.85s | 354ms | 是 |
| 4000 | 494.47s | 799ms | 是 |
| 5000 | 614.87s | 750ms | 是 |
| 6000 | 735.52s | 669ms | 是 |

6000 档完整指标：

| 指标 | 结果 |
| --- | ---: |
| 完成目标 | 6000/6000 |
| 总墙钟 | 735.52s（12分16秒） |
| 距 30 分钟 deadline 余量 | 1064.48s（17分44秒） |
| Engine 峰值 | 250 |
| asyncio Task 峰值 | 253 |
| RSS 峰值 | 274.4MB |
| event-loop lag P99 | 50ms |
| timeout overshoot P99 | 669ms |
| timeout overshoot max | 1.21s |
| 调度等待 P99 | 703.52s |
| dispatch-to-start P99 | 0.8ms |
| callback error | 0 |

调度等待 P99 达到约 11 分 44 秒，但单目标 timeout overshoot P99 只有 669ms。这是“排队不计入单目标 30 秒预算”的直接证据；如果排队被计入，后排数千目标应在约 30 秒时一起失败，而不是持续 12 分钟按 250 槽位完成。

## 5. quantum 对照

四轮均为 6000 个目标瞬时到达、固定 250 槽位、单目标 30 秒、Run deadline 1800 秒。

| quantum | 总墙钟 | 相对 q=1 | overshoot P99 | loop lag P99 | dispatch-to-start P99 | callback error | 判定 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 735.52s | 基线 | 669ms | 50ms | 0.8ms | 0 | 选择 |
| 2 | 730.22s | 快 0.72% | 347ms | 90ms | 32ms | 0 | 收益不足 3% |
| 4 | 730.75s | 快 0.65% | 458ms | 41ms | 118ms | 0 | 收益不足 3% |
| 8 | 733.90s | 快 0.22% | 1530ms | 38ms | 254ms | 0 | overshoot 越线 |

不能按 `6000 / quantum` 推导 yield 次数。初始填满 250 槽位后，目标超时通常错峰释放，稳态经常只有一个空槽可补：

| quantum | scheduler yield 次数 |
| ---: | ---: |
| 1 | 6000 |
| 2 | 4279 |
| 4 | 4018 |
| 8 | 4212 |

量子增大没有改变 24 批左右的设备等待主成本，只减少部分极轻量的调度让权；因此总周期差异不到 1%。与此同时，dispatch-to-start P99 随量子从 0.8ms 增长到 254ms，`quantum=8` 还把超时偏差 P99 放大到 1.53 秒。

## 6. 结论

### 6.1 新架构是否还存在本次超时问题

- 不存在“排队中的目标被 30 秒单目标预算提前掐掉”的问题；
- 6000 个瞬时积压目标始终只保持 250 个 Engine 在途，Task 峰值 253，没有一次性创建 6000 个活跃采集任务；
- `quantum=1/2/4` 均未出现 callback error，超时偏差 P99 小于 1 秒；
- `quantum=8` 重新出现 1.53 秒 P99 超时漂移，因此较大批次仍可能放大同步初始化和取消汇聚；
- 6000 个全超时目标在 12 分 16 秒完成，满足 30 分钟 Run 周期。

### 6.2 quantum 最终值

固定 `quantum=1`，不提供环境变量：

1. `2/4` 的总时间收益都不到 1%，显著低于 3%门槛；
2. 槽位稳态错峰释放，较大量子多数时候凑不满批次；
3. `dispatch-to-start` 随量子增大而恶化；
4. `8` 已违反超时偏差门槛；
5. `1` 的行为最简单、响应最确定，且 6000 档已有 17 分 44 秒周期余量。

### 6.3 容量解释

本轮证明“250 槽位 + 新调度架构”在全部无响应的外层超时场景下功能正确，但不单独证明生产真实设备的 CPU 容量安全。真实成功采集还包含 SNMP 报文处理、GETNEXT/WALK、结果解析和发布；因此生产是否从 200 提升到 250，仍应结合目标机器和真实设备响应压测决定。

## 7. 复现命令

```bash
cd agents/stargazer
.venv/bin/python scripts/benchmark_snmp_scheduler.py \
  --targets 6000 \
  --concurrency 250 \
  --quantum 1 \
  --target-timeout-seconds 30 \
  --cycle-deadline-seconds 1800 \
  --milestone-step 1000
```

量子对照完成后生产实现已固定为 `1`，脚本现在也只接受 `--quantum 1`，用于复现最终
架构的积压与超时边界；表中的 `2/4/8` 数据保留为定标历史证据，不再对应生产可调入口。

## 附录 A：误解口径后的边界诊断

澄清需求前曾把“1000–5000 个瞬时到达目标”误解为“1000–5000 个同时在途槽位”。该组边界实验不属于正式需求结论，但留下了一个有效诊断事实：当在途 Engine 提高到上千时，RSS 达到约 0.7–1.2GB，3000 以上出现 1–2 秒级超时长尾；因此不能把积压目标总数直接配置为在途并发数。

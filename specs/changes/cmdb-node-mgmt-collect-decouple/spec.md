# CMDB 节点管理：发现与采集解耦

Status: implemented

## Completion evidence

- 租约：同步 `node_mgmt_sync`、采集 `node_mgmt_collect` 可同时持有。
- 采集入口不再等待成功同步；执行前拉节点管理、认领已有 host、刷新系统采集任务名单后走 `exec_task`。
- 发现路径不再创建/更新/退役区域采集任务。
- 验证：`uv run pytest apps/cmdb/tests/test_node_mgmt_sync_execution.py apps/cmdb/tests/test_node_mgmt_sync_collection.py apps/cmdb/tests/test_node_mgmt_sync_models.py apps/cmdb/tests/test_node_mgmt_sync_empty_source.py apps/cmdb/tests/test_node_mgmt_sync_host_mapping.py apps/cmdb/tests/test_node_mgmt_sync_persistence.py apps/cmdb/tests/test_node_mgmt_sync_resilience.py apps/cmdb/tests/test_node_mgmt_sync_display.py --no-cov` → 124 passed。

## Problem Statement

CMDB「节点管理同步」把发现和采集绑成一段管道：同步写完 host 后把实例名单拷进隐藏的区域采集任务，采集还要等同版本同步成功，两段还共用一把运行租约。同步会因为采集仍在 submitted 而丢拍；采集名单是同步留下的快照，不是本轮自己看到的节点管理源。运维看到的是采集失败或像没跑起来，即使库存同步本身是健康的。

## Solution

发现只负责把 sidecar 镜像成 host 库存。采集每次执行前自己问节点管理「现在有哪些 sidecar」，用共用身份认领**已有** host，把命中的实例快照写进该区域系统采集任务的目标名单，再走现有采集任务执行。两段各持一把租约，采集不再等待上一次同步成功。采集核心（任务执行、插件、凭据、下发）不改。尚未入库的节点本轮不采，留给发现管道。

## User Stories

1. As a CMDB 管理员, I want 节点管理同步在采集进行中仍能按时写库存, so that 发现不会被采集占用的锁挡住。
2. As a CMDB 管理员, I want 自动采集不依赖「上一次同步是否成功」, so that 打开采集后不必空等一个同步周期，也不会因为一次空源同步把采集闸死。
3. As a CMDB 管理员, I want 每次自动采集都按当前节点管理 sidecar 刷新区域采集任务的目标名单, so that 新出现的已入库主机能进采集，源侧已消失的 sidecar 会从名单拿掉。
4. As a 平台用户, I want 区域系统采集任务仍然按原来的采集任务执行, so that 采集结果回写、周期和接入点行为与手工主机采集任务一致。
5. As a CMDB 管理员, I want 节点管理里已有、但 CMDB 里还没有 host 的 IP 本轮不进采集目标, so that 采集不会在库存外建主机，也不会改采集任务对实例身份的要求。

## Implementation Decisions

### 两段职责

- **发现 / 同步**：从节点管理拉非容器 sidecar，按共用身份写入或更新 host，源侧消失只清 `node_id`、不删实例。不再创建或更新区域系统采集任务，不再把实例名单写进采集任务。
- **采集**：独立周期与开关。每次执行前拉同一份节点管理源（不读同步 run、不等待同步终态），按云区域保证隐藏系统采集任务壳存在，刷新目标名单后调用现有采集任务执行。
- 配置上的自动同步 / 自动采集开关保持独立；采集打开不要求本拍同步成功。

### 租约

- 运行租约按阶段拆开：同步与采集可同时各有一条活跃 run。
- 同步 submitted/running 不得挡住采集抢自己的租约，反之亦然。
- 采集父 run 在等待子任务结果期间只占采集租约。超时、恢复、心跳仍按现有 run 模型，只是 scope 不再共用。
- 去掉「等待同步」这种采集前置状态；不再用「同配置版本最近一次权威同步」作为采集闸门。

### 执行前刷新目标名单

- 采集核心继续把任务上的实例列表当作 CMDB 主机快照（须带稳定实例身份，不能只写 IP 或节点管理原始节点）。缺身份的目标现有采集逻辑会跳过，本变更不放宽该契约。
- 刷新步骤：按云区域取出本轮 sidecar → 只用共用认领规则查找已有 host（`node_id`，否则 ip+云区域）→ 命中的实例快照写入该区域系统采集任务；未命中的 sidecar 本轮不写入、不在采集路径新建 host。
- 本轮源侧已没有的 sidecar，从该区域任务名单中去掉。某云区域在本轮节点管理结果里已不存在：由采集编排退役该区域系统采集任务（与今日发现侧退役语义一致，改由采集执行）。不要为「空名单」再造必须先同步的闸门。
- 区域还没有系统采集任务时，由采集编排创建壳（隐藏、系统编码、接入点、周期、占位凭据与现网系统任务一致）。发现路径不再承担建壳。
- 刷新名单之后调用现有采集任务执行入口；父 run 只绑定该次执行响应给出的执行 ID，不使用调用前内存里可能过期的任务执行字段。

### 明确不改

- 不改采集任务执行入口的业务语义、host 采集插件、作业/协议下发、用户可见的手工采集任务。
- 采集刷新路径不调用发现的 host 持久化（不建、不改库存字段、不回填节点关联）。库存仍只由发现与节点推送写入。
- 不在本变更把系统采集从空 SSH/作业通道改成 sidecar 直采；那是采集通道问题，与名单解耦分开。

## Testing Decisions

只测编排对外行为：两段能否并行持锁、采集是否不再等同步、执行前名单是否按本轮节点管理源 + 已有 host 刷新、未入库 sidecar 是否不进名单、现有执行入口是否仍被调用且绑定响应中的执行 ID。不测采集插件内部，不把刷新名单的私有拆分方式锁进断言。

优先沿用节点管理同步相关测试缝：服务级同步/采集入口、租约抢占、区域系统采集任务、空源与名单刷新。补采集侧的节点管理列表与 host 认领替身，避免再要求一次成功同步才能采集。

必测：

- 采集 submitted 占用采集租约时，同步仍能获得同步租约并完成；同步活跃时采集仍能获得采集租约。
- 从未有过成功同步、或最近一次同步是空源阻塞时，只要自动采集打开且节点管理能列出 sidecar，采集仍执行刷新并尝试下发。
- 节点管理列出的 sidecar 在库存中已有 host：执行前该区域系统任务名单包含该实例身份；源侧本轮没有的 IP 从名单消失。
- 节点管理列出的 sidecar 在库存中不存在：名单不含该 IP，且采集路径没有新建 host。
- 刷新后调用采集执行入口；父 run 绑定响应里的执行 ID，即使任务行上仍留着更早的执行字段。
- 发现成功不再作为采集前置条件；发现路径不再把实例列表写进系统采集任务（可用现有同步成功用例断言不再触碰采集任务名单，或采集任务在仅跑发现后保持刷新前状态）。

## Out of Scope

- 把系统采集改成经 sidecar 取数，或为节点管理同步补真实 SSH 凭据。
- 采集刷新时 upsert host（方案 2）。
- 仍由发现维护采集名单、只拆租约（方案 3）。
- 采集子因在父 run 上的更细展示、heartbeat 续 deadline、空源发现漏清 `node_id` 的补齐（发现身份规格已有要求，本变更不顺手扩 scope）。
- 用户手工创建的采集任务目标编辑。

## Further Notes

共用认领规则与「源消失只清 `node_id`、不删 host」仍以节点管理同步共用身份变更为准。本变更只改变「谁在何时填写系统采集任务名单」，不改变 host 是谁。

同一 sidecar 在发现尚未写入的窗口内会漏采一拍，下一拍采集再认领；这是方案 1 的明确取舍，不要用采集路径补写库存来消掉。

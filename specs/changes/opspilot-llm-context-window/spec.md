# OpsPilot LLM 模型上下文窗口

Status: in-progress

## Problem Statement

管理员为智能体、Wiki 问答和知识构建选用的 LLM 模型，上下文容量从数万到百万 token 不等，但平台没有在模型上标注真实窗口。请求打包仍使用与模型无关的硬顶（Wiki 知识注入约 8k、构建单次约 16k、Agent compaction 约 80k、单条消息 4k）。结果是：大窗口模型用不上容量；小窗口模型可能按更大预算打包后被网关拒绝。技能「对话窗口条数」默认仍是 10，不能单独解决 token 超窗。

## Solution

在 LLM 模型上增加真实上下文窗口（input+output 合计，单位 token）。新模型和存量一律默认 200K。表单用整数加单位 K/M 填写，后端只存 token。每次使用该模型的调用不得超过窗口；对话/Agent、Wiki 问答注入、Wiki 构建分块按窗口比例派生工作预算，不打满窗口。历史过长走 compaction；系统提示、本轮问题和工具定义已经放不下时明确失败。

## User Stories

1. As a 模型管理员, I want 在 LLM 模型上配置上下文窗口（默认 200K，单位 K 或 M）, so that 各技能和 Wiki 都按该模型的真实容量打包，而不必逐个技能改预算。
2. As a 模型管理员, I want 把 32k 模型改成 32K、把 1M 模型改成 1M, so that 小窗口不会被按 200K 打爆，大窗口可以注入更多知识、减少构建分块次数。
3. As a 智能体使用者, I want 长对话在接近工作预算时自动压缩旧轮次、单条过长内容被截到预算内, so that 对话能继续且不静默丢掉正在问的这一句。
4. As a Wiki 使用者, I want 问答注入的知识和构建时的资料分块随所选模型窗口放大（约 15% 输入工作预算）, so that 200K 档模型明显比今天的 8k/10k 用得更多，又不会把整本资料一次性塞进 prompt。
5. As a 运维人员, I want 窗口填错（小于 8K 或大于 2M）时保存失败、本轮核心内容已经超窗时看到明确错误, so that 配置错误和异常输入可被发现，而不是截断当前问题或删掉系统提示。
6. As a 智能体使用者, I want 在对话输入区看到下一次发给模型的包占输入工作预算的比例（点开有分色：系统 / 工具 / 技能包 / Wiki / 摘要 / 对话）, so that 我知道还剩多少上下文、压缩是否已经发生，而不是把会话 billed token 或界面全文当成额度。

## Implementation Decisions

- 字段语义是模型真实上下文窗口，不是产品愿用额度。挂在 LLM 模型上，与「是否支持多模态」同类，一次配置全部智能体与 Wiki 引用继承。Embed / Rerank / OCR 模型不加此字段。
- 存储与 API 只使用正整数 token。默认 200_000。合法范围换算后为 8_000～2_000_000（含）。存量记录 migration 一律 backfill 为 200_000，字段必填，不允许空值回落到今天的 8k/16k/80k。
- 管理表单仅 LLM 模型展示：整数输入 + 单位二选一（K 或 M）。K × 1_000，M × 1_000_000（十进制，不是 1024）。默认展示 200 + K。不允许小数；1.5M 填 1500 + K。单位换算只发生在表单，提交给后端的是 token。
- 所有走该 LLM 模型的调用受窗口硬顶（含技能对话、Agent 图、技能渠道、工作流 Agent 节点、Wiki 问答、Wiki 构建及构建内短调用）。按比例打包只做三件事：对话/Agent（含工作流与渠道）、Wiki 问答知识注入、Wiki 构建资料分块。标题/分类/JSON 抽取等短调用只保证不超窗，不刻意填满。
- 工作预算从窗口 W 派生，不打满，也不把今日 8k 知识 / 16k 构建单次 / 80k compaction 继续当作与窗口无关的独立上限（含环境变量不得再 `min()` 压回这些旧顶）。对照 Cursor：其产品不预切比例、约 90% 窗口才自动压缩；本变更刻意更早压缩，并为 Wiki 注入保留硬顶。
- 共用公式：
  - 安全余量 = `max(256, 5% × W)`
  - 输出预留 = `min(场景默认 max_output, 10% × W)`；Wiki 问答场景默认仍可由现有输出环境变量提供，构建直出/map 输出默认保持今天的场景值，只受 10% × W 封顶，不为「知识更大」把单次输出抬到数万
  - 输入工作预算 = `W − 输出预留 − 安全余量`
  - Agent compaction 触发 = 输入工作预算的 75%（200K 时约 70% 窗口）
  - Wiki 问答注入知识 = 输入工作预算的 15%
  - Wiki 构建单次资料分块 = 输入工作预算的 15%
  - 单条消息截断 = 输入工作预算的 20%
- 技能「对话窗口条数」仍先生效，默认仍是 10，再对留下的消息做 token 裁剪与 compaction。要用大窗口装更多历史，须在技能里把条数调大。关闭历史仍为 0 条。
- 历史过长：先轻量裁剪（单条上限）再 compaction，保留最近轮次原文；不采用 ChatGPT 网页那种静默丢掉旧轮次、界面仍显示全文的行为。
- 裁无可裁：系统提示 + 本轮用户问题 + 工具定义已大于输入工作预算时，明确失败，不截断当前问题，不删除系统提示或工具定义。Wiki 构建对资料仍用分块/map-reduce，不得为了塞进单次调用而丢弃未处理原文。
- v1 token 计数各路径沿用现有计数器（Wiki 粗估、Agent 侧既有编码），靠 5% 安全余量扛误差；本次不统一 tokenizer、不按供应商切换计数器。
- Wiki 资料级软审计总额、问答调用次数上限保持现有运维开关；它们约束「一篇资料/一次问答一共花多少」，不替代窗口派生的单次打包预算。调用方可传入更紧的知识 token 预算，但不得突破该模型派生值。
- 派生预算应由一处纯函数（窗口 + 场景输出默认）算出，对话、Wiki 问答、Wiki 构建都消费同一结果，避免三条链路各写一套比例。

## Testing Decisions

- 好测试只断言对外契约：保存/迁移后的 token 值与范围拒绝；给定 W 与场景输出时的派生数字；问答注入与构建分块实际遵守派生预算；Agent 请求带上派生的 compaction / 单条上限；条数裁剪仍先发生；核心超窗失败且不截断本轮问题。不绑定私有 helper 调用次数或文件内常量名。
- 最高接缝优先：窗口派生纯函数（W=200_000 与 W=8_000 的整表数字）；LLM 模型写入与序列化校验（默认、backfill、越界拒绝）；Wiki 问答 `build_context` 在未另指定更紧预算时使用派生知识额度，指定更紧预算时取更小值且不超过派生值；Wiki 构建预算在超单次派生窗口时分块或失败，不再按 16k/10k 旧顶；构造 Agent 图请求时 compaction 阈值与单条上限来自该模型；技能渠道/对话仍按 `conversation_window_size` 先截条数。
- 既有先验：模型能力字段与序列化（多模态同类）、Wiki 上下文 token 预算与资料构建预算、消息裁剪与 runtime 策略、技能渠道对话门禁。优先扩展这些模块级测试，不先上浏览器 E2E。表单 K/M 换算可用组件或纯函数单测锁住「200+K → 200000、2+M → 2000000、提交越界被拒」。
- 用量环：拟合后的包发出 `llm_context_usage`（有界整数/bool/segment id，不含正文）；无输入工作预算则不发；前端 parse 丢掉未知字段。打开已有会话时按当前技能配置与窗口条数现算一包用量（不做 compaction LLM、不落库）；无历史或关闭历史时不恢复快照。无快照时草稿会话仍显示空环。

## Out of Scope

- 统一全链路 tokenizer，或按供应商选择精确计数器。
- 把技能对话窗口条数默认从 10 调大，或废除条数配置。
- 把工作预算改成打满窗口，或把 compaction 推迟到约 90% 窗口（Cursor 自动压缩点）。
- 按窗口放大 Wiki 单次生成页的输出上限（仍用场景默认 + 10% W 封顶）。
- 为 Embed / Rerank / OCR 配置上下文窗口。
- 请求级覆盖模型窗口；按模型名猜测窗口并自动写入。
- 接入供应商服务端 compaction（Responses / Anthropic compact 等）。
- 按模型名猜测窗口；空值回落旧 8k/16k/80k 双轨。

## Further Notes

- 对齐来源：grill-me（2026-08-26）。关键取舍：真实窗口而非愿用额度；比例派生而非打满；存量 backfill 200K；条数默认仍 10；单条 20%；短调用只硬顶；裁无可裁明确失败；表单整数+K/M；对照 Cursor 后仍维持更早的 compaction 与 Wiki 15% 硬顶。
- 用量环：事件名 `llm_context_usage`，payload 只有有界整数/bool/白名单 segment id；分母是输入工作预算，分子是闸门拟合后的下一次实发包。不落库。打开 Web/平台已有会话时按窗口条数现算用量，不能从 0% 起跳；技能关闭聊天历史时不展示圆环（每轮独立发包）。草稿/新会话无快照时仍显示空环，点开说明发一条后才有分类。目录按模型名猜测填写提示仍不做。
- **实现必须另起 git worktree**（独立分支与工作目录），不要在当前已有无关改动的工作区上直接开发本变更。spec 本身写在主工作区 `specs/changes/opspilot-llm-context-window/`。
- 200K 是 Claude 档默认，不是按厂商探测。小窗口模型上线后须由管理员改准，否则按 200K 打包会在网关失败。

## 2. M1：追加留言接口必须说明的契约

### 2.1 业务效果

请求只在指定工单中追加一条备注，绝不能附带挂起、恢复、审批、转派、终止或重新打开工单。成功后工单页面应能看到正文、时间和真实认证作者。

告警側会发送如下内容：

| 告警规则勾选项 | 覆盖场景 | 示例内容 |
|---|---|---|
| 分派 | 自动分派、人工分派、转派 | 告警分派给张三；或由张三转派给李四 |
| 认领 | 处理人认领 | 张三认领告警，告警进入处理中 |
| 恢复 | 指标自动恢复、人工解决 | “监控指标已恢复”与“张三人工标记已处理”分别表述，不混淆 |
| 关闭 | 人工关闭、超时自动关闭、ITSM 回写导致的告警关闭 | 告警已关闭，注明原因及来源 |

只有事件发生时已经成功关联工单且规则勾选该事件才留言；建单失败、待确认、仍在建单中或未勾选时跳过，不补发建单前历史操作。

**请特别确认已办结／已终止工单能否追加备注。** “工单先关闭、告警后恢复”以及“工单关闭触发告警关闭”都会遇到这一情况。业务期望允许追加备注而不重开工单；若 ITSM 无法支持，请明确限制及错误码，不能把静默丢弃记为成功。这会直接影响留言需求的覆盖范围。

### 2.2 建议请求信息（不是已存在的接口格式）

```json
{
  "ticket_id": "<实际工单ID，字符串>",
  "source": "bklite-alerts",
  "request_id": "<该条告警生命周期操作的稳定唯一标识>",
  "content": "【告警认领】告警 ALERT-DEMO-001 于 2026-09-23 10:05:00+08:00 被测试用户甲认领，状态：待响应 → 处理中。"
}
```

- 路径或请求体中携带 ticket_id 均可，以 ITSM 发布的正式契约为准。
- 最小支持纯文本、中文、多行；提供最大字符／字节数、转义规则，超限明确返回参数错误，不能静默截断或执行 HTML。
- 实际 API 调用人来自认证身份。告警操作者是由告警系统核实后写入正文的业务信息，不能通过请求中的 `operator` 覆盖 ITSM 日志的真实认证作者。
- 同一个事件的重试使用同一 request_id；同一告警第二次分派是新事件，使用新的 request_id，不能因事件类型相同被去重。

### 2.3 去重、响应和查询

请在契约中明确：

1. 在经过授权校验的组织／调用方及工单范围内，同一 request_id 并发或重复提交同一内容只产生一条评论，并返回相同评论 ID。重复请求也不能跳过权限校验。
2. 同一 request_id 携带不同工单或不同内容时如何处理；推荐在其定义的唯一范围内返回明确冲突，不静默覆盖历史评论。
3. 返回真实评论 ID（字符串）、所属工单 ID、创建时间以及是否属于重复请求；成功响应采用现有 result/code/message/data 风格即可。
4. 明确去重记录保留时间。告警侧自动／人工重试不能超出该保证范围；不要仅承诺短暂的进程内去重。
5. 如何核验实际写入：现有详情／日志能返回评论 ID、正文、时间和作者即可；若不能，请提供只读评论查询。无需同时开发多套查询入口。
6. 缺少／无效认证、越权、工单不存在、已关闭不允许留言、正文超限、重复键冲突和内部异常分别怎样返回。

如果暂时无法实现去重，请明确说明。告警侧会把留言响应丢失标为“结果待确认”，不能承诺自动重试不重复；这属于留言可靠性的限制，不能把非幂等评论接口宣传为可安全重试。

### 2.4 M1 验收材料

- 一条普通留言成功，页面可见，工单状态、处理人和当前节点未改变。
- 同一请求重复及并发发送，只存在一条评论。
- 同一告警发生两次真实分派，两条不同事件各产生一条评论。
- 服务端成功写入但客户端未收到响应，重试仍返回原评论。
- 已关闭工单留言的成功证据，或明确的不支持说明及拒绝响应。
- 无关用户和另一个团队不能留言或通过去重响应获知评论内容。
- 请求、响应、权限及限制文档；全部通过现有 OpenAPI 网关提供，不增加绕过网关的端口。

## 3. E1：创建幂等增强建议

文档已明确 `ticket_create/` 不幂等；这不是遗漏说明。本项是请求增强，未交付时告警侧仍可按“结果待确认＋人工核查”接入。

建议支持一个由告警侧提供的稳定创建请求标识，具体字段名由 ITSM 定义：

- 同一授权范围和同一请求标识的并发／重复调用最多创建一个工单，并返回原工单 ID，不依赖标题搜索去重。
- 返回成功时明确工单已持久化；若创建异步进行，明确返回“处理中”并提供按请求标识查询结果的办法，不把受理当作创建成功。
- 查询可区分处理中、已成功、明确失败。仅“没有查到”不能代替“原请求不会再创建”的保证。
- 明确相同标识、不同请求内容的冲突语义，以及校验失败未创建时修正表单后应沿用还是更换标识。
- 明确去重有效期、权限范围和凭据轮换后同一业务请求如何保持唯一性；不能以原始 token 值作为业务唯一身份。

**原子创建去重是关键；仅增加一个可搜索的告警 ID 字段，不等于实现幂等。** 若 ITSM 无法保证原子去重，请回复实际保证范围，告警侧继续采用保守处理，不要求为了本期重做工单引擎。

## 5. 告警侧到底缺哪些数据

**告警基本字段已有，缺的是可复现的样例、真实环境标识和每次生命周期操作的上下文。** 增加留言后，仅有一条 Alert 的最终快照不足以证明整条留言链路。

| 数据 | 当前情况 | 谁准备／AI 能否构造 |
|---|---|---|
| 标题、内容、对象、指标、标签、来源 | Alert 模型和动作 payload 已有 | AI 可生成虚构但合理的测试值 |
| 告警级别 | 已有 `level`；实际代码取决于环境 Level 字典 | 先读取真实级别字典，AI 按合法代码组合；不可凭中文名称猜代码 |
| 团队、用户、接入源、策略／动作规则 ID | 环境真实配置，不是任意字符串 | 环境提供或经正常接口创建；AI 用参数引用，不凭空假装存在 |
| 创建、分派、认领、转派、恢复、关闭的操作序列 | 有现有状态与操作入口；留言所需事件快照／逐次唯一性尚需告警侧实现 | AI 可生成场景；集成测试必须调用实际入口产生事件，不直接改 status 冒充链路通过 |
| 每次操作的 ID、时间、执行人、旧／新处理人、旧／新状态、原因、自动／人工来源 | 当前 `build_match_payload` 未完整提供；Alert.operator 是当前处理人，不是本次操作者 | 告警侧在操作发生时持久化；AI 可生成测试夹具，不能代替真实操作事件捕获 |
| 监控源恢复事件 | Event 模型已有 action、external_id、source、push_source_id、team 等信息 | AI 可生成同来源、同团队、同恢复关联键的触发／恢复配对数据 |
| ITSM 工作流字段、工单 ID、评论 ID、真实响应 | 来自 ITSM | 联调必须由 ITSM 提供／返回；AI 只能制作明确标注的 mock |

当前动作绑定已有 `title/content/level/resource_*`、`labels.*`、`enrichment.*` 及代表事件 `event.*` 等字段；时间、团队、当前处理人等虽然在模型中存在，也不能不检查绑定层就承诺任意路径可用。新增所需上下文应显式加入 ITSM 执行快照。

`Event.event_id` 标识源事件，不是“用户第二次转派”的事件 ID。为留言新增的生命周期操作 ID 必须在实际操作时生成并持久化；同一事件重试不能重新生成。这里只明确需要的数据，不要求新增通用事件平台。

## 6. AI 应覆盖的场景

| 场景 | 应准备的数据或动作 | 期望 |
|---|---|---|
| A01 正常建单 | CPU、内存、磁盘、服务不可用等告警，合法字段和规则 | 每条 Alert 一张工单，内容映射正确 |
| A02 未命中／多规则命中 | 一条不匹配、一条同时匹配两条 ITSM 规则 | 未命中不建；多命中按归属规则只建一次 |
| A03 分派认领留言 | 工单成功后分派、认领，勾选对应事件 | 每次实际操作一条备注，不流转工单 |
| A04 多次转派与重复投递 | 认领、转派、再认领、再转派；重放其中一次事件 | 不同操作分别留言；同事件重复投递不重复留言 |
| A05 自动恢复 | 触发与恢复来自同接入源、push_source、external_id 和团队 | 告警自动恢复，已有工单追加恢复备注但不关闭 |
| A06 人工解决／人工关闭／超时关闭 | 分别走对应合法入口和状态 | 文案区分原因，不把人工解决写成指标恢复 |
| A07 未勾选／无成功工单 | 关闭留言开关、创建失败或仍在建单时发生操作 | 不留言，不补发建单前历史事件 |
| A08 工单先关闭 | ITSM 真正关闭测试工单，再触发告警恢复／关闭 | 按 M1 已关闭工单契约验证留言，不偷偷重开工单 |
| A09 可选关闭回写 | 开关开／关 × 三种活跃及各非活跃告警状态 | 仅开关开且仍活跃时关闭告警，其余只更新展示 |
| A10 明确失败后补建 | 必填字段缺失，修正规则后重试；重复同一个补建请求 | 原失败可查，补建成功一次，请求重放不额外创建 |
| A11 超时与响应丢失 | HTTP 测试替身或故障注入，分别模拟创建／评论实际成功但客户端超时 | 按实际幂等保证去重，未保证时进入待确认；不能仅造一条 Alert 就声称覆盖 |
| A12 双团队权限 | TEAM_A／TEAM_B 及无关用户，跨团队读取／建单／留言／补录尝试 | 不越权；环境实体真实存在 |
| A13 会话与并发 | 观察期自愈、观察期转正；自动／手动并发触发 | 自愈不建，转正一次，并发一主工单 |
| A14 文本与空值 | 中文、多行、引号、合法 0/false、必填缺失、字段超限 | 正确保留类型，缺失／超限明确拒绝，不泄露敏感数据 |

模拟 ITSM 关闭、任务重投或网络故障必须由对应测试驱动器执行，不能用改写告警 fixture 的字段冒充远端工单状态变化或真实消息重复。

## 8. 双方交付与范围说明

ITSM 开发请交付：M1 正式接口及其验证结果；E1 是否支持和实际保证范围；D1～D4 的真实字段说明、响应样例、页面模板及测试环境准备结果。无需再次提供已经明确的八接口清单或重做鉴权。

告警侧负责：字段映射、操作快照与稳定事件 ID、异步投递和去重、失败记录／通知、周期查询、可选关闭回写、页面展示与手动核查，以及测试夹具和驱动。AI 生成告警数据不能替代这些代码能力，也不能替代真实 ITSM 契约。

[基础功能方案](spec.md)保留不含留言时的主链路设计。本文作为最新追加需求，覆盖其中“本期不做留言”的范围限制；待 M1 契约明确后补齐告警侧留言实现细节及验收，不将留言功能写成已经支持。追加留言不要求为了所有生命周期事件重做告警主状态机。

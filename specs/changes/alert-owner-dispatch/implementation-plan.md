# 实施方案：告警责任人上报、丰富与兜底分派

依据：[spec.md](spec.md)。状态：M1–M6 已落地（2026-10-13）。

## 总体策略

- 按数据流顺序做六个里程碑：上报 → 聚合 → 丰富 → 分派 → 前端 → 完整流程。
- 每个里程碑先写失败测试再补实现，测试只走现有对外入口（接入、丰富引擎、聚合构建、分派执行、序列化保存）。
- 只改本任务范围。不回填存量告警，不改存量告警源配置，不做应用系统多跳反查。

## 测试边界

| 边界 | 入口 | 断言 |
|---|---|---|
| 事件接入 | 告警源 `create_events` | `Event.assignee` 归一化结果 |
| 丰富 | `EnrichmentEngine.enrich_batch` | `assignee` 是否被替换、`enrichment_meta.owner_source` |
| 聚合 | `AlertBuilder` 创建与更新 | `Alert.owners` 并集与上限 |
| 分派保存 | 分派策略序列化器 | 开关、兜底必填、升级层拒绝 |
| 分派执行 | `execute_auto_assignment_for_alerts` | 实际通知对象是责任人还是兜底 |
| 完整流程 | 接入 → 丰富 → 聚合 → 分派 | 三条路径：丰富替换、保留上报、走兜底 |

## M1 事件上报责任人

1. `common/source_adapter/constants.py`：默认映射和字段说明增加 `assignee`（用户名数组，可选）。
2. 接入映射后归一化：只保留非空字符串，去空白、去重，最多 20 个；非数组或非法元素丢弃，不拒绝整条事件。未映射的源保持空列表。
3. 测试：`tests/test_source_adapter.py` 补上报、非法元素、超限、未映射四条。

验收：映射了 `assignee` 的新源写入归一化列表；旧源配置不含该键时行为不变。

## M2 告警责任人聚合

1. `Alert.owners`：JSONField，默认空列表，迁移 `0036_alert_owners`。
2. `AlertBuilder` 创建和更新：取 `action=created` 的成员事件 `assignee` 有序并集，最多 50 个，口径与 `monitor_objects` 相同。
3. 告警序列化器返回 `owners`（只读）。列表过滤支持责任人精确成员，不用 JSON 子串包含。
4. 测试：创建、更新并集、上限、精确过滤。

验收：一条告警的责任人等于其创建事件责任人的并集；列表按责任人过滤不误伤用户名前缀。

## M3 丰富责任人映射

1. `provider_config.owner_fields`：属性 ID 列表，最多 5 个、不重复、非空字符串。序列化器校验；不配置则该规则不写责任人。
2. 引擎在投影之后、同一批实例上取值：
   - 按 `on_multiple` 选实例（`first` 取首条，`merge`/`list` 取全部）。
   - 合并所选用户字段，只接受整数用户 ID（排除布尔值），去重。
   - 整批事件一次查询 `system_mgmt.User`，丢弃不存在或已禁用用户，每条事件最多 20 个用户名。
3. 写入（丰富优先）：收集到的用户名非空则替换 `assignee`；为空、未命中、未查到、查询失败或超时时保留上报值。
4. `enrichment_meta.owner_source`：`enrichment`（附贡献规则 ID，最多 20 个）、`reported` 或 `none`。不记录用户名单。
5. 内置预设不默认开启；前端新增表单默认填 `operator`（M5）。
6. 测试：`tests/test_enrichment_engine.py` 覆盖 spec 丰富条目（合并字段、替换、保留、失败保留、多规则合并、无配置不变）。用户查询打桩，不连真实 CMDB。

验收：丰富到就替换上报值；任何查不到或失败都保留上报值，且不把该事件记成丰富失败。

## M4 分派优先通知告警责任人

1. `notification_target.prefer_alert_owner` 默认 `false`。缺失该字段时分派行为不变。
2. 开启后，已选用户或组织变为兜底且必须非空。升级层携带该字段时保存拒绝。
3. `AlertAssignmentOperator` 对开启该开关的策略按告警逐条解析：
   - `owners` 中存在且未禁用的用户非空：只分派给他们。
   - 否则解析页面选择的兜底用户或组织。
   - 兜底也为空：保持未分派，进入现有全局未分派通知。
4. 操作日志写命中类型（责任人 / 兜底）和人数，不写用户名单。INFO 按策略汇总两类次数。
5. 测试：复用自动分派测试入口，覆盖开关关闭回归、只通知责任人、空责任人走兜底、禁用责任人走兜底、同批不同责任人、兜底为空、升级层拒绝。

验收：有责任人的告警不通知兜底人员；没有责任人的告警以页面选择为准。

## M5 前端

1. 丰富规则弹窗（CMDB）：「责任人映射」多选，新增默认 `operator`，写入目标只读为「告警责任人」，提示丰富优先。
2. 分派策略弹窗：「优先通知告警责任人」开关。开启后用户/组织标签改为兜底，并显示说明。
3. 告警列表与详情展示责任人；列表筛选走 M2 的精确成员过滤。
4. 通知模板变量增加 `owners`。
5. 前端测试覆盖两个表单的提交载荷。

验收：保存的载荷与 M3、M4 的后端契约一致；关开关的旧策略编辑后不带 `prefer_alert_owner: true`。

## M6 完整流程

一条集成测试走完三条路径，入口是告警源接入，出口是自动分派结果：

1. 事件上报了用户，CMDB 丰富到另一组用户 → 告警责任人和通知对象都是丰富结果。
2. 事件上报了用户，CMDB 没有该字段 → 告警责任人和通知对象都是上报用户。
3. 事件没有用户，丰富也没有 → 通知对象是页面选择的兜底用户，告警责任人为空。

另外跑 M1–M5 触碰的现有测试，确认旧的丰富和分派行为没有回退。

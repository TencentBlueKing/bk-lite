# 智能体飞书长连接

Status: implemented

## Problem Statement

智能体发布里的飞书渠道只有 URL 回调：要有公网地址，并填写 Verification Token，配置了加密还要 Encrypt Key。部署在内网、没有固定回调地址时，飞书消息到不了智能体。飞书已经提供官方长连接，由我们主动连出去，不需要回调地址，但发布渠道还不能选这种接法。

## Solution

飞书发布渠道增加和企微机器人一样的连接方式。选长连接并启用后，由一个常驻进程用官方 SDK 连上飞书，接收单聊文字和群里单独 @ 了该机器人的文字。先回复一条「正在处理」，再更新这一条，直到换成最终答案。生成的文件在答案定稿后另发一条文件消息。现有 URL 回调保持不变。同一个飞书应用在整个环境里只能被一条飞书渠道占用。

## User Stories

1. As a 运维人员, I want 给飞书渠道选择长连接并只填写 App ID 和 App Secret, so that 没有公网回调地址也能接入智能体。
2. As a 飞书用户, I want 发出文字后马上看到「正在处理」，随后同一条消息变成回答, so that 我知道机器人已经接上，而不是一直空白或收到第二条文字。
3. As a 飞书用户, I want 在同一个会话里接着发下一句时，上一轮停掉, so that 机器人按新消息回复，而不是两条回答抢着刷。
4. As a 飞书群用户, I want 只有单独 @ 了这个机器人时才得到回复, so that 普通聊天和只 @所有人 不会把机器人叫起来。
5. As a 飞书用户, I want 发送图片、文件或语音时得到「当前仅支持文本消息」, so that 我知道这条消息没有进入智能体。
6. As a 飞书用户, I want 处理失败、超时或文件发不出去时看到明确结果, so that 答案不会一直停在「正在处理」，文件失败也不会改掉已经定稿的答案。
7. As a 运维人员, I want 保存渠道时就被拒绝重复的 App ID, so that 两个智能体不会去抢同一个飞书应用。
8. As a 运维人员, I want 多个 Server 副本同时运行时只有一个进程连着这些应用, so that 连接不会互相踢掉。

## Implementation Decisions

- 渠道类型仍是飞书发布渠道，不新增渠道类型，不新增表。连接方式与企微机器人相同：长连接与 URL 回调二选一，缺省仍是 URL 回调。长连接只保存 App ID 和 App Secret。URL 回调继续保存 Verification Token 和可选的 Encrypt Key。不迁移已有回调数据。
- 只连接已启用、选择了长连接、且 App ID 和 App Secret 都有值的渠道。停用、删除或更换凭据时断开对应连接，凭据变了再重连。
- 新建或修改任意飞书渠道时，App ID 已被另一条飞书渠道保存则拒绝保存，并告知该 App ID 已被发布，重复发布会导致系统混乱。对方是长连接还是 URL 回调、是否启用，都算占用。修改本渠道且 App ID 不变时允许保存。
- 常驻进程在服务启动完成之后由进程守护拉起，不参与启动门禁。连不上飞书只重试。一个进程维护全部飞书长连接。多副本用 Redis 锁选出唯一持有者，只有持锁进程建立连接并续期。
- 连接、心跳和断线重连只用飞书官方 Python SDK 的长连接客户端，不自己写 WebSocket。只订阅接收消息事件。回调必须马上返回，智能体在后台执行，避免飞书因超时重推。同一条消息已经接过就不再开一轮。
- 只做飞书国内企业自建应用。回复、更新消息、上传文件和发送文件都走该 SDK 的开放接口，不走长连接传字节。
- 单聊的每条文字都处理。群聊只有 mentions 里出现这个机器人本身才处理。用官方机器人信息里的 open_id 对齐 mention，再从正文删掉该项的占位符 key，不按显示名切割。其他人的 @ 保留。只 @所有人、没有单独 @ 机器人的群消息忽略：不回复、不跑智能体、不打断当前轮。
- 图片、文件、语音等非文字只回复「当前仅支持文本消息」并结束。不先发「正在处理」，不跑智能体，不写入会话历史。
- 一轮以飞书会话标识为准。同一会话同时只有一轮。又收到应处理的文字时，立刻停止上一轮生成，包括正在进行的模型调用。上一条飞书消息停在已经显示的内容，还没有正文就停在「正在处理」，不再修改它。新的一轮只包含这句新消息。半截回答写入该发言人的会话历史。还没有正文时，历史里只有上一条用户消息，「正在处理」不写入历史。
- 打断按整个会话共用。会话历史和记忆按发言人分开，群里一个人的上下文不包含其他人的话。单聊的历史就是这个人自己的。
- 收到应处理的文字后立即回复「正在处理」。之后大约每 2 秒用当时已生成的全文更新同一条消息。第一次出现正文时不再包含「正在处理」。结束时把这条消息改成最终答案，不另发第二条文字。更新失败时，把当前应显示的内容补发成一条新消息，且只补发一次；之后这一轮改补发的那条。
- 流式内容只有最终回答正文，不包含思考过程和工具调用。回复语言跟着用户这一句：含中文就用中文，否则用这句话本身的语言。
- 10 分钟从发出「正在处理」起算，不是从用户发消息起算。提前 30 秒结束。已有正文就用正文，没有正文则改为「处理超时，请再发一次」。超时和失败文案写入助手历史。结束后不再补发。
- 中途失败时，把这条消息改成智能体流里已经展示给用户的失败说明。流里没有这句时，用「处理失败，请稍后重试」。异常对象原文不写入飞书。失败的这一轮不发文件。
- 没有可展示正文时，把这条消息改成「处理完成，但未产生可展示内容」。
- 答案定稿后，本轮生成的文件用官方接口上传，再另发一条文件消息。上传或发送失败时，答案气泡保持不变，另发一条「文件发送失败，请稍后重试」。
- 断开期间的用户消息不补收、不补回。重连后只处理新消息。
- URL 回调的校验、解密和回复保持不变。同一渠道同一时刻只按当前连接方式工作。

## Testing Decisions

- 测外部行为：给定渠道配置和一条飞书入站事件，断言回复或更新的消息、是否另发了文件或失败提示、会话历史，以及是否执行了智能体。不连接真实飞书，不断言 SDK 内部的心跳或线程。
- 长连接客户端用假的官方 SDK 客户端验证：凭据不入日志、文本先「正在处理」再被全文覆盖、更新失败后只补发一次、非文本固定回复、群里未 @ 和只 @所有人被忽略、@ 占位符被去掉而其他人的 @ 仍在、同一会话打断、发言人历史隔离、超时和失败文案、文件消息与文件失败提示。
- 锁用假的 Redis 验证第二个进程在锁被持有时不建立连接。
- 渠道保存沿用现有发布渠道接口测试：重复 App ID 被拒绝，修改本渠道且 App ID 不变可以通过。
- URL 回调已有测试继续通过，用来锁住未选长连接的渠道不受影响。
- 历史写入沿用智能体会话消息的现有断言方式。

## Out of Scope

- 工作台 ChatFlow 和通知节点里的飞书。
- 商店应用，以及用 tenant_key 区分多家企业的同一个应用。
- Lark 海外域名。
- 旧版消息卡片回调。
- 把用户发来的图片或文件交给多模态模型。
- 把思考过程或工具调用刷到飞书。
- 按字推送。
- 断线重放，或在超时、打断之后另发一条补答。
- 新增长连接专用渠道类型。
- 改现有飞书 URL 回调的静默丢弃行为。

## Further Notes

- 飞书后台要把订阅方式改成「使用长连接接收事件」，并且保存时这条连接必须已经在线，否则后台保存失败。同一个自建应用不能同时依赖回调地址和长连接。
- App ID 由飞书生成，在开放平台内唯一。不同企业的自建应用不会撞号。本变更要防的是两条发布渠道填写了同一套凭证。
- 每个应用同一时间只能有一条长连接。官方要求事件处理尽快返回，否则会重推。
- 飞书没有企微那种流式气泡。同一条消息的刷新使用官方更新消息接口。

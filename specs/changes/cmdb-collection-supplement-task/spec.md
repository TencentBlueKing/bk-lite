# CMDB 多任务采集同一实例：字段级数据调和

Status: implemented — 后端判断、配置、落库和页面入口已接上。实机 SNMP 见 implementation.md。

## 方案

采集任务本身不增加调和参数。用户单独创建一条数据调和，把会采到同一批实例的任务圈进来，并在调和里按字段设置优先级。

以 MySQL 为例：任务 A、B 都扫描 `ip1`，任务 C 扫描 `ip2`。创建一条 MySQL 数据调和，只选择 A 和 B。A 或 B 落库时，如果实例属于对方，就按这条调和里的字段顺序决定每个字段写不写。C 不在调和里，继续走现在的独占逻辑。

判断发生在落库当时。插件采完、写入之前就查调和；不是先按旧逻辑落库，再另起一次任务改写。

- 一个采集任务最多属于一条数据调和。
- 调和成员不少于两个时才生效。成员因删除任务而不足两个时，调和停止生效，剩下的任务按现在的单任务方式写入。
- 字段值按该字段自己的任务顺序决定。空值不覆盖其他来源的非空值。人工修改优先于任何采集任务。来源超过 7 天没刷新，低优先级可以接管。
- `collect_task` 仍是实例的生命周期所有者。成员顺序用来决定归属转移，不使用字段顺序。

## 适用范围

字段调和只作用于任务目标模型的主实例。

| 支持 | `task_type` | 典型模型 | 写入路径 |
|---|---|---|---|
| 是 | `host` | 主机、物理服务器（SSH） | 通用链路 `MetricsCannula` → `Management` |
| 是 | `db` | Redis、MongoDB、Elasticsearch、PostgreSQL、HBase | 通用链路 |
| 是 | `middleware` | Nginx、Tomcat、Kafka、RabbitMQ、ZooKeeper 等 | 通用链路 |
| 是 | `protocol` | MySQL、Oracle、MSSQL、PostgreSQL、InfluxDB、SSL 证书、物理服务器（IPMI / Redfish） | 通用链路 |
| 是 | `snmp` | 网络设备 | 通用链路；接口等子模型和拓扑关联保持现有冲突规则 |
| 是 | `other` | 社区版没有注册插件 | 经 `RegisteredCollect` 时走通用链路 |
| 是 | `custom_script` | 任意目标模型 | 通用链路 |
| 否 | `cloud` | 阿里云、腾讯云、华为云、ZStack、存储阵列等 | — |
| 否 | `vm` | VMware vCenter | — |
| 否 | `k8s` | K8s 集群 | — |
| 否 | `ip` | IP 地址 | — |
| 否 | `config_file` | 配置文件版本 | — |

- 是否支持按 `task_type` 判定。`cloud`、`vm`、`k8s`、`ip`、`config_file` 不支持，在服务端集中定义，插件不声明。
- `custom_script` 全部支持。例外：目标模型为 `vmware_vc` 时进入 `collect_vmware`，不经过通用链路，不能加入数据调和。
- 没加入生效调和的任务保持现有行为：不读写 `_collect_sources`，采到其他任务的实例仍然判冲突。
- 所有者是不支持的任务类型，或不在同一条生效调和里：判冲突，不写字段，不改归属。

## 数据调和

数据调和不是采集任务，没有周期、凭据和执行状态。配置存在 PostgreSQL，不改 `cmdb_collectmodels`。过期天数 N 放在系统配置，不放在这两张表。字段来源 `_collect_sources` 仍在 FalkorDB。

### 表

`cmdb_collect_reconcile` 是一条调和。`cmdb_collect_reconcile_order` 同时保存成员顺序和字段顺序。

`cmdb_collect_reconcile`

| 列 | 类型 | 约束 | 含义 |
|---|---|---|---|
| id | bigint | 主键 | |
| name | varchar(128) | 与 `model_id` 联合唯一 | 调和名称 |
| model_id | varchar(64) | 非空，索引 | 目标模型。模型定义在图里，不做外键 |
| version | integer | 非空，默认 1 | 乐观锁。每次修改顺序加 1 |
| created_at / updated_at | timestamptz | 非空 | 来自 `TimeInfo` |
| created_by / updated_by | varchar(32) | 非空，默认空串 | 来自 `MaintainerInfo` |
| domain / updated_by_domain | varchar(100) | 非空 | 来自 `MaintainerInfo` |

`cmdb_collect_reconcile_order`

| 列 | 类型 | 约束 | 含义 |
|---|---|---|---|
| id | bigint | 主键 | |
| reconcile_id | bigint | 外键 `cmdb_collect_reconcile.id`，级联删除，索引 | 所属调和 |
| scope | varchar(64) | 非空 | `member` 表示成员顺序；其他值是字段 `attr_id` |
| task_id | bigint | 外键 `cmdb_collectmodels.id`，级联删除，索引 | 采集任务 |
| position | integer | 非空，从 0 开始 | 越小越优先 |

约束：

- `(reconcile_id, scope, task_id)` 唯一。同一顺序里一个任务只出现一次。
- `(reconcile_id, scope, position)` 唯一。同一顺序里名次不重复。
- `scope = 'member'` 时 `task_id` 全局唯一。一个采集任务只能成为一条调和的成员。
- 字段顺序里的 `task_id` 必须已经是这条调和的 `member`。保存时校验，数据库不另做跨行约束。
- 删除采集任务时，数据库级联删掉它的成员行和全部字段行。删完后成员不足两行，调和配置保留，但停止生效。

任务执行时用 `task_id + scope = 'member'` 找到所属调和，再读取该调和的全部顺序。

### 创建

- 选择一个支持范围内的模型。
- 选择至少两个该模型的采集任务。已经属于其他调和的任务不能再选。
- 保存后生成两层顺序：
  - **成员顺序**：所选任务的顺序，用于归属转移和过期后的归属移交。
  - **字段顺序**：每个模型字段一份，只包含转换层会写入该字段的成员。初始顺序等于这些任务在成员顺序中的相对顺序。用户可以单独调整某一字段。脚本返回名不进入顺序。
- 转换层不会写入该字段的任务不出现在这一字段的顺序里。

### 生效

- 生效成员不少于两个时，调和参与落库判断。
- 成员被删除到不足两个时，调和配置保留，但停止生效。剩下的任务按单任务写入：它输出的字段直接写，没输出的字段保持原值。
- 再次加入任务、生效成员达到两个后，调和恢复。
- 删除采集任务时，在同一事务中把它从成员顺序和全部字段顺序里移除。它留下的字段来源视为没有来源。
- 修改顺序后，下一轮采集按新顺序判断，不回溯改写已有值。

### 页面

入口在采集任务页面。

- 新建数据调和：选模型，再选任务。
- 详情里是字段表。一行一个字段，从左到右优先级降低，只列出会采集它的成员。点某一行只调整这个字段。
- 只有一个成员会采集的字段不能调整。
- 成员顺序单独配置，不放在字段表里。
- 采集任务的创建和编辑表单不出现调和开关或优先级。

### 组织权限

可选任务和可调整顺序的范围，复用采集任务列表的 `get_queryset_by_permission`。

- 只能看到、只能选择当前用户有权限的任务。无权限的任务不展示名称和数量。
- 调整顺序需要采集任务的编辑权限。用户只在有权限的任务之间排序，无权限任务保持原位。
- 新建或删除某个字段的单独顺序，会改变所有成员的相对位置，只允许对该调和的全部成员都有权限的用户操作。
- 保存时校验提交的任务正好等于用户可见的成员，防止越权改动或遗漏。用版本号拒绝并发提交，后提交的一方刷新后重试。

## 字段来源记录

每个实例在 FalkorDB 节点上保存内部属性 `_collect_sources`，值为 JSON 字符串：

```json
{
  "fields": {
    "<attr_id>": {"source": "<task_id 或 manual>", "updated_at": "<ISO8601>"}
  },
  "seen": {
    "<task_id>": "<ISO8601>"
  }
}
```

- `fields` 记录每个字段当前值的来源。`seen` 记录每个调和成员最近一次采到这个实例的时间。本轮没有写入字段时也刷新 `seen`。
- 写入 `seen` 时去掉已删除任务和超过存活窗口的条目。
- 与字段值同一次 SET 写入。名称以下划线开头，不产生变更记录。
- 放行 FalkorDB 的属性白名单，并在实例列表、详情、导出、搜索和变更记录中隐藏。Neo4j 不改。
- 存量实例没有该属性时，字段视为没有来源，第一轮写入者成为来源。

## 落库判断

任务 T 执行到写入时：

1. T 不属于一条生效调和：按现有逻辑。实例属于其他任务则冲突。
2. T 属于一条生效调和：所有者是同一调和的其他生效成员时，进入字段判断和归属判断。所有者在调和之外，包括不支持的任务类型，则冲突。

任务 T 本轮要把字段 X 写成 v 时，使用该字段的顺序。人工来源高于任何成员。来源任务已删除时视为没有来源。按第一条成立的规则处理：

| 条件 | 结果 |
|---|---|
| 本轮结果里没有 X | 不改值，也不改来源 |
| X 的来源是人工 | 不写 |
| X 没有来源 | 写入，来源记为 T |
| X 的来源是 T | 写入，包括写空，刷新来源时间 |
| v 为空，且当前值非空 | 不写 |
| T 在该字段顺序中位于来源之前 | 写入，来源改为 T |
| T 位于来源之后，且当前值为空 | 写入，来源改为 T |
| T 位于来源之后，且来源已过期 | 写入，来源改为 T |
| T 位于来源之后，当前值非空且未过期 | 不写 |

- 空值是 `None`、空字符串、空列表。`0` 和 `false` 不是空值。
- 过期和存活窗口都是全局 N 天，默认 7 天，可在系统配置中修改。N 小于等于 0 表示不过期、不移交归属。
- 值与现值相同时不写字段值，但按上表更新来源和来源时间，不产生变更记录。
- 运行字段 `collect_task`、`organization`、`collect_time`、`auto_collect` 不参与字段判断。`inst_name` 只用于匹配，匹配成功后不改名。
- `ip_addr`、云区域等业务字段参与字段判断。主机实例名对齐依赖内网 IP 和云区域，需要保持对齐时，把这些字段的顺序设给负责它们的任务。

## 人工来源

所有经实例编辑服务的更新都算人工来源，包括页面单条编辑、批量编辑、Excel 导入更新和 OpenAPI：

- `InstanceManage.instance_update`、`instance_update_by_uuid`、`batch_instance_update`、`batch_instance_update_by_uuids`。
- Excel 导入更新 `utils/Import.py` 的 `inst_list_update`。它直接调用 `batch_save_entity`，不经过 `InstanceManage`。
- 实现时核对 OpenAPI 的实例更新是否都经过这些方法。

只有值确实变化的字段记为 `manual`。手工新建和 Excel 导入新增不标记，采集可以补全字段。实例详情里人工锁定的字段有标识，并提供「恢复自动采集」。清除后来源后，下一轮按字段顺序写入。

## 生命周期

归属只比较成员顺序，不看字段顺序。比较范围只包括同一条生效调和的成员。

| 命中的实例 | 结果 |
|---|---|
| 所有者是 T | 刷新 `collect_time`，参与清理 |
| 所有者不在这条生效调和里 | 冲突，不写字段，不改归属 |
| 不在 T 的组织范围 | 冲突，不写字段，不改归属 |
| 无所有者 | 同组织则接管 |
| 所有者在成员顺序中位于 T 之后 | 归属转给 T |
| 所有者位于 T 之前，且所有者的 `seen` 已超过存活窗口 | 归属转给 T。T 必须是窗口内看得到它的成员里最靠前的 |
| 所有者位于 T 之前，且仍在窗口内 | 不改归属，只做字段判断并刷新 `seen` |

- 任何成员都可以创建实例，创建者成为所有者。
- 归属转移保留实例现有的 `organization`。
- 只有所有者按自己的清理策略产生删除候选。窗口内还有其他成员看到过这个实例，本轮不删。
- 删除仍用 `delete_entity_if_unchanged`，原子核对 `collect_task`、`collect_time` 和 `_collect_sources`。
- 删除采集任务时仍清空图里的 `collect_task`。下一轮第一个采到它的任务接管。

子模型实例和关联不进入调和。物理服务器的内存、磁盘、网卡，以及 SNMP 接口，属于其他任务时仍然判冲突。主实例的字段判断不受影响。这是已接受的限制。

## 并发与可观测性

- 条件 SET：只有 `_collect_sources` 与本轮读取时一致才写入。失败则重读并再判断一次，仍失败就放弃该实例，下一轮再收敛。
- 任务详情分开统计「因优先级未写入的字段数」「组织范围冲突」「调和外所有者冲突」「并发放弃」。
- 变更记录归属于实际写入的任务，只包含值确实变化的字段。

## 影响面

- 新增数据调和的 PostgreSQL 模型、迁移、读写接口和权限校验。采集任务删除时同步移除成员。
- `collection/metrics_cannula.py`：生效成员写入主实例时，同一调和内的所有者不再判冲突，并带上 `_collect_sources`。
- `collection/common.py`：主实例增加字段判断、归属转移与移交、`seen` 刷新、删除前的多来源检查。
- FalkorDB：白名单放行、条件 SET、删除核对。Neo4j 不改。
- 实例编辑和 Excel 导入更新标记 `manual`，新增「恢复自动采集」。
- 前端：采集任务页面的数据调和列表、新建表单、字段顺序和成员顺序。实例详情展示来源和人工锁定。
- 系统配置增加全局天数 N，默认 7。
- 插件开发指南补充调和的落库时机、空值语义和 `inst_name` 匹配约束。

扫描和 PC 采集仍走独立写入路径，不更新 `_collect_sources`。之后调和成员可能按来源规则覆盖这些值。

## 不在本次范围

- 在采集任务上增加调和开关或优先级参数。
- 云、VMware、K8s、IP 发现、配置文件采集。
- 子模型实例和关联的字段调和。
- 把 `collect_task` 改成多值。
- 修改顺序后回溯重算已有值。
- 修改图字段类型，或实例列表的「任务名(ID)」展示。

## 验证

测试使用 SQLite 和有状态图适配器，走实际 `MetricsCannula` → `Management`。FalkorDB 的条件 SET 和删除核对单独测试。

调和配置：

- 表结构：成员顺序与字段顺序同行存储、同一模型下名称唯一、一个任务只能有一条 `member` 记录、同一顺序内任务和名次不重复、删除任务只删顺序行并令成员不足两条的调和停止生效、删除调和保留采集任务。
- 创建时至少两个任务，且目标模型与任务类型都在支持范围内。
- 一个任务不能加入第二条调和。`vmware_vc` 自定义脚本不能加入。
- 字段顺序只包含转换层会写入该模型字段的成员，初始相对顺序与成员顺序一致。脚本返回名不进入顺序。
- 删除任务后从成员顺序和字段顺序中移除。成员不足两个时停止生效，配置仍在；再加入任务后恢复。
- 无权限任务不可选、不展示。调整顺序不改变无权限任务的位置。版本号冲突时拒绝后提交的修改。

MySQL 网段：

- A、B 扫描 `ip1` 并加入同一调和，C 扫描 `ip2` 且不在调和里。A 先创建 `ip1` 后，B 按字段顺序补写，不判冲突。C 采到 `ip1` 仍然冲突。
- A 被删除后只剩 B：B 直接写入自己输出的字段，没输出的字段保持原值。

字段判断：

- 同一字段上靠前的任务覆盖靠后的任务，与执行先后无关。靠后的任务不重复写。
- 靠前的任务输出空值时，不覆盖靠后任务已写入的非空值。靠前任务自己是来源时，可以把字段写空。
- 靠后任务写入自己负责的字段后，下一轮可以更新自己的值。
- 靠前任务超过 7 天不输出该字段，靠后任务可以接管。N 小于等于 0 时不接管。
- 值相同时不写字段值，来源改为更靠前的任务。
- 运行字段和 `inst_name` 不被采集结果修改。

人工来源和生命周期：

- 页面编辑、批量编辑、Excel 导入更新后，值变化的字段不再被采集覆盖。手工新建可以被采集补全。
- 「恢复自动采集」后，下一轮按字段顺序写入。
- 成员顺序更靠前的任务采到实例后，归属转移。字段顺序不影响归属。
- 所有者超过 7 天没看到实例：移交给窗口内仍看得到它、且成员顺序最靠前的任务，不删除。
- 所有成员都超过窗口后，按所有者的清理策略删除。
- 组织范围不符、所有者在调和之外：拒绝写入，不改归属。

范围和兼容：

- `host`、`db`、`middleware`、`protocol`、`snmp`、`other`、`custom_script` 可以加入调和。
- `cloud`、`vm`、`k8s`、`ip`、`config_file` 不能加入，行为不变。
- 物理服务器 SSH 与 Redfish、两个 SNMP 任务：主实例按调和写入；同名子模型实例仍判冲突。
- 没有 `_collect_sources` 的存量实例，第一轮写入者成为来源。
- `_collect_sources` 不出现在实例列表、详情、导出、搜索和变更记录中。

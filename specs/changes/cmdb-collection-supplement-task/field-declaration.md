# 采集字段顺序

Status: implemented

本文只说明字段顺序比的是什么。成员顺序、空值、人工锁定、过期天数、归属转移仍以 `spec.md` 为准。确认前不改代码。

## Problem Statement

采集结果要经过每个插件自己的转换层，才写成实例上的模型字段。任务 A 的脚本返回 `proa`，任务 B 的脚本返回 `prob`，转换之后都写入模型字段 `prot`。

字段顺序要决定的是：写 `prot` 时，任务 A 和任务 B 谁优先。顺序不需要展示或配置 `proa`、`prob` 这段对应关系。自定义采集也是同一条路：脚本结果先转换，再写入模型字段。

## Solution

一行就是一个模型字段。这一行里只放「转换层会把结果写入该字段」的任务，按优先级从上到下排。

转换层留在各插件里。调和不读取脚本原文，不维护第二份字段对应表，也不要求用户在调和里填写采集侧的名字。

内置主机和自定义补采脚本只要转换后都写主机上的同一个字段，就出现在同一行。例如两边都写 `os_version`，就只排 `os_version`。只被内置任务写到实例上的字段，这一行只有内置任务，不能调整。

## User Stories

1. As a 采集配置人员, I want 按模型字段排列任务优先级, so that 我只决定谁写入这个字段，不用关心脚本原来的返回名。
2. As a 采集配置人员, I want 内置采集和自定义补采出现在它们都会写入的字段上, so that 补采只和内置任务争这些字段。
3. As a 采集配置人员, I want 只有一个任务会写入的字段不能调整, so that 顺序里不会出现并不写这个字段的任务。

## Implementation Decisions

- 字段顺序的键是模型属性。来源是各插件转换层写入主实例的字段名。
- 任务 A 写入 `prot`、任务 B 也写入 `prot` 时，两人排在 `prot` 这一行。`proa`、`prob` 只存在各自转换层里。
- 内置插件的转换层就是它现有的字段对应。调和取对应关系的模型字段一侧。网络设备取设备字段，不含接口。
- 自定义采集使用它自己的转换层。转换结果已经是模型字段，和内置插件一样进入顺序。不为调和再增加一份勾选或 `collect_fields`。
- 一条调和只收同一个模型的任务。不同模型即使字段名相同，也不排在一起。
- 某一行的初始顺序等于这些任务在成员顺序中的相对先后。
- 子模型、关联、`inst_name` 和运行字段不进入字段顺序。`inst_name` 仍只用于匹配实例。
- 落库时，一个任务只把转换层产出的模型字段送去判断。转换层没有产出的字段，视为本轮没有这个字段。

## Testing Decisions

- 两个任务的转换层分别从不同返回名写入同一模型字段时，顺序里只有这个模型字段，两个任务都在这一行。
- 只有一个任务的转换层写入该字段时，这一行不能调整。
- 自定义任务和内置任务写入同一个模型字段时，出现在同一行。
- 自定义任务的转换层没有产出的字段，不覆盖实例上的现值，也不改来源。
- 不同模型的任务不能创建成一条调和。

## Out of Scope

- 在调和或采集任务上再配一套返回名到模型字段的对应。
- 从脚本正文或某次采集结果推断对应关系。
- 修改各插件转换层的内部实现。
- 成员顺序、空值、人工锁定、过期天数、归属转移、子模型冲突。

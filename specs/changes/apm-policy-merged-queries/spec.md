# APM 策略评估按目标合并查询

Status: done

来源需求：p398_956。

## Problem Statement

APM 策略默认每分钟评估。调度按「策略 × 服务」拆成子任务，每个子任务里每个目标（端点、版本、实例、下游依赖）
单独向 VictoriaTraces 发 RED 汇总、趋势，当前窗还要查 Top 操作；按“全部端点”展开时先查活跃端点。一条策略
最多 100 个目标，失败重试会把同一批扫描再打一遍。这些查询和用户正在看的调用链共用 VictoriaTraces，查询条数
随目标数线性增长。

## Solution

同一条策略、同一服务、同一时间窗，把所有目标的 RED 合成一次按目标维度分组的查询；趋势合成一次分组区间查询；
基线对比的历史窗同理。取回后分发给各目标做判断。判断结果、告警快照证据、目标状态与逐目标查询完全一致。
整个服务这一窗的唯一 Span 超过单次上限时，本轮退回逐目标查询。

## User Stories

1. 作为平台运维，我配置“全部端点”的策略后，VictoriaTraces 承受的策略查询条数不随端点数增长。
2. 作为策略使用者，我看到的触发、恢复、证据曲线和以前一致，不因合并查询改变判断。
3. 作为策略使用者，按版本、按实例、下游依赖、基线对比的策略同样受益且结果一致。
4. 作为平台运维，查询失败时这一轮这条策略按现在的“查询失败”处理并重试，不留下半评估状态。

## Implementation Decisions

- 合并粒度：一个评估子任务（一条策略 × 一个服务 × 一个评估时刻）内的全部目标。不跨策略、不跨服务合并。
- 入口目标：在现有去重口径（1 天以内按 `trace_id + span_id`）上，按目标维度（入口操作名，及策略展开所需的
  版本、实例）分组，一次取回全部目标的整窗 RED，含策略级慢请求与 Apdex 计数；趋势一次分组区间查询取回。
  去重聚合需要保留分组维度（例如按 `trace_id, span_id` 去重时同时保留 name/version/instance）。
- 目标为“整个服务”（端点模式 SERVICE）的策略只有一个目标，保持现状即可，不强行走分组。
- 当前窗需要 Top 操作的地方，结果必须与逐目标查询一致；能从同一次分组结果派生就派生，不能则保持现有单次查询，
  但不得随目标数增长。
- 依赖目标：按依赖维度分组，一次取回。
- 基线对比：上一窗、1 小时前、24 小时前、偏移小时/天的历史窗，各自一次分组查询；`baseline_days` 的按天查询
  加上目标维度分组。
- 唯一 Span 上限：沿用 `MAX_UNIQUE_SPANS` 与截断检测。分组查询触发上限时，本轮退回现有逐目标路径（逐目标路径仍
  各自受上限保护）。
- 失败语义：分组查询失败 = 本轮这条策略在该服务上的全部目标按现有“查询失败”处理（记 `last_failed_at`，整轮重试）。
  同分钟重试时已成功的目标仍按现有游标跳过。
- 合并只发生在 telemetry store 的读取层与评估器的取数层；目标展开、判断、快照、目标状态、消失关闭逻辑不改。
- 试算（dry-run / preview / test_query）走同一取数路径，结果一致。

## Testing Decisions

- 核心测试是等价性：同一组夹具数据下，合并路径与逐目标路径得到的数值、触发/恢复判断、快照证据序列、目标状态一致。
  用内存 telemetry store 夹具同时实现两条路径，或对同一组 Span 夹具分别跑两条路径比较。
- 查询次数：一条含 N 个端点的策略一轮评估对 telemetry store 的调用次数为常数（不随 N 增长）；用记录调用的 fake 断言。
- LogsQL 形状：在适配器层用现有 HTTP session mock 断言分组查询带分组维度、带去重、带上限。
- 覆盖：全部端点、指定端点、版本、按实例、依赖、上一窗/偏移/基线天、超上限退回、分组查询失败。
- 先例：`test_policy_service.py`（查询次数）、`test_policy_scope.py`（100 目标与消失关闭）、
  `test_policy_baseline_days.py`、`test_policy_dependencies.py`、`test_victoriatraces_adapter.py`（LogsQL 与上限）。
- 验证命令：sqlite 下跑 `server/apps/apm/tests`。

## Out of Scope

- 策略改读 VictoriaMetrics 聚合层。
- 改评估频率、评估延迟或目标上限。
- 跨策略、跨服务合并查询。

## Further Notes

- 执行顺序见 `specs/changes/observability-aggregate-metrics/spec.md` 的「总执行顺序」。
- HTTP 依赖仍逐目标查询；别名重叠或分位值无法合并时整轮退回逐目标。

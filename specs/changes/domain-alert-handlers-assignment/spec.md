# 监控 / 日志 / APM 告警处理人与分派

Status: complete

## Problem Statement

售前要求监控、日志、APM 各自的告警有一份轻量分派闭环。今天三域策略只有通知人，告警上的 `operator` 是关单后才写入的操作员，列表也不能按「我是处理人」过滤，活跃告警只能关闭。值班无法在本模块里指定默认处理人、认领空单或把空单分给组织里的人。

## Solution

APM 策略先补上自己的所属组织。三域策略再增加可选的多名处理人，作为新告警的默认分配人。告警创建时把当时策略处理人快照到这条告警上；之后改策略只影响新告警。列表用「处理人」展示这份快照，并增加「我的告警」条件。还没有处理人的活跃告警支持认领、分派、关闭；手工分派后按该策略通知配置给被分派人发分派通知。创建时的快照不是分派，不发分派通知。

## User Stories

1. As a 策略配置人, I want 在监控 / 日志 / APM 策略上可选多名处理人，候选人来自该策略已选组织的用户, so that 我能给后续告警指定默认值班人而不必每次手工分
2. As an APM 策略配置人, I want APM 策略像监控 / 日志一样必填所属组织, so that 策略可见性、处理人候选和新告警组织不再借服务组织凑
3. As a 策略配置人, I want 开启通知并需要填写通知人时，通知人默认带上已选处理人且允许删除, so that 我不用把同一批人填两遍
4. As a 值班人, I want 告警列表用「处理人」展示当前分配人，并可用「我的告警」只看处理人包含我的单, so that 我能按自己的队列值班，而不把关单人误当成处理人
5. As a 能操作活跃告警的人, I want 当这条告警还没有处理人时认领给自己、或从这条告警所属组织里选人分派、或关闭, so that 空单能在本模块闭环，而不必去告警中心
6. As a 被分派的处理人, I want 有人手工分派给我之后，按该策略已开的通知渠道收到分派通知, so that 我知道有新单进来
7. As a 已经有处理人的活跃告警的操作者, I want 继续只能关闭、不能再认领或分派, so that 处理人名单不会被第二次分派覆盖
8. As a 策略维护者, I want 改策略处理人只影响之后新产生的告警, so that 已经在响的单保持当时的分配人

## Implementation Decisions

- 监控、日志、APM 各自在本 app 内实现策略字段、快照、列表过滤、认领 / 分派和通知，不抽跨 app 公共库或共享服务。三域只对齐产品语义，代码和数据模型留在各自 app，便于以后独立售卖。已有的通用组织用户查询、JSON 成员过滤可以继续各用各的现成工具，但不为此新建 `domain_alert_*` 公共模块。
- 处理人和分派人是同一角色。策略处理人是新告警的默认分配人；告警处理人是这条单当前的分配人名单，可以多人。
- 三域策略和告警都新增 `handlers` JSON 名单，不复用 `operator`。`operator` 继续表示关闭 / 恢复时的最后操作人，列表「处理人」只读 `handlers`。历史告警不回填，空名单就是没有处理人。
- `handlers` 与通知人下拉使用同一套用户标识，便于默认带入通知人。「我的告警」用当前用户的 id 与 username 做成员匹配；认领写入与下拉相同的标识。
- 告警创建时把当时策略 `handlers` 原样快照到告警 `handlers`。空名单保持为空。创建不是分派：不发分派通知，不写生命周期事件。
- APM 策略补上自己的所属组织，对齐监控 / 日志：创建必填、写前校验可分配组织、列表 / 详情按策略组织 fail-closed，不再借 `service.organization_links` 当策略组织。存量策略迁移时从当时服务组织回填；之后改服务组织不改写策略组织。
- 选服务时若策略组织还是空的，默认带上该服务当前组织，允许改。不要求策略组织必须是服务组织子集（与监控 / 日志一致，只校验调用方可分配）。
- 新产生的 APM Alert / Event 改为快照**当时策略组织**，不再快照服务组织。已有告警组织不变。
- 告警权限和分派选人看告警自己的所属组织，不回读策略当前组织。三域策略处理人候选都看**该策略已选组织**。
- 分派通知只走需要接收人的人工渠道。仅 NATS、告警中心副本或「无需接收人」的渠道不向被分派人发人到人通知。
- 落地时改写监控 / 日志 / APM capability 里「领域告警不做分派」的旧表述，避免文档与 613 冲突。
- 「我的告警」只是列表查询条件，不改变现有可见性。点上之后在当前可见集合里再筛处理人包含当前用户的记录。
- 认领、分派只允许活跃且 `handlers` 为空的告警。认领把当前用户写成唯一处理人。分派用请求名单整表替换空名单，至少一人，且每人必须是未禁用、属于告警所属组织的用户。有处理人之后本期不提供转派。关闭规则与今天一致，与是否有处理人无关。
- 认领、分派与关闭使用同一套对象权限：调用者必须能看见这条告警，并具备该域现有关闭所需的操作权限。认领不额外要求操作者属于告警组织（能看见即可）。
- 并发认领 / 分派必须锁行并按「名单仍为空」条件更新，后到者失败，不得覆盖已有处理人。
- 手工分派成功后发分派通知的条件：监控 / 日志看策略 `notice` 为开且存在需要接收人的渠道；APM 看是否存在 `delivery_mode=message` 且需要系统用户的通知目标。策略已删除或通知未配置则跳过，认领不发。创建触发通知仍走原接收人，不发分派通知。
- 分派选人在三域都按告警组织拉用户。APM 现有接收人接口只认当前组织，本域要补「按组织 ID 列表取用户」，不能复用监控 / 日志的 API。
- 策略组织变更时，已选处理人按与通知人相同的规则剔除越界用户。开启通知且通知人为空、同时已有处理人时，把处理人写入通知人；用户删掉的通知人不再自动补回。
- 监控策略模板 / 批量套用若复制通知字段，同步带上空的 `handlers`，避免模板把处理人做成隐式必填。
- 认领与分派收敛到各域一个服务入口，且不得把认领 / 分派塞进监控「每种状态动作一条」的唯一约束里。事件写入由 614 规格在该入口成功提交后、同一事务内补写，见 `specs/changes/domain-alert-lifecycle-events/spec.md`。
- 不回写告警中心处理人，不复制告警中心的未分派 / 待响应 / 处理中状态机，不新增对外 OpenAPI。

## Testing Decisions

- 只测对外行为：策略读写与默认通知人、创建快照、列表展示与「我的告警」、认领 / 分派 / 关闭的可点与拒绝、分派通知收件人、组织变更后的候选人。不测内部如何拼 JSON 查询。
- 最高接缝是各域现有策略详情、告警创建扫描 / 评估、告警列表与关闭入口。在这些入口上改期望并补处理人用例，不另起平行框架。
- 必须覆盖：APM 策略创建必填组织、按策略组织可见、新告警快照策略组织、改服务组织不改策略；策略处理人可空、多选、越界剔除；通知人默认带处理人且可删、不再自动补回；新告警快照策略处理人，改策略不影响旧告警；空处理人的活跃告警可认领、可分派、可关；有处理人后认领 / 分派被拒绝，关闭仍可；分派选人拒绝告警组织外或禁用用户；并发第二个认领 / 分派失败；「我的告警」只留下处理人包含当前用户的可见告警，不靠 `operator`；手工分派在通知开启时发给被分派人，通知关闭或策略已删除时不发；创建不发分派通知；历史空 `handlers` 的活跃告警可被认领 / 分派。
- 三域各走自己的创建与关闭入口做对等断言。前端锁定策略表单、列表列名、我的告警条件和空处理人时的三个操作。

## Out of Scope

- 认领 / 分派 / 关闭 / 恢复的事件写入与详情时间线展示（614，见 `specs/changes/domain-alert-lifecycle-events/spec.md`）。
- 转派、升级、待响应状态、超级用户改处理人。
- 创建快照当作分派，或策略变更回写已有告警。
- 认领通知、关闭原因输入框。
- 回填历史 `operator` 为处理人。
- 告警中心处理人双向同步，或领域侧复制告警中心状态机。
- 新增对外 OpenAPI 认领 / 分派。

## Further Notes

这是领域告警上的轻量自闭环，不是告警中心值班模型下沉。告警所属组织已与策略解耦；分派选人跟告警组织走，策略处理人候选仍跟策略组织走。事件审计由 614 承接：在本规格预留的认领 / 分派入口成功后写事件，关闭 / 恢复不双写。复验跟进（分布图 / `my_alert` 次要入口 / 展示名 / 分派日志）见 `specs/changes/domain-alert-handlers-followup/spec.md`。

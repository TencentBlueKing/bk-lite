# 后台进程数据库连接生命周期（Issue #7076）

状态：附件清理路径已复现并修复；NATS 现场连接来源待核实。

## 问题与证据

现场通过 PG client_port 与宿主机 socket 关联，确认两个 NATS listener 持有五条长期 idle 连接，附件清理调度器持有一条。采样时没有连接满、空闲事务或锁等待。当前证据不能证明六条连接是此前连接超限的根因，也不能证明 NATS 连接数量持续增长。

附件清理调度器在调用 `cleanup_expired_artifacts` 后直接休眠，没有 HTTP 请求结束信号，也没有显式连接清理。在真实 PostgreSQL、`CONN_MAX_AGE=0` 下，测试确认连接在休眠及 `--once` 返回时仍未关闭。

NATS 标准同步入口已经使用 `DatabaseSyncToAsync`，在真正执行 ORM 的线程前后调用 `close_old_connections`。真实 PostgreSQL 测试确认连续三轮成功或异常后连接都被关闭，主线程连接不受影响。因此本次不修改监听器、消息回复或 ACK 逻辑。

## 修复范围与契约

- 附件清理调度器每轮前后调用 Django `close_old_connections`；退出、异常、取消经过 finally 清理。
- 保留 Django 配置的连接寿命策略，不新增全局连接池、不跨线程关闭连接。
- 保留 batch_size、interval 上下界、清理结果输出及 `--once` 语义。
- 连接清理成功时，任务原异常仍向外传播，不自动重放对象删除操作。连接清理本身失败沿用 Django 的异常传播，不新增双重故障的异常优先级机制。
- 新增 NATS 入口连接生命周期回归保护，不将入口测试成功扩大解释为所有旁路线程均正常。
- 不改数据库配置、不新增生产监控或定时采集、不终止生产会话。

## 验证

- NATS 入口：真实 PG 下连续三轮成功/异常保持返回值或异常身份、释放工作线程连接且保留其他线程连接。
- 现有附件清理和管理命令、NATS 队列/背压/错误协议相关回归共 52 项通过。

- 全量 `make test` 的应用套件在约 311 秒后仍处于收集阶段（已收集 41240 项），人工中断，不能宣称全量门禁通过。

## 未解决项

NATS 五条现场连接尚未关联到具体 subject/handler/线程。需要线上镜像提交、有效 CONN_MAX_AGE，以及触发操作/对应消息日志；可在复现时再次对照 PG PID + backend_start、client_port 与应用 PID。若标准入口之外的线程访问 ORM，必须在该线程实际调用边界验证并修复，不在监听主线程补清理冒充解决。

本次不关闭 #7076，也不声称修复了历史 `too many clients already` 的全部原因。

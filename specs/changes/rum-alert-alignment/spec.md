## Problem Statement

RUM 的「事件」模块（告警、策略）和监控、日志、APM 同类模块差距很大。顶部「告警 / 策略」分段导航是共用组件，差在下面：告警列表只有「进行中 / 历史」胶囊和刷新，没有搜索、筛选、处理人和通知结果；策略表单的通知渠道是手填渠道 ID；告警产生后通知当场发送，失败只打日志，不会补投，也不会进告警中心。

底层原因是运行闭环没有搭起来：策略没有组织，告警没有组织、处理人和策略快照；判定任务每 30 秒扫全部策略，一条慢查询会挡住其它策略；指标查不到行时返回 0，无数据和真实零值分不开；策略停用或删除会把进行中告警直接改成「已恢复」，策略删掉后历史告警连名字都没有；通知里的详情链接指向不存在的页面；RUM 不在可信内部调用方名单里，即使发告警中心副本也会被记成 APM 来源。

RUM 尚未上线，没有存量数据需要兼容。

## Solution

RUM 保留自己的策略和告警表，不并入监控策略，不抽跨 App 公共库，按监控 / 日志 / APM 已确认的领域告警语义补齐整条运行闭环：策略带所属组织、处理人、从系统渠道列表选择的通知目标；告警拆成「告警」「告警事件」「投递箱」三张表，与 APM 同形；判定按策略拆成独立任务并区分无数据；通知先落投递箱再投递，支持告警中心事件副本；进行中告警可认领、分派、转派、关闭，动作写入事件时间线。页面换成与 APM、日志一致的下划线页签、筛选行和内容卡。

分两期交付：第一期做地基与运行闭环（组织、快照、渠道选择、无数据判定、拆任务、投递箱、告警中心副本、后端筛选、列表骨架、链接修复）；第二期做处置闭环（处理人、认领 / 分派 / 转派 / 关闭、生命周期事件、「我的告警」、通知列与人工重投）。第二期必须整套一起上。

## User Stories

1. As a RUM 策略配置人, I want 创建策略时必选所属组织，并从系统渠道列表选择通知目标、看到渠道是普通通知还是告警中心副本, so that 我不用手填渠道 ID，也知道告警会送到哪里
2. As a RUM 策略配置人, I want 策略上可选多名处理人，候选人来自该策略已选组织, so that 新告警有默认值班人
3. As a RUM 策略配置人, I want 配置判定窗口、持续时长和「连续 N 次无数据后触发」, so that 稀疏流量下不会把流量断开误报成指标为零，也不会把真实零值误报成无数据
4. As a RUM 值班人, I want 一条策略超阈值后只产生一条进行中告警，恢复后变为「已恢复」，停用或删除策略时进行中告警变为「已关闭」且保留策略名、应用、指标快照, so that 告警状态和历史不会因为策略变动失真
5. As a RUM 值班人, I want 触发、恢复、重复通知、分派、转派都经投递箱送达，失败自动补投，详情里能看到每条投递的状态、次数和原因，并能人工重投终止失败的那条, so that 通知不会悄悄丢
6. As a 告警中心值班人, I want 策略选了告警中心副本渠道时，中心里出现这条 RUM 告警且来源是 RUM, so that 跨源聚合不缺 RUM，也不会错记成 APM
7. As a RUM 值班人, I want 告警列表有「活跃告警 / 历史告警」页签、搜索、应用筛选、「我的告警」、处理人列和通知列，空数据时保留表头, so that 和监控、日志、APM 的事件页用法一致
8. As a RUM 值班人, I want 对无处理人的活跃告警认领、分派、关闭；有处理人时当前处理人可转派、可关闭；非处理人关闭被拒绝；已恢复、已关闭不可再手工关闭, so that 处置规则与其它三域一致
9. As a RUM 值班人, I want 告警详情时间线按序展示触发、恢复、认领、分派、转派、关闭, so that 谁接单、谁交班、何时收口有据可查
10. As a 收到通知的人, I want 点通知里的链接直接打开对应告警详情, so that 不用再到列表里翻
11. As a RUM 策略维护者, I want 策略列表看到最近一次判定时间和结果, so that 能分辨策略在跑还是卡住了

## Implementation Decisions

### 范围与原则

- RUM 作为第四个领域告警域接入既有语义，继承 `domain-alert-handlers-assignment`、`domain-alert-lifecycle-events`、`domain-alert-reassign` 和 `docs/design/product-decisions/domain-alert-handlers.md` 的全部已确认规则；只对齐语义，不抽公共库，不复制告警中心状态机，不回写处理人到告警中心，不新增对外 OpenAPI。
- 一条策略仍只看一个应用的一个指标，告警对象是应用。不按页面、版本拆目标，不做策略组、策略模板、对象树、分布图。
- RUM 未上线，没有数据迁移、回填、兼容字段或降级标记。模型直接建成最终形状。

### 组织与权限

- 策略新增所属组织，多选、创建必填，写前按调用方可分配组织校验，列表 / 详情按策略组织 fail-closed。应用保持租户级，`org_id` 字段不动，不在本次范围。
- 告警创建时快照策略当时的组织与处理人。告警列表、详情、认领 / 分派 / 转派 / 关闭都按告警自己的组织在服务端过滤，不回读策略当前组织。分派选人按告警组织拉用户；策略处理人候选按策略组织拉用户。
- 权限分开：策略增删改继续用 `monitors-Operate`；认领、分派、转派、关闭和人工重投用 `alert_events-Operate`；查看用对应 `-View`。RUM 菜单权限定义里 `alert_events` 目前只有 `View`，须补上 `Operate`，并加入默认角色的权限集合。

### 策略模型与表单

- 策略字段：名称、应用、所属组织、指标、比较符、警告 / 严重阈值、严重级别、判定窗口（5 / 15 / 60 分钟，默认 15）、持续时长（默认 5 分钟，表单可见）、无数据连续次数（默认 3，0 表示不报无数据）、重复通知间隔（可空）、处理人（可空多选）、通知目标、启用。删掉无人使用的 `signal`。
- 判定状态从 `pending_since / recovering_since` 换成连续命中次数、连续恢复次数、连续无数据次数和判定游标，与 APM 同形。
- 通知目标是带渠道 ID、渠道名、渠道类型、投递方式、接收人模式和接收人的对象，不再是字符串 ID 列表。告警中心副本渠道不填接收人；普通渠道接收人默认带处理人，可删，删后不自动补回。
- 策略组织变更时，按与通知人相同的规则剔除越界的处理人与接收人。
- 判定窗口默认 15 分钟是 RUM 与 APM 的有意差异：RUM 流量稀疏，窗口太短会一直无数据。重复通知是 RUM 保留的能力，APM 没有，不删。

### 告警模型

- `RumAlertEvent` 现有单表拆成三张：
  - 告警：状态 `active / recovered / closed`、当前严重级别、当前值、组织快照、处理人快照、策略名 / 应用 / 指标 / 比较符 / 阈值快照、策略 ID 快照、开始时间、结束时间、最后事件时间、操作人（关闭 / 恢复时的最后操作人，不是处理人）。
  - 告警事件：动作 `triggered / recovered / claimed / assigned / reassigned / closed`，发生时间，严重级别，值，结构化内容（谁、做了什么、处理人变成谁），组织快照。事件标识按发生次唯一，认领 / 分派 / 转派不得复用「告警 + 动作 + 级别」这种会和触发撞车的键。
  - 投递箱：投递键、所属事件（可空）、所属告警、渠道、投递方式、接收人、标题、正文、载荷、状态 `pending / delivered / failed`、尝试次数、下次重试时间、认领时间、最后错误码与错误信息、投递 / 失败时间。投递键按「事件 + 渠道」唯一。
  - 重复通知不是事件：它不写事件行，投递键按「告警 + 第 N 次重复通知 + 渠道」唯一，N 记在告警上并随每次重复通知递增；告警上同时记最后通知时间，用于判断是否到达重复间隔。重复通知只走人工渠道，不向告警中心重复发副本。
- 状态枚举与 APM 一致，不再使用 `firing / resolved`。前端状态色、国际化键一并改。
- 详情时间线直接读事件表，不再从触发时间和恢复时间两个字段拼。详情里现有的指标趋势保留，仍按需实时查询。

### 判定

- 调度改为每分钟分发一次：只负责把启用策略拆成独立任务，每条策略一个任务、有界重试。
- 单条策略的状态推进在行锁内进行，并按判定游标幂等：同一策略同一分钟重复执行不得开出第二条进行中告警。
- 指标查询区分「有值」和「无数据」。查不到行即无数据，不再返回 0。无数据连续达到配置次数且告警未进行中时触发无数据告警；有值后无数据计数清零。
- 指标读失败只跳过当前策略，记最后失败时间；成功记最后成功时间。策略列表展示最近一次判定时间与结果。
- 停用策略：不再判定、不再重复通知；进行中告警系统关闭，状态 `closed`，操作人记系统，写一条 `closed` 事件。删除策略：先同样处理，再删除；告警靠自身快照保留策略名、应用、指标。
- 人工关闭是终态；之后再次超阈值另开新告警，不复用。自动恢复、停用、删除等系统关闭不看处理人。

### 通知与告警中心

- 触发、恢复、重复通知、分派、转派都先写投递箱，再由每分钟任务投递。认领不发通知。创建时快照处理人不是分派，不发分派通知。
- 渠道调用失败可重试；渠道不存在、接收人无效、渠道不属于事件组织是终止失败。详情展示每条投递的状态、次数、原因；终止失败的投递允许人工重投，重投记审计。
- 把 `lite-rum` 加入可信内部调用方名单；告警中心副本以 `lite-rum` 身份签名投递，`pusher` 为 `lite-rum`。副本载荷资源类型 `rum_application`，资源 ID 与资源名为应用名，级别从 `info / warning / critical` 映射到告警中心等级，组织取渠道授权范围与事件组织的交集。
- 分派 / 转派通知只走需要接收人的人工渠道；告警中心副本和无需接收人的渠道不发人到人通知。策略已删除或没有可用渠道则跳过。
- 通知里的详情链接改为告警列表地址加 `event` 查询参数；列表页读到参数时自动打开对应详情抽屉。

### 告警处置

- 进行中且处理人为空：可认领（当前用户成为唯一处理人）、分派（整表写入至少一人，每人须未禁用且属于告警组织）、关闭。
- 进行中且已有处理人：当前处理人可转派（整份替换，至少一人，空单拒绝）、可关闭。非处理人关闭：列表与详情不展示关闭，接口拒绝且状态不变。没有超级用户豁免。
- 已恢复、已关闭不可再手工关闭。
- 认领 / 分派 / 转派 / 关闭收敛到单一服务入口，锁行并按前置条件更新，后到者失败；事件写入与处理人名单更新同一事务，通知在提交后发送，通知失败不删事件。
- 「原因」是结构化审计，不新增必填原因弹窗。

### 列表接口

- 告警列表接口支持状态（活跃 / 历史）、应用、关键词、「我的告警」筛选和服务端分页，不再由前端拉 200 条自行切分。「我的告警」只按处理人包含当前用户过滤，不改变可见性。
- 详情接口返回告警、事件序列、投递列表与指标趋势。

### 页面

- 告警列表：与 APM、日志一致的下划线页签「活跃告警 / 历史告警」，筛选行（搜索、应用、「我的告警」），内容卡，空数据保留表头。「告警中心」入口放工具栏右侧，不再和页签排成一组。
- 列名对齐 APM：名称、级别、状态、指标 / 值、应用、处理人、通知、触发时间、操作。操作列按处置规则显示详情、认领、分派、转派、关闭。
- 详情抽屉：状态与级别、关键指标、指标趋势、事件时间线、通知投递列表（含人工重投）。
- 策略列表：筛选、新建、表格收进同一张卡；新增「组织」「处理人」「最近判定」列。编辑继续用抽屉，这是 RUM 字段少于 APM 的合理差异。
- 策略表单：通知渠道改为系统渠道选择器，新增组织、处理人、判定窗口、持续时长、无数据连续次数字段。渠道选择器的交互对齐 APM 策略编辑器里的通知目标字段（按渠道显示投递方式与接收人模式）；是否把该组件升为共享组件按 `web/COMPONENT_GOVERNANCE.md` 判断，不满足条件就在 RUM 内实现，不跨 app 直接 import APM 的页面组件。
- 告警级别：RUM 保留 `info / warning / critical`，不改成 APM 的 `critical / error / warning`；页面上的级别色沿用 RUM 现有语义色映射。

## Testing Decisions

- 只测对外行为：给定指标序列与策略配置，产生的告警状态、事件动作、投递记录与接口返回；不测内部如何拼查询或锁。
- 后端最高接缝：策略服务（创建 / 更新 / 停用 / 删除）、单条策略判定任务、投递任务、告警处置服务、告警列表与详情接口。沿用 `apps/rum/tests/test_monitors_service.py` 的 MemoryPolicyStore / MemoryEventStore 内存接缝风格扩展；判定与分析用例参考 `test_victoria_analytics.py` 的假 VictoriaLogs 服务；处置用例参考 `apps/apm/tests/test_alert_handlers.py` 和 `test_policy_service.py`。
- 第一期必须覆盖：
  - 创建策略组织必填、越界组织拒绝；策略列表 / 详情按组织过滤。
  - 同一策略同一分钟重复执行只开一条进行中告警；恢复后状态 `recovered` 且各有一条触发 / 恢复事件。
  - 无数据与零值分离：流量断开时 `session_count <` 策略不触发；无数据连续 N 次后触发，有值后恢复。
  - 指标读失败只跳过该策略，其它策略继续判定，最后失败时间被记录。
  - 停用策略后进行中告警变 `closed` 并有系统关闭事件；删除策略后历史告警仍带策略名、应用、指标。
  - 投递箱：渠道暂时失败后补投成功且不重复发送；渠道不存在 / 接收人无效 / 组织不匹配终止失败且原因可见。
  - 重复通知：到达间隔后每个人工渠道各一条新投递，不写事件、不发告警中心副本；未到间隔不发。
  - 告警中心副本以 `lite-rum` 身份发出，载荷资源类型 `rum_application`，级别映射正确；未配置副本渠道时不发。
  - 列表接口按状态、应用、关键词过滤并分页。
- 第二期必须覆盖：
  - 新告警快照策略处理人，改策略不影响已有告警。
  - 空处理人可认领 / 分派 / 关闭；第二次认领 409 且只有一条 `claimed`；分派拒绝组织外或禁用用户。
  - 有处理人后只有当前处理人可转派 / 关闭；非处理人关闭被拒绝且状态不变；转派整份替换、空单拒绝。
  - 已恢复 / 已关闭不可手工关闭。
  - 「我的告警」只留下处理人包含当前用户的可见告警。
  - 分派 / 转派只在存在需要接收人的人工渠道时发通知；认领不发；创建不发分派通知。
  - 人工重投只接受终止失败的投递，并记审计。
- 前端锁定：列表页签、筛选项、列名、空数据保留表头；按状态与处理人显示 / 隐藏操作按钮；通知链接参数打开详情抽屉；策略表单的渠道选择器与新增字段。前端用例延续 `web/src/app/rum/__tests__/` 现有 vitest 风格。
- 日志按仓库 §8 规则改动的地方补行为回归测试：模板与参数、单一 traceback 所有权、不泄露载荷。

## Out of Scope

## Further Notes

- 规格未写、按 APM 同类实现推断的点：
  - 一条策略只盯一个应用，判定计数、游标、最近成功 / 失败时间直接记在 `RumAlertPolicy` 上，不另建目标状态表。
  - 持续时长换成连续命中：`forDurationSec <= 0` 时第一次判定即触发或恢复，否则 `max(1, seconds // 60)`。默认 300 秒即 5 次。游标是该分钟的时区 ISO，同一策略同一分钟只开一条进行中告警。
  - `monitor_metric` 查不到行返回 `None`。`error_rate` 在会话数小于等于 0 时也是无数据；数值 0 是有效样本。无数据告警用策略上的级别。
  - 可重试投递按 APM 指数退避，上限 8 次后终止。系统关闭与手工关闭的操作人分别是 `"system"` 和当前用户名；这两类关闭不入投递箱。
  - 事件键是 `{alert_id}:{action}:{uuid}`。重复通知不是事件，键是 `{alert_id}:renotify:{n}:channel:{channel_id}`。
  - 告警中心级别沿用监控映射：`critical → 0`、`warning → 2`、`info → 3`，未知为 `3`。触发动作在副本载荷里写成 `created`。组织交集交给 `dispatch_notification`，RUM 传入事件组织和 `producer=lite-rum`。
  - 列表可见性跟当前团队数据范围，查不到就空，没有超级用户全量豁免。投递认领租约 300 秒。
  - 分派 / 转派的人工渠道是 `message` 且接收人模式为 `system_user` 或 `free_text`。`system_user` 的接收人换成新处理人；`free_text` 沿用渠道上配置的接收人。告警中心副本和 `none` 不发。
  - 人工重投只接受 `failed`，审计写入 `RumAlertDeliveryRetry`，并把尝试次数清零后重新进入待投递，避免第 8 次上限立刻再次终止。
- 第一期不依赖第二期；第二期依赖第一期的组织、告警 / 事件表和投递箱。第二期不得只上「关闭」按钮：没有处理人规则的关闭与已确认的领域决策冲突。

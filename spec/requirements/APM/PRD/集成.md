## 1. 背景与目标

APM 集成菜单承担"应用接入与数据连通"的引导与管理职责,是 APM 在 P0 阶段的入口模块。集成菜单下设两个并列的二级页:

- **添加接入**:接入方式总览 + 接入详情页,引导用户以自助方式把应用接入 APM,接入后按"① 上报端点 + ② 接入配置"两步完成配置,几分钟后即可在"服务 / 探索 / 接入列表"菜单看到首批数据。
- **接入列表**:已接入实例视图,按"接入方式 / 接入时间 / 活跃状态"的接入维度呈现所有已经上报数据的应用 / 服务,跟"服务目录"(按健康度视角)互为补充:服务目录关注"现在活不活",接入列表关注"怎么接进来的、最近还活着吗"。

集成菜单不向业务侧签发任何凭证或鉴权 token;OTLP 入口鉴权由部署环境的反向代理 / mTLS / Header 校验负责,APM 业务层不参与鉴权决策。

集成菜单是 APM 的**唯一**接入入口,所有 SDK、OTel Collector、eBPF、Kubernetes Operator 等接入方式,都通过"添加接入"完成配置;接入后的实例统一在"接入列表"中管理。

## 2. 范围定义

- **添加接入**(二级页):接入方式总览(按 SDK / OTC / eBPF / K8s 四组展示,SDK 组下分 Node.js / Java / Python / .NET / Go 五种语言卡)+ 接入详情页(每种接入方式对应一页,采用"① 上报端点 + ② 接入配置"两步布局,垂直分块,不嵌套 Tabs)。
- **接入列表**(二级页):已接入实例表格,按服务 / 应用 / 环境 / 接入方式 / 接入时间 / 最近上报 / 状态 字段展示;行操作仅 1 类(查看,跳到"服务目录 → 该服务详情");新增 P0 同步落地。
- 上报端点:平台统一分配的 OTLP 端点 URL,SDK / Agent 走 `telegraf/api`,OTel Collector 走 `v1/traces`;按云区域单选 + 组织多选联动。
- 接入配置:按接入方式给出可复制的代码片段;SDK 类用"自动探针 / Docker 运行(-e 注入)"两段 Segmented 切换,OTC 类用 Collector exporter YAML 片段,eBPF / K8s 类按各自特殊形态给出。

## 3. 关键能力

### 3.1 权限模型(APM 接入适用)

APM 接入页的可见与可操作遵循 bklite 统一权限体系:

- **菜单操作**:接入页(`/apm/integration`)的菜单项在 bklite 角色系统中声明 `operation=["View", "Operate"]`;用户对集成页的查看、配置、复制等操作均不引入额外鉴权。
- **数据隔离**:集成页不展示其他 Group 的接入历史(集成菜单**本身不持久化接入历史**,仅展示当前 Group 用户的本地接入配置上下文)。
- **配置管理**:集成页的接入方式卡片与代码片段以**只读模板**形式呈现,组织管理员不可自定义代码片段,仅能通过"系统管理 → 菜单 / 角色"控制本组织成员对集成页的访问与操作权限。
- **角色配置**:不在 APM 内部声明"接入管理员"角色;用户在 APM 接入页可执行复制、切换云区域 / 组织等操作,只需具备集成菜单的 `Operate` 权限,由系统管理员在"系统管理 → 角色"中给角色配菜单 operation。

### 3.2 接入方式总览

- 按"SDK / OTC / eBPF / K8s"四组横向分块展示可选接入方式。
- SDK 组下分 Node.js、Java、Python、.NET、Go 五张语言卡,每张卡注明接入方式描述(例 Node.js 写"零代码自动探针接入",Java 写"字节码注入零代码接入",Go 写"编译期引入 SDK 接入")。
- OTC 组下展示"OTel Collector(链路)"卡,描述"已有自建 Collector?改它的 exporter 把链路推到本平台"。
- eBPF 组下展示"eBPF 自动注入(OBI)"卡,描述"无需改代码,内核态 eBPF 自动捕获服务链路",标记"低侵入"。
- K8s 组下展示"Kubernetes 注册注入(OTel Operator)"卡,描述"装一次 Operator,给 Pod 打一行注解即零代码注入探针"。
- 每张接入卡为入口,点击后跳转到对应接入详情页。

### 3.3 接入详情页(① 上报端点 + ② 接入配置)

接入详情页以单一接入方式为粒度(例 Node.js、Java、OTel Collector),由"① 上报端点"和"② 接入配置"两个垂直分块组成,**不使用 Tabs 切换**——两段都同时可见,自上而下排布。

接入详情页**不展示**以下内容(已剔除):

- 接入自检卡(传输与准入 / 数据落库 / 最近活跃 / 采样保留 4 项)
- Trace 接入任务路径 5 步
- "接通后先核对" / "跨服务不断链"双栏静态提示
- 排错说明(Markdown 文档)

理由:第一版聚焦"把链路接进来",自检与排错放进服务目录、探索菜单(基于真实数据);静态说明留给用户拷贝代码后自行处理,避免在接入页引入与实际数据无关的推断式文字。

#### 3.3.1 ① 上报端点

`① 上报端点` 块自上而下展示:

- **云区域(单选,必填)**:下拉,值域 `default` / `cn-north(华北)` / `cn-east(华东)` / `hk(香港)` / `global(海外)`,默认 `default`。
- **组织(多选,必填)**:下拉,选项 `Default` / `finance` / `ops` / `platform` 等,默认 `['Default']`。
- **API 端点(只读 POST URL)**:根据云区域查表,渲染为深色代码块,左上有绿色 `POST` 角标,右上"复制"按钮。端点 URL 不允许在接入页自定义。

云区域 → API 端点映射分两套:

- **SDK / Agent 通用通道**:`https://bklite.{区域}.canway.net/telegraf/api`,接收 OTLP/HTTP 上报。
- **OTel Collector 专属 traces 端点**:`https://replay.bklite.{区域}/v1/traces`,专用于 otlphttp/saas exporter。

OTC 接入详情页显示 OTC 专属端点;其它接入方式(SDK / eBPF / K8s)显示通用通道端点。组织多选为后续多租户扩展保留,第一版不参与端点拼接,仅作为接入上下文的元数据保存。

#### 3.3.2 ② 接入配置(按语言 / 方式)

`② 接入配置` 块按接入方式给出可复制的代码片段,以**只读代码块**形式呈现,右上"复制"按钮。

**SDK 类(Java / Node.js / Python / .NET / Go)统一形态**:顶部副标题"按下方片段配置上报,几分钟即可看到数据进来" + `Segmented` 切换两段(语言原生自动探针 / Docker 运行 -e 注入)+ 每段下方 BASH 代码块。代码块内统一字段:

- 端点(`OTEL_EXPORTER_OTLP_ENDPOINT=${endpoint}`):由 IntegrationDetail 注入,从上方 `① 上报端点` 联动
- 协议(`OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`)
- 传播器(`OTEL_PROPAGATORS=tracecontext,baggage`)
- 资源属性(`OTEL_RESOURCE_ATTRIBUTES=service.name=...,service.namespace=...,deployment.environment=...,service.version=...`)
- **不输出任何接入凭证 / Authorization Header** —— 第一版不做鉴权,APM 业务层不签发 token;鉴权由部署环境的反向代理 / mTLS 负责

各语言两段具体内容:

| 语言 | 自动探针段 | Docker 运行段 |
| --- | --- | --- |
| Java | 下载 opentelemetry-javaagent.jar + `OTEL_*` env + `java -javaagent:./opentelemetry-javaagent.jar -jar app.jar` | Dockerfile 写 `ADD .../opentelemetry-javaagent.jar /otel.jar` + `ENV JAVA_TOOL_OPTIONS=-javaagent:/otel.jar` + `docker run -e OTEL_*` |
| Node.js | `npm install @opentelemetry/auto-instrumentations-node` + `OTEL_*` env + `node --require @opentelemetry/auto-instrumentations-node/register app.js` | `docker run -e OTEL_* -e NODE_OPTIONS="--require .../register"` |
| Python | `pip install opentelemetry-distro[otlp]` + `opentelemetry-bootstrap -a requirements.txt` + `OTEL_*` env + `opentelemetry-instrument python app.py` | `docker run -e OTEL_* -e ENTRYPOINT=opentelemetry-instrument ... python app.py` |
| .NET | `curl -fsSLO .../otel-dotnet-auto-install.sh -O && sh ./otel-dotnet-auto-install.sh` + `OTEL_*` env + `. $HOME/.otel-dotnet-auto/instrument.sh && dotnet run`,附 Windows / IIS 的 PowerShell 模块注册(`Import-Module OpenTelemetry.DotNet.Auto.psm1` + `Register-OpenTelemetryForIIS`) | `docker run -e OTEL_* ... bash -c ". /root/.otel-dotnet-auto/instrument.sh && dotnet run"` |
| Go | `go get go.opentelemetry.io/otel {sdk,exporters/otlp/otlptrace/otlptracehttp,semconv/v1.26.0}` + 写入 `tracing.go`(initTracer + resource + sdktrace.NewTracerProvider)+ `OTEL_*` env + `go run .` | `docker run -e OTEL_EXPORTER_OTLP_* -e OTEL_SERVICE_NAME -e OTEL_SERVICE_NAMESPACE -e OTEL_DEPLOYMENT_ENVIRONMENT -e OTEL_SERVICE_VERSION` |

**OTel Collector 形态**:不切换两段,只一段 Collector exporter 配置。结构:小标题"Collector exporter 配置" + 描述"在已有 Collector 的 exporters / service 段追加以下内容" + YAML 代码块(`exporters.otlphttp/saas.traces_endpoint: ${endpoint}`,service.pipelines.traces.exporters 引用 `otlphttp/saas`)。**不输出 headers / authorization** —— 第一版不做鉴权。

**eBPF(OBI)形态**:不切换两段,只一段部署 + 启动代码。结构:`kubectl apply -f .../obc.yaml` + `OTEL_EXPORTER_OTLP_ENDPOINT` 等环境变量 + `obi --config ./obi-config.yaml` 启动。

**K8s(OTel Operator)形态**:不切换两段,只一段 Operator + Instrumentation CR + Pod 注解。结构:`helm install opentelemetry-operator` + `Instrumentation` CR YAML(`exporter.otlp.endpoint: https://otlp.bklite.cloud` + `propagators: [tracecontext, baggage]`)+ `Deployment` YAML 注解 `instrumentation.opentelemetry.io/inject-<lang>: "true"`。

### 3.4 上报端点

- 上报端点由平台统一分配,**不签发任何凭证 / token / Authorization Header**;OTLP 入口鉴权由部署环境负责,APM 业务层不参与鉴权决策。
- SDK / Agent 与 OTel Collector 走两套不同的端点路径(`telegraf/api` 通用通道 vs `v1/traces` Collector 专属),端点 URL 在接入详情页 `① 上报端点` 块展示,以只读 POST URL 形式提供,支持"复制"操作。
- 端点 URL 包含区域标识,由云区域下拉联动,前端按 5 个区域固定映射(`default` / `cn-north` / `cn-east` / `hk` / `global`),不允许在接入页自定义。
- 第一版云区域映射以前端常量形式给出,后续接入后端"按 Group 解析可用端点"接口时再切换。

### 3.5 接入列表(已接入实例视图)

"接入列表"是集成菜单的第二个二级页,跟"添加接入"并列,承担"接入之后我接了什么 / 接入方式是什么 / 最近还活着吗"的管理职责。接入列表与"服务目录"互为补充:服务目录按"健康度"视角看每一个服务,接入列表按"接入"视角看每一个服务(接入方式 / 接入时间 / 活跃状态)。

#### 3.5.1 列表字段(列顺序从左到右)

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 服务 | 链接(粗体) | 点击跳到该服务的"服务目录 → 单服务详情" |
| 应用 | 链接(对应 OTel `service.namespace`) | 点击跳到该应用的"应用详情";字段内部仍叫 `namespace`,UI 列名改为「应用」以贴合中文用户习惯 |
| 环境 | 文字(对应 OTel `deployment.environment`) | 例 `production` / `staging` / `dev`;与顶部"环境 Select"同源 |
| 接入方式 | Tag(SDK 5 种语言 / OTC / eBPF / K8s) | 标签着色区分,带"推荐"角标仅展示用,不参与筛选 |
| 接入时间 | 相对时间(例 `3 天前`) | 首次上报时间(精确到分钟) |
| 最近上报 | 相对时间(例 `5 分钟前`) | 最近一次 Span 落库时间 |
| 状态 | Tag(活跃 / 静默 / 已归档) | 活跃 = 近窗 15 分钟有 Span;静默 = 近窗无但未达 7 天;已归档 = 服务目录归档后同步过来;**不展示**"失联"独立档位(由"静默 ≥ 7 天"自动归并到"已归档"流程) |
| 操作 | 单按钮 | 仅「查看」一项,跳到"服务目录 → 该服务详情" |

> 上报协议(第一版固定 OTLP/HTTP)不单独占列;统一在 §3.3 端点路径约束里表达(SDK/Agent 走 `telegraf/api`,OTel Collector 走 `v1/traces`)。后续若需要扩展 OTLP/gRPC,会走单独的 PM 流程,在接入详情页配置块和后端 pipeline 同时升级。

#### 3.5.2 顶部工具栏(从左到右,单行)

- **服务名搜索框**:模糊匹配 service.name 与应用名(对应 `service.namespace`),带清除按钮。
- **接入方式 Select**(默认"全部"):选项 `SDK / OTC / eBPF / K8s` 与 SDK 子项 `Node.js / Java / Python / .NET / Go`,选中后只展示该接入方式的实例。
- **环境 Select**(默认"全部环境"):`production` / `staging` / `dev` 等;与"环境"列同源,改了 Select 后"环境"列同步刷新。
- **时间 Radio**:实心 `15m` / `1h` / `4h` / `1d` / `7d`,默认 `7d`;时间窗影响"最近上报"列与"状态"判定。
- **不展示**状态 chips(活跃 / 静默 / 失联 / 全部)、tag chips、未归类应用过滤等;这些维度直接通过表格列内筛选或环境 Select 表达,不另起一排 chip。

#### 3.5.3 状态判定与"接入时间"语义

- **接入时间 = 首次上报时间**:以 service.name + service.namespace 联合键首次在 VictoriaTrace 落库的时间为准,作为该实例"接入"时间锚点;不维护单独的"接入记录表"。
- **状态(活跃 / 静默 / 已归档)**:
  - **活跃**:近窗 15 分钟内有 Span 落库;视觉 = 绿色 Tag + 圆点。
  - **静默**:近窗无 Span 落库,但 `now - 最近上报时间 < 7 天`;视觉 = 灰色 Tag + 圆点。
  - **已归档**:服务目录归档后同步过来;视觉 = 琥珀色 Tag + 圆点。**第一版不展示独立的"失联"档位**,由"静默 ≥ 7 天"自动走服务目录的归档流程,接入列表只读呈现"已归档"结果。
- 状态判定与"服务目录 → 服务节点三态(活跃 / 静默 / 已归档)"完全一致,接入列表不独立计算,服务目录的归档 / 解档操作会同步反映到接入列表的"状态"列。
- 状态实时按 VictoriaTrace 落库数据计算,前端不缓存,每次进入接入列表重算。

#### 3.5.4 行操作

- **查看**:跳到"服务目录 → 该服务 → 单服务详情",**不**打开新的"接入详情"页面(避免重复入口)。
- 接入列表**不提供**独立的"改接入方式"行操作:第一版由"服务目录 → 单服务详情"承载入口,后续若要从接入列表直接改,会走单独的 PM 流程,在列表里以"跳到对应 SDK / OTC / eBPF / K8s 详情页复用配置片段"的形式补一个跳转按钮;**不**做原地编辑接入方式弹窗 / 抽屉(避免在接入列表里再造一个跟添加接入详情页重复的代码片段编辑器)。
- 接入列表**不提供**行级"归档"操作:归档由"服务目录"独立入口承担(右上"···"菜单),接入列表只读展示归档状态;不在接入列表行级别加归档入口,以避免两个入口的归档状态不一致。

#### 3.5.5 跟"服务目录"的数据一致性

- 接入列表的实例 = 服务目录中"已上报过数据"的服务全集;两者按同一份底层数据(VictoriaTrace 落库的 service.name + service.namespace 联合键)渲染,不会出现"接入列表有但服务目录没有"或反之的实例。
- 接入列表的"状态"列完全复用服务目录的"三态(活跃 / 静默 / 已归档)"判定;服务目录的归档 / 解档操作会同步反映到接入列表的"状态"列;接入列表不独立写"状态"字段。
- 接入列表的"接入方式"字段由 APM 元数据表(`Service` 表的 `integration_method`)存储,服务目录不展示该字段;两者在"实例范围"上对齐,但展示维度不同:接入列表 = 接入维度,服务目录 = 健康维度。

## 4. 关键规则

- APM 不向业务侧签发任何凭证或鉴权 token,接入侧鉴权由平台部署环境(反向代理的 IP 白名单 / mTLS / Header 校验等)负责。
- 第一版接入配置代码块**不输出任何 Authorization / Bearer / Header**;鉴权完全交给部署侧,APM 业务层不做任何 token 注入或鉴权判断。
- 接入详情页只展示"① 上报端点 + ② 接入配置"两步,不再展示接入自检 / Trace 任务路径 / 排错说明 / 接通后核对 等推断式或过程性内容;接入状态与首批数据反馈由"服务 / 探索"菜单的真实数据承载。
- 接入方式总览与接入详情页按 Group 隔离可见,默认对所有 Group 开放;Group 管理员可在系统管理中通过"角色"控制本 Group 成员对集成页的访问与操作权限。
- 上报端点由平台统一分配,接入详情页不允许用户自定义端点 URL,仅提供复制。
- 资源属性中 `service.name + service.namespace` 联合作为服务的唯一键,缺一不可,缺一的服务上报将不被纳入服务目录(在接入配置代码块中以 `service.name=...,service.namespace=...` 形式强制要求填写)。
- 接入页不持久化任何接入历史(谁接入过、什么时候接入、是否成功);接入状态由服务目录 / 探索菜单的真实数据呈现,集成菜单保持"只读模板"形态。
- 接入页菜单 operation(`View` / `Operate`)在角色系统中声明,组织管理员通过系统管理中"角色 → 菜单 operation"控制本 Group 成员对集成页的访问与操作权限。
- 接入列表的实例范围与"服务目录"完全一致(同一份 VictoriaTrace 落库数据,service.name + service.namespace 联合键),不会出现"接入列表有但服务目录没有"或反之的实例;两者在"实例范围"上对齐,展示维度不同(接入列表 = 接入维度,服务目录 = 健康维度)。
- 接入列表的"状态"列完全复用服务目录的"三态(活跃 / 静默 / 已归档)"判定,不在接入列表独立计算;服务目录的归档 / 解档操作会同步反映到接入列表的"状态"列。
- 接入列表的"接入方式"字段在 APM 元数据表(`Service` 表的 `integration_method`)中存储,服务目录不展示该字段;第一版接入方式由用户在"添加接入"详情页配置时写入,后续若要从接入列表改,会走单独的 PM 流程(走"服务目录 → 单服务详情"承载入口),不在接入列表做"原地编辑"弹窗 / 抽屉。
- 接入列表的"行操作"只有"查看"一类,跳"服务目录 → 单服务详情";**不提供**"改接入方式"行操作,**不提供**"归档"行操作,避免在接入列表里再造一个跟添加接入详情页重复的代码片段编辑器,也避免两个归档入口的状态不一致;归档入口以服务目录的"···"菜单为唯一路径。

## 5. 关键技术架构选择

- OTLP 入口以 OpenTelemetry Collector 形式部署,接收 OTLP/HTTP 与 OTLP/gRPC 双协议,统一进行限速、资源属性归一化与流量分流。
- **鉴权由部署环境负责**(反向代理 / mTLS / Header 校验),APM 业务层不参与鉴权决策;鉴权失败由部署层返回 4xx,APM 端到端协议不感知鉴权存在。
- 接入配置代码块由前端硬编码模板渲染,模板参数(`endpoint` / `service.namespace` / `deployment.environment` 等)由前端运行时按用户选择注入;第一版不做后端"按 Group 解析可用模板"接口,云区域端点表以前端常量维护。
- 端点路径分两套:SDK / Agent 走 `telegraf/api`(统一 OTLP/HTTP 通道),OTel Collector 走 `v1/traces`(otlphttp 协议);两套端点对应不同 deployment 入口,但都属于同一 APM OTLP 接入层。
- Trace 原始 Span 与 Span 索引存储于 VictoriaTrace,按 `(service.name, deployment.environment, service.version)` 三元组做分桶;APM RED 预聚合(吞吐 / 错误率 / 分位 / Apdex)写入 VictoriaMetrics,两者在同一 VictoriaMetrics 生态内协同工作。
- 资源属性(`OTEL_RESOURCE_ATTRIBUTES`)以 `service.name + service.namespace` 联合唯一键接入服务目录;`deployment.environment` 与 `service.version` 用于环境筛选 / 部署对比 / 回归定位;`service.namespace` 缺失的服务归入"未归类应用"虚拟分组(详见"服务"规格书 §3.1.2)。
- 接入页菜单 operation(`View` / `Operate`)在角色系统中声明,组织管理员通过系统管理中"角色 → 菜单 operation"控制本 Group 成员对集成页的访问与操作权限;接入页不维护 Group 维度的接入历史。
- 接入页不引入新的聚合接口与新表;所有"接入是否成功"的状态均由服务目录 / 探索菜单的现有接口在接入完成 1-2 分钟后基于真实 Span 落库数据呈现。
- 接入列表的实例数据直接复用服务目录的服务列表查询接口(新增 `integration_method` 字段),不引入独立的"接入实例"聚合接口;接入列表的工具栏在 WHERE 条件中按 `integration_method` 过滤,`integration_method` 字段在 APM 元数据表中以 `Service` 表的可空列存储(未配置接入方式时为空字符串,接入列表显示为"未标注")。
- 接入时间(首次上报)由 VictoriaTrace 的 `service.name + service.namespace` 联合键首次落库时间戳推算,不再单独维护"接入记录"表;接入时间 = service 首次落库时间,后端在 `Service` 表的 `first_seen_at` 字段上推算。
- 接入列表的"状态"判定完全复用"服务目录"的三态计算,后端在 `Service` 表的 `state` 字段上计算(`active` / `silent` / `archived`);接入列表只读展示,不写状态。
- 接入方式在 SDK / OTC / eBPF / K8s 间支持热切换,但**不重启应用**;新配置在用户部署侧生效后,通过 VictoriaTrace 上报的 `service.name` 上的 `integration_method` Span tag(或 Service 元数据变更)反映到接入列表,无需 APM 内部重启。第一版接入列表**不提供"改接入方式"行入口**,接入方式变更由用户在部署侧完成,通过新 Span 落库自动更新接入列表的接入方式列;后续若需要从接入列表直接发起,会走单独的 PM 流程。

## 6. 验收标准

- 用户在接入方式总览可看到 SDK、OTC、eBPF、K8s 四组接入方式,SDK 组下分 Node.js、Java、Python、.NET、Go 五张卡;每张卡点击进入对应接入详情页。
- 接入详情页采用"① 上报端点 + ② 接入配置"两步布局,两段同时可见、不嵌套 Tabs;**不展示**接入自检 / Trace 任务路径 / 接通后核对 / 排错说明。
- ① 上报端点 块包含云区域单选(5 个值)、组织多选(可多 Group)、API 端点(POST URL,只读,带复制按钮);云区域切换时 API 端点自动联动。
- SDK 类(Java / Node.js / Python / .NET / Go)接入配置采用"自动探针 / Docker 运行(-e 注入)"两段 Segmented 切换,代码块统一以"端点 / 协议 / 传播器 / 资源属性"四项为骨架,各语言按自身原生方式补安装与启动命令;**不输出任何 Authorization / Bearer / Header**。
- OTel Collector 接入配置只一段 YAML(`exporters.otlphttp/saas.traces_endpoint: ${endpoint}` + `service.pipelines.traces.exporters: [otlphttp/saas]`);**不输出 headers**。
- eBPF / K8s 接入配置只一段,按各自原生部署 + 启动 / 注解方式给出,不输出鉴权相关字段。
- 接入页不向业务侧签发任何凭证或鉴权 token;鉴权由部署环境(反向代理 / mTLS)负责,APM 业务层不参与鉴权。
- 上报端点由平台统一分配,前端以只读 POST URL 形式提供并支持复制;端点 URL 不允许在接入详情页自定义。
- 资源属性以 `service.name=...,service.namespace=...,deployment.environment=...,service.version=...` 格式输出;`service.name` 与 `service.namespace` 缺一的服务不被纳入服务目录。
- 接入页按 Group 隔离,跨 Group 数据不可见;Group 管理员通过系统管理中"角色 → 菜单 operation"控制本 Group 成员对集成页的访问与操作权限。
- 接入页不持久化任何接入历史;接入状态与首批数据反馈由"服务 / 探索"菜单的真实数据呈现,接入页保持只读模板形态。
- 集成菜单下设两个并列的二级页:"添加接入"(原接入方式总览 + 接入详情页)与"接入列表"(已接入实例视图);接入列表填补"接入之后用户看不到自己接了什么"的空白,跟"服务目录"按健康度视角互为补充。
- "接入列表"二级页顶部工具栏仅含"服务名搜索 + 接入方式 Select(SDK / OTC / eBPF / K8s + SDK 5 子项)+ 环境 Select + 时间 Radio(15m/1h/4h/1d/7d)";**不展示**状态 chips、tag chips、未归类应用过滤等其他维度。
- "接入列表"二级页表格列顺序为:`服务` / `应用` / `环境` / `接入方式` / `接入时间` / `最近上报` / `状态` / `操作`;`应用` 列对应 OTel `service.namespace` 字段,`环境` 列对应 `deployment.environment` 字段(与工具栏"环境 Select"同源);`接入时间` 字段 = 该 `service.name + service.namespace` 联合键首次在 VictoriaTrace 落库的时间,`最近上报` = 最近一次 Span 落库时间,`状态` = 复用服务目录的三态(活跃 / 静默 / 已归档);**不展示**独立的"上报协议"列(由 §3.3 端点路径统一约束)。
- "接入列表"二级页行操作仅 1 类:`查看`(跳到"服务目录 → 该服务详情");**不提供**"改接入方式"行操作(改接入方式由用户部署侧完成,通过新 Span 落库自动更新,不在接入列表做入口),**不提供**"归档"行操作(归档入口以服务目录的"···"菜单为唯一路径),**不提供**原地编辑接入方式弹窗 / 抽屉。
- "接入列表"二级页数据范围与服务目录完全一致(同一份 VictoriaTrace 落库数据),不会出现"接入列表有但服务目录没有"或反之的实例;两者按"实例范围"对齐,展示维度不同(接入列表 = 接入维度,服务目录 = 健康维度)。

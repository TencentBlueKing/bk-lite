## 1. 背景与目标

服务菜单承担"以服务为锚点的可观测性"职责,是 APM 的中心一级菜单。服务菜单覆盖三个能力:服务目录(以应用或服务为单位的健康总览与单服务详情)、服务拓扑(服务间调用关系地图)、SLO(以服务为单位的可靠性契约)。三者共同构成服务可观测性的核心闭环。

服务目录是 P0 阶段的能力,服务拓扑与 SLO 是 P1 阶段的能力,后两者在 P0 接入首批数据后逐步开放。

## 2. 范围定义

- 服务:服务目录(**应用视角**:应用卡片网格 / **服务视角**:服务列表表格)、**应用详情子页**(应用级拓扑 + 关键信息 KPI + 该应用下服务列表)、单服务详情(单服务 RED 时序、Top 端点、Top 错误、上下游依赖、部署事件叠加、实例分布、运行时指标、Apdex 满意度 + 阈值配置、已归档入口)。
- 服务目录核心指标:服务名(健康点 + 语言标签)、**活跃告警数(按最高等级染色,置于吞吐量左侧)**,吞吐量、错误率、P99 时延、Apdex 满意度、近期趋势、最近部署、SLO 状态、版本、最近活跃。
- 服务拓扑:服务依赖有向图、节点健康与吞吐编码、边指标标注、时间窗拓扑、环境过滤、节点下钻、边下钻、上下游聚焦、搜索与定位、布局与交互、分组聚合与折叠、视图分享、环路与自调用识别;**节点三态(活跃/静默/已归档)与自动归档**。
- SLO:SLO 列表、SLI 定义(可用性 + 延迟达标率)、SLO 配置、时间窗口(滚动/日历)、错误预算、燃尽率展示、状态总览、历史合规与趋势、good 口径可配。

## 3. 关键能力

### 3.1 服务(P0)

服务菜单的"服务"二级页是**唯一一个**展示服务总览与下钻单服务的入口,不分"应用页 / 服务页"。页面提供两种**视角**用于总览(应用 / 服务),但**只有一种详情页**(单服务详情)。

#### 3.1.1 页面总体结构

服务二级页自上而下(注意:**列表页与详情页的工具栏不同**):

1. **顶部二级导航(已固定,只含路由)**:`服务 / 服务拓扑 / SLO`,激活态 = `服务`。该行**只承载页面级路由切换**,不混入任何筛选 / 视角 / 抽屉按钮。
2. **页面工具栏**(根据当前页面状态分两套):
   - **列表页工具栏**(page = `app-list` 或 `service-list`):视角切换 `应用 | 服务` + 服务名搜索 + 环境 + 应用 + 健康度 + 版本 五个筛选 + 时间窗(15m / 1h / 4h / 1d / 7d + 自定义)+ "已归档"按钮(带 Badge 数量)。
   - **详情页工具栏**(page = `app-detail` 或 `service-detail`):**只保留时间窗 + 已归档按钮**,**完全不显示**视角切换、搜索、环境、应用、健康度、版本筛选。原因:详情页已锁定单一应用或单一服务,这些"列表级筛选"控件没有意义且会与页内的"返回服务"操作争抢视线。
3. **总览内容区**:跟随当前视角/页面渲染。共四种页面状态,共享同一页面容器(不跳一级路由,仅在二级页内切换):
   - 视角 = `应用` + page = `app-list`:应用卡片网格(详见 §3.1.2)
   - 视角 = `应用` + page = `app-detail`:**应用详情子页**(详见 §3.1.2.1)—— 由普通应用卡片点击进入。
   - 视角 = `服务` + page = `service-list`:服务列表(全部或已选应用下)
   - page = `service-detail`:单服务详情(详见 §3.1.4)
4. **页面状态机**:`app-list ↔ app-detail ↔ service-list ↔ service-detail` 之间均为页面内状态切换(类似 Tab 切换),URL 含 `?page=<state>&app=<namespace>&service=<name>` 便于分享。
5. 不再有面包屑、页面介绍段、整页服务计数统计;聚合信息以原生 Segmented/Select/卡片自身的视觉呈现。

**设计边界**:二级导航 vs 工具栏严格分层

- 二级导航 = "页面级导航",只放**路由入口**(服务 / 服务拓扑 / SLO)。点击触发跨页跳转,不携带任何局部 UI 状态。
- 工具栏 = "本页内控件",放**视角切换、筛选、时间窗、已归档**等所有本页的局部 UI 状态。点击不触发跨页跳转。
- 两层不能混用:任何不属于"路由"的控件都不应出现在二级导航行;反之亦然。
- 已归档抽屉入口放在工具栏尾部(右侧),不在二级导航行。

#### 3.1.2 应用视角(应用卡片网格)与应用详情下钻

- 应用聚合规则:平台按 OTel Resource 上报的 `service.namespace` 自动归类,**应用名 = service.namespace**;**当 service.namespace 缺失时,服务归入名为"未归类应用"的虚拟应用**,统一展示,引导用户补全 namespace。
- 应用卡片展示字段(自上而下,自左而右):
  - **顶部行**:健康点(取该应用下最差服务的健康等级)+ 应用名 + (未归类则加"未归类"角标) + 右上角「活跃告警数」chip(钟铃图标 + 数字,按应用下所有服务的告警求和并取最高等级染色;0 告警也显示,作为"健康"信号)。
  - **应用名下方小字**:服务数(`N 个服务`,12px 灰字,缩进对齐健康点)。
  - **KPI 两列**:Σ 吞吐量(/s) · Σ 错误率(%)。
  - **底部服务 tag 列表**:应用下所有服务,一行展示,按真实宽度自适应折叠;超出可视宽度时,尾部折叠为 `+N` chip。
- **服务 tag 智能折叠规则**:不做固定 N 截断,而是按容器宽度裁剪。每个 tag 的真实宽度由 ResizeObserver 测量,累加后超过容器宽度即停,剩余服务折叠为单个 `+N` 蓝底 chip;窗口 resize 时自动重算。
- 卡片点击行为(按下钻语义拆分):
  - **普通应用(有 namespace)** → 进入"应用详情子页"(`page = app-detail`),展示应用级 KPI + 应用级子拓扑 + 该应用下的服务列表(详见 §3.1.2.1)。
  - **未归类应用(namespace 缺失)** → 不下钻到应用详情,在当前页进入服务列表筛选(`page = service-list` + 顶部"已选应用:未归类应用"信息条 + namespace 为空),详情见 §3.1.3。
  - 虚拟应用"未归类应用"在产品上不具备"应用级聚合实体"的语义(它只是缺失 namespace 的兜底分组),无法计算"应用级 KPI / 子拓扑",因此不提供应用详情页。
- 切换与筛选保持状态:用户在应用视角选中应用后,即便切到 `服务` 视角,应用筛选条件依然生效;切回 `服务` 视角时,该应用作为默认值带入。

##### 3.1.2.1 应用详情子页

- 入口:应用视角下点击普通应用卡片(非"未归类应用")。
- 路由:相对服务页内嵌路径(不是独立一级或二级菜单);URL 含 `?app=<namespace>&page=app-detail` 便于分享。
- 页面布局(自上而下):
  - **顶部标题行**:`HealthDot + 应用名 + 最差 <服务名> Tag + 异常服务名 Tag(若存在)`.注意"最差"Tag 显示的是**最差服务的名字**(不是健康等级),并列时按 throughput 取最大。
  - **同行两栏布局**(左 16 列 = 服务拓扑,右 8 列 = 关键信息 KPI):
    - **服务拓扑(应用聚合)**:本应用节点用蓝色虚线包围盒圈出,显示该应用的服务节点;上下游应用的服务以灰色虚线节点呈现;退化下游边用红色实线标识;工具栏含"本应用 N 节点" + "M 异常"小 tag。
    - **关键信息 KPI 网格**(9 项,2 列 × 4 行 + 1 行全宽):
      - **第一行(全宽)**:健康度 — HealthDot + `严重/警告/关注/良好/健康` Tag + 灰色"最差 <服务名>"。
      - **第二行**:Σ 吞吐量(/s) · Σ 错误率(%)。
      - **第三行**:P99(max, ms) · 服务数。
      - **第四行**:告警(应用下所有服务告警数求和) · SLO(已配 SLO 的服务数)。
      - **第五行**:最近部署 · 版本(独立 version 数)。
  - **该应用下的服务列表**:嵌入服务视角表格(同 §3.1.3 的字段),选中服务名 → 进入该服务的"单服务详情",与从外部服务列表点选完全进入同一个详情组件(不分两套入口)。
- **不要**的东西(经过迭代已剔除):
  - 不再显示「告警 Alert」(条件渲染)—— 应用级 KPI 已能体现告警情况,顶部 Alert 容易让用户看到"自动推断",与"仅展示事实"原则冲突。
  - 不显示「同比 delta」—— 单服务和应用级都不带环比,避免猜测。
  - 不显示「查看 Trace / 编辑 SLO / 订阅变更」操作区—— Trace 编辑在 Tab 内的"调用链"Tab,SLO 编辑在 SLO 菜单。
- **共享工具栏**:沿用服务页的工具栏(仅时间窗 + 已归档),视角切换在应用详情页失效(已锁定单一应用),按钮 disabled 并提示"先返回服务目录"。

#### 3.1.3 服务视角(服务列表表格)

- 服务列表字段(列顺序已对齐运维查看习惯):
  1. **服务**:HealthDot + 语言标签 + 服务名(链接) + (静默时加"静默"tag)
  2. **活跃告警**:Tag 胶囊样式(钟铃 + 数字),按最高等级染色;0 也显示(灰底)以稳定列宽
  3. **吞吐量(/s)**
  4. **错误率**
  5. **P99**(ms)
  6. **APDEX**(0~1,按阈值 ≥0.9 绿 / ≥0.75 黄 / <0.75 红 加粗)
  7. **趋势**:8 根迷你柱状图,按健康度着色
  8. **最近部署**
  9. **SLO**:达标 tag + 错误预算百分比进度条
  10. **版本**
  11. **最近活跃**
- **列顺序原则**:告警 → 流量 → 质量(SLI)→ 趋势 → 元数据。运维打开服务列表第一眼看告警(高优先级危险信号),其次才是流量/质量,避免翻看中间列。
- "已选应用"模式下:页面退化为该应用下的服务列表;字段一致,顶部多一条"已选应用:XXX [清除]"信息条,其它逻辑不变。
- 排序与筛选:支持按错误率、P99、吞吐、健康严重度、服务名排序;筛选条件(环境/健康度/版本/时间窗)全程保留。
- 单服务入口:点击服务名 → 进入"单服务详情"(路由:`/service/<service.name>?ns=<namespace>`)。

  - 应用详情页内服务列表点服务名
  - 单服务详情页顶部"所属应用"链接(可点击下钻到对应应用的应用详情子页)
  - 已归档抽屉中点"查看历史"等价于跳转到该服务归档前的 RED 快照详情

  以上入口走到完全相同的"单服务详情"组件与路由处理。
- 页面布局:
  - **顶部行**:`HealthDot + 服务名 + 健康 Tag(严重/警告/关注/良好/健康) + "所属应用 <应用名>" 链接 + 右上 `···` 菜单(仅「归档」操作)`。

  - **Top 端点 / Top 错误**:Top 端点按总耗时占比、Top 错误按受影响 Span 数。
  - **上下游依赖 + 部署事件**:列在该服务下挂"上下游 / 部署事件"两栏,便于故障传播定位。
- 支持按版本过滤,过滤状态写入 URL 便于分享;按版本过滤后,RED 时序、Top 端点、Top 错误、上下游依赖、实例分布等均按该版本范围展示。

### 3.2 服务拓扑(P1)

#### 3.2.1 依赖有向图

将 Group 内服务调用关系渲染为有向图,节点代表服务或推断依赖,边代表调用关系,方向为上游调用下游。
- 节点健康与吞吐编码:通过节点颜色展示健康状态,节点大小展示吞吐,悬停展示服务吞吐、错误率、P50/P95/P99 时延等 RED 摘要。
- 边指标标注:在调用边上展示或悬停查看请求速率、错误率、P99 时延等指标,边粗细表达吞吐,边颜色表达健康。

#### 3.2.2 时间窗与环境过滤

支持按最近 15 分钟、1 小时、4 小时、1 天、7 天或自定义时间窗重算拓扑节点、边和健康指标,便于对比故障前后服务依赖变化;支持按生产、预发、开发等环境单选过滤拓扑,避免不同环境调用关系混合展示。

#### 3.2.3 下钻与聚焦

节点下钻:支持点击拓扑节点查看服务 RED 摘要、上下游清单,并跳转到对应服务详情;边下钻:支持点击调用边查看上游到下游的调用 RED 指标,并携带上游服务、下游服务、时间窗、环境等条件跳转到 Trace 检索;上下游聚焦:支持选择节点进入 Ego 图聚焦模式,仅展示该节点及 N 跳上下游邻居;搜索与定位:支持按服务名模糊搜索节点,匹配后高亮并自动居中。

#### 3.2.4 布局、分组、分享

布局与交互:支持缩放、平移、适配全图、重置视图、力导向布局、分层布局和节点位置固定;分组聚合与折叠:支持按命名空间、团队、标签等维度分组折叠节点,展示组级 RED 汇总和跨组调用边;视图分享:支持将时间窗、环境、聚焦节点、跳数、布局、搜索高亮等视图状态固化为分享链接,便于协同排障;环路与自调用识别:支持识别并标注服务自调用和循环依赖。

#### 3.2.5 节点三态与自动归档(活跃 / 静默 / 已归档)

服务拓扑节点按时间窗内是否上报数据分为"活跃 / 静默 / 已归档"三态。

- **活跃**:近窗(默认 15 分钟)有 Span 上报。视觉 = 实线 + 健康色(绿/黄/红),大小=吞吐。
- **静默**:近窗无数据上报,且静默时长 < 归档阈值(默认 7 天)。视觉 = 虚线 + 灰色;hover tooltip 显示"最后活跃于 X 天前";静默 ≥ 6 天时节点右上"!"小标提示"明天将归档";支持节点右键"立即归档"与"标记为活跃"操作。
- **已归档**:静默 ≥ 归档阈值(默认 7 天,自动归档),或用户主动归档。**默认不显示在拓扑中**,移入"已归档服务"列表;已归档服务的 Span 仍写入 VictoriaTrace(数据不丢),仅不展示在默认拓扑与服务目录中。

自动归档规则:

- 阈值默认 7 天,范围 1-30 天,可在系统设置中调整。
- 触发:每天凌晨低峰时段跑一次扫描,把所有"静默 ≥ 阈值"的服务移入"已归档服务"列表。
- 自动解档:已归档服务在归档后**再次上报**(任何 Span 落库),自动从"已归档"移回"静默"态(因是真实流量恢复,不是"新服务"),避免把"老服务偶然恢复"误识别为新接入。

用户操作:

- 静默节点(< 7 天):hover 看最后活跃时间;节点右键"立即归档" / "标记为活跃"。
- 已归档服务列表:支持**恢复**(回默认拓扑,作为静默态)、**查看历史**(跳转到该服务归档前最后一次有数据时的 RED 快照)。
- 手动归档入口:服务目录行末"···"菜单 → 归档;单服务详情右上"···" → 归档;批量归档(服务目录多选 → 批量归档,单次最多 100 个,带二次确认)。
- 时间窗切换会重算节点的活跃/静默状态,前一时间窗的视图状态不保留。

### 3.3 已归档服务(P1)

**不作为独立页面/独立二级菜单**;在"服务 → 服务"页(任意视角)的右上"已归档"按钮中打开 Drawer 抽屉展示已归档服务清单。

为什么不放独立页面:

- 已归档服务是低频操作,大多数用户日常不进;
- 放在独立页面会膨胀顶部二级导航,挤占"服务 / 服务拓扑 / SLO"等高频入口;
- 抽屉形态更轻,可在主页面上下文中直接操作(恢复/查看历史),完成后一键关闭,不打断主流程。

抽屉内容:

- 列表字段:服务名、namespace、应用归属、环境、最后活跃时间、归档原因(**自动 / 手动**)、归档时间。
- 操作:**恢复**(移回默认拓扑,作为静默态)、**查看历史**(跳转到归档前 RED 快照)、**彻底删除**(P0/P1 不做,留到 P2 之后讨论)。
- 抽屉标题:"已归档服务",副标题显示当前归档数量与数据保留期汇总(如"3 个归档服务 · 数据保留期最长 90 天")。
- 抽屉宽度:560px,右侧滑入,可关闭。
- 入口位置:在任何"服务"页(应用视角 / 服务视角)的右上"已归档"按钮;**与视角切换互斥**——视角切换器在筛选条上方,已归档在筛选条右侧,不冲突。

### 3.4 SLO(P1)

#### 3.4.1 SLI 定义与配置

- SLI 定义:支持基于入口 Span 定义可用性 SLI 和延迟达标率 SLI。
  - 可用性 SLI:good = 非 Error 入口 Span 数,total = 入口 Span 总数。
  - 延迟达标率 SLI:good = 耗时 < 配置阈值的入口 Span 数,total = 入口 Span 总数。
- SLO 配置:支持配置服务级或端点级 SLO,包括 SLI 类型、目标达成率、滚动或日历窗口、窗口长度、good 口径。

#### 3.4.2 时间窗口与错误预算

时间窗口:支持滚动窗口和日历窗口,滚动窗口持续回看最近 N 天,日历窗口按自然月或季度结算,满足实时治理和周期汇报两类场景。错误预算:自动计算错误预算总额、已消耗预算、剩余预算和燃尽率,在无数据或样本不足时不做达标/违约结论,便于正确评估可靠性风险。

#### 3.4.3 燃尽率展示与状态总览

燃尽率展示:SLO 燃尽率仅作为 SLO 详情页与首页摘要的展示指标,不接入事件菜单告警通道;MVP 不基于燃尽率触发告警。如需对 SLO 燃尽率超阈进行告警,需在「事件」菜单按 SLO 关联的服务 / 端点配置度量告警策略(MVP 支持 4 类度量:错误率 / P99 / P95 / 吞吐)。状态总览:提供 SLO 总览看板,支持按剩余预算、燃尽率、违约状态排序,并按服务、环境、负责团队、窗口类型、是否违约筛选或分组。历史合规与趋势:展示历史达成率时序、目标线、按结算周期的合规台账,并支持导出用于复盘、汇报或对客 SLA 沟通。

#### 3.4.4 good 口径可配(与业务错误判定解耦)

good 口径可配:支持配置客户端 4xx 是否计入失败、主动取消或限流降级是否合格/不合格/排除出分母。
- SLO good 口径**与业务错误判定完全解耦**:
  - 业务错误判定(用于 Issue 聚类、Top 错误、错误率等)走 OTel Error 语义 + 业务侧 Span 标签,详见"探索"菜单 3.3.1。
  - SLO good 口径(用于可用性 / 延迟达标率)由每个 SLO 独立配置,4xx 是否计入"非 good"在 SLO 维度配置。
  - 两套配置互不共享,业务错误的判定不依赖 SLO 配置,SLO good 口径也不影响 Issue 聚类。
- SLO 详情中明确展示 good/total 精确定义,便于对外解释与对内归因。

## 4. 关键规则

- 服务的唯一标识为 `service.name + service.namespace`(允许 namespace 缺失)。
- 当 `service.namespace` 存在时,该服务归入同名的"应用";**当 `service.namespace` 缺失时,服务归入名为"未归类应用"的虚拟应用**,统一展示以提示用户补全 namespace。
- 应用目录按 Group 隔离,跨 Group 数据不可见;不允许 incident 式跨 Group 协同。
- 服务菜单的"服务"二级页是**唯一的应用/服务总览入口**,**不存在独立的"应用详情页"**。点击应用卡片 = 在当前页激活服务筛选;**唯一**的详情入口是"单服务详情"。
- 服务节点存在**三态(活跃 / 静默 / 已归档)**,按近窗数据上报情况滚动评估,逻辑详见 §3.2.5。
- 已归档服务的 Span 仍写入 VictoriaTrace(数据不丢),仅不在默认服务目录与拓扑中展示;**归档不物理删除数据**。
- 已归档服务再次上报(任何 Span 落库)会自动从"已归档"移回"静默"态,避免把"老服务偶然恢复"误识别为新接入。
- 已归档服务关联的告警策略**自动暂停**,避免对"已下线服务"误告警;解档后自动恢复。
- 已归档服务不参与收藏;彻底删除在 P0/P1 不做,留到 P2 之后讨论。
- 服务健康分级以"近窗错误率 + 近窗 P99 时延"为依据,样本量不足时降级为"待定"。
- 服务目录的"陈旧/失联"状态以"近窗(默认 15 分钟)无活跃 Span"为判定依据,与探针侧心跳解耦。
- 服务拓扑节点与边基于 Trace 边统计推断,推断置信度由平台内置算法决定,不对外暴露具体置信度数值。
- 服务拓扑时间窗切换会重算节点、边和健康指标,前一个时间窗的视图状态不保留。
- 服务拓扑节点按"活跃 / 静默"双态呈现,无数据节点不消失,以灰色虚线视觉降级;用户可启用"只看活跃"过滤。
- 服务拓扑视图分享链接包含时间窗、环境、聚焦节点、跳数、布局、搜索高亮,链接打开后状态完全一致。
- 单服务详情支持按版本过滤,过滤状态写入 URL 便于分享;按版本过滤后,所有该服务详情内的图表、列表、摘要均按该版本范围展示。
- Top 错误项支持点击进入"探索"菜单错误二级的对应 Issue 详情。
- SLO 目标达成率与错误预算以"good/total"为唯一计算口径,不受业务侧其他聚合影响。
- SLO good 口径配置对客户端 4xx、主动取消、限流降级三类场景独立配置,配置变更仅对变更后产生的 Span 生效。
- SLO 燃尽率不接入事件菜单告警通道,仅在 SLO 详情页与首页摘要中展示;如需对 SLO 燃尽率超阈进行告警,需在「事件」菜单按 SLO 关联的服务 / 端点配置度量告警策略(MVP 支持 4 类度量:错误率 / P99 / P95 / 吞吐)。
- 业务错误判定与 SLO good 口径是两套独立配置,前者由 OTel Error 语义 + 业务侧 Span 标签决定,后者由每个 SLO 独立配置;两套不共享。
- 服务目录、SLO 列表、服务拓扑按 Group 隔离,跨 Group 数据不可见;不支持 incident 式跨 Group 协同。
- **活跃告警聚合规则**:
  - 服务级:`ServiceRow.activeAlerts = { count, level }`,level 来自该服务命中最严重的告警等级(1=严重 / 2=警告 / 3=关注 / 4=良好 / 5=健康,数字越小越严重);0 表示无告警。
  - 应用级:应用下所有服务的 `activeAlerts.count` 求和,`level` 取所有服务中的最小值(最严重);0 表示应用下无活跃告警。
  - 染色规则:`level ≤ 2` → 红色(严重/警告);`level === 3` → 琥珀(关注);`level ≥ 4` 或 0 → 灰色;渲染为胶囊 Tag(钟铃 + 数字,圆角 10,border 1px)。
  - 0 告警也显示"🔔 0"灰底 chip,作为"健康"信号;后续可调整为隐藏。
  - 静默行(silent)统一 opacity 0.6,与其它列一致。
- **服务目录行高与列顺序原则**:告警(危险信号)→ 流量(吞吐量/错误率)→ 质量(SLI:P99/APDEX)→ 趋势 → 元数据(部署/SLO/版本/活跃)。运维打开服务目录第一眼看告警,其次才是流量/质量。

## 5. 关键技术架构选择

- 服务目录的服务清单由 APM 内部基于 OTel Resource 上报的 `service.name + service.namespace` 联合唯一键自动发现,不与 CMDB 同步,不复用 CMDB 服务模型。
- 单服务 RED 时序从 VictoriaTraces 的 Span 派生查询获得；上游/下游依赖使用 VictoriaTraces dependencies 接口，APM 不维护 VictoriaMetrics 预聚合副本。
- 单服务详情按版本过滤由 VictoriaTraces 中的 `service.version` 维度实现，后端执行有界查询，前端不在线聚合。
- 服务目录**只有一套列表查询接口**,内部按"应用 = service.namespace"聚合返回;**应用详情子页**不引入新的"应用详情"查询接口,而是**复用 3 个现有接口**组合:① 服务列表接口(按 namespace 过滤)→ 该应用下服务列表;② 服务拓扑接口(按 namespace 过滤)→ 应用级子拓扑;③ 应用级 KPI 接口(可选;若没有则前端从服务列表中按 namespace 聚合 Σ 吞吐量 / Σ 错误率 / max P99)。这一组合方式避免新增聚合接口,降低后端实现成本。
- 服务拓扑节点与边来自 VictoriaTraces dependencies 接口，按时间窗和环境查询；不另建 APM 边指标存储。
- 服务拓扑节点的"活跃 / 静默"双态由后端结合目录最近活跃时间与当前查询窗判定，前端不做二次计算。
- JVM、Go 等 OTel Runtime Metrics 不在当前 traces-only 数据面范围内；若后续开放，必须单独决定指标存储与上线契约，不能默认复用 Monitor VictoriaMetrics。
- Apdex 从 VictoriaTraces Span 计算，以服务的"满足阈值 Span 数 / 总 Span 数"为分子分母，支持 Group 级与服务级阈值覆盖。
- SLO 配置以 Django ORM 持久化，SLO 计算从 VictoriaTraces 派生，错误预算与燃尽率由 APM 运行期任务计算。
- SLO good 口径在 SLO 计算时按"每个 SLO 的配置"独立判定，与业务错误判定解耦；两套规则不共享。
- SLO 燃尽率仅在 SLO 详情页与首页摘要中展示,不触发事件菜单告警,不进入告警通道;事件菜单的度量告警策略不感知 SLO 燃尽率,两者解耦。
- 部署事件叠加以 OTel Resource 的 `deployment.environment` 与 `service.version` 联合推断,推断事件在 APM 内部标记为"推断部署";外部 CI/CD 上报的部署事件作为可选扩展,不强制要求。
- 服务目录、SLO、服务拓扑的数据查询接口在 WHERE 条件中按用户所属 Group 过滤,跨 Group 数据不可见;不引入跨 Group 协同机制。
- 应用聚合以 `service.namespace` 为唯一维度,后端按 `service.namespace IS NULL OR service.namespace = ''` 归入"未归类应用",前端以独立虚拟卡片展示,允许用户点击查看缺失 namespace 的服务清单(等价于在筛选中传入"未归类应用"虚拟值)。
- 服务节点的"已归档"状态以 APM Service 元数据表的 `archived_at`(归档时间)与 `archived_reason`(`auto` / `manual`)字段持久化;OTLP 入口无差别接收所有服务的 Span 写入,服务是否归档不影响数据写入,只影响"是否在默认服务目录与拓扑中展示"。
- 自动归档扫描任务每天凌晨低峰时段执行一次,扫描条件为"近窗(默认 15 分钟)无活跃 Span 且 最后活跃时间 ≤ now - 7 天",扫描结果批量更新 Service 表的 `archived_at` 字段;扫描任务对原有数据无破坏性,仅修改展示状态。
- 自动解档在 VictoriaTrace 检测到该 `service.name + service.namespace` 有新 Span 落库时触发,后端清除 Service 表的 `archived_at` 与 `archived_reason` 字段,服务回到"静默"态(因新数据刚开始,健康指标尚未稳定)。
- 已归档服务关联的告警策略暂停由"事件"菜单策略引擎在评估时跳过 `archived_at IS NOT NULL` 的服务实现,无需在策略表内显式标记。

## 6. 验收标准

- 服务二级页(服务)是**唯一的**应用与服务总览入口;**含应用详情子页**(`page=app-detail`)—— 点击普通应用卡片进入,展示应用级拓扑 + 关键信息 KPI 9 项 + 该应用下服务列表;**未归类应用**卡片点击不进入应用详情,直接进入服务列表筛选(等价于"服务视角 + 应用筛选=空 namespace")。
- 服务二级页顶部仅有二级导航 + 视角切换器(应用 / 服务)+ 通用筛选条;**不含**面包屑、页面介绍段、整页聚合统计 Tag。
- 视角切换为视图态切换,不进路由;切换后筛选条件全程保留。
- 服务列表字段(列顺序)含:服务(健康点 + 语言标签) / **活跃告警** / 吞吐量(/s) / 错误率 / P99 / APDEX / 趋势 / 最近部署 / SLO / 版本 / 最近活跃;支持按错误率、P99、吞吐、健康严重度、服务名排序。
- **活跃告警列固定在吞吐量左侧**——运维打开服务目录第一眼看告警(高优先级危险信号),其次才是流量/质量;染色按告警最高等级(level ≤ 2 红 / level = 3 琥珀 / 其它 灰);0 告警也显示(灰底"🔔 0")作为健康信号。
- 应用视角下,namespace 缺失的服务归入"未归类应用"虚拟卡片(虚线 + 橙色顶部边框 + "未归类"角标);点击同样在当前页激活"未归类应用"的服务筛选。
- **应用卡片**展示字段:健康点 + 应用名 + 服务数(应用名下方小字) + 右上角活跃告警数 chip + Σ 吞吐 + Σ 错误率 + 应用下服务 tag 列表(智能折叠 +N,按容器宽度裁剪,非固定 N)。
- **应用详情子页**:顶部 = HealthDot + 应用名 + "最差 <服务名>" Tag + 异常服务名 Tag;同行两栏(左 16 列 = 应用级拓扑,右 8 列 = 关键信息 KPI 9 项);下方嵌入该应用下的服务列表。
- **关键信息 KPI 9 项**:健康度(全宽,HealthDot + 严重/警告/关注/良好/健康 Tag + "最差 <服务名>") · 吞吐量(Σ) · 错误率(Σ) · P99(max) · 服务数 · 告警 · SLO · 最近部署 · 版本。**不带同比 delta**。
- **单服务详情**:顶部 = HealthDot + 服务名 + 健康 Tag + "所属应用 <应用名>" 链接(可下钻到对应应用的应用详情) + 右上 `···` 菜单(仅「归档」);**核心 KPI(吞吐/错误率/P99/Apdex)不带环比 delta**;**不显示顶部"告警 Alert"**;**不显示右上"查看 Trace"按钮**(Trace 入口放 Tab 内「调用链」)。
- Apdex 卡右上角提供「阈值」按钮,点击抽屉可改 Apdex 满意阈值 T(MVP 简化版只暴露租户默认 + 单服务覆盖开关)。
- 单服务详情支持按版本过滤,过滤状态写入 URL;展示 RED 时序(吞吐/错误率/P50/P75/P90/P95/P99/平均)、Top 端点、Top 错误、上下游依赖、部署事件叠加、实例分布、运行时指标、Apdex。
- Top 错误项可点击进入"探索"菜单错误二级的对应 Issue 详情。
- 服务拓扑按时间窗(15m/1h/4h/1d/7d/自定义)与环境单选过滤;节点颜色表达健康、节点大小表达吞吐;边粗细表达吞吐、边颜色表达健康。
- 节点按"活跃 / 静默"双态呈现,无数据节点不消失,以灰色虚线视觉降级;用户可启用"只看活跃"过滤。
- 服务节点存在三态:活跃(实线 + 健康色)、静默(虚线 + 灰色,hover 显示最后活跃时间)、已归档(默认不显示,移入"已归档服务"列表)。
- 自动归档阈值默认为 7 天,可在系统设置中调整(范围 1-30 天);每天凌晨低峰时段执行一次扫描,静默 ≥ 阈值的服务自动归档。
- 已归档服务在 VictoriaTrace 中的 Span 数据保留(归档不删数据),但不在默认服务目录与拓扑中展示。
- 已归档服务再次上报自动解档回"静默"态(避免误识别为新服务);解档后关联告警策略自动恢复。
- 已归档服务关联的告警策略自动暂停,避免对"已下线服务"误告警。
- 已归档服务入口以"已归档"按钮 + Drawer 抽屉形式挂在"服务"二级页右上;**不**单独占据二级导航位;批量归档单次最多 100 个服务,带二次确认。
- 彻底删除在 P0/P1 不做,留到 P2 之后讨论。
- 节点下钻跳转单服务详情,边下钻跳转 Trace 检索并携带上游/下游/时间窗/环境;Ego 聚焦模式可设置跳数。
- 拓扑视图支持按服务名模糊搜索、布局切换(力导向/分层/节点固定)、分组折叠(命名空间/团队/标签)、分享链接完整复现状态。
- 拓扑自动识别并标注服务自调用与循环依赖。
- SLO 支持基于入口 Span 定义可用性 SLI 和延迟达标率 SLI,good/total 计算口径明确,支持按服务/端点维度配置。
- SLO 时间窗口支持滚动与日历两类;错误预算自动计算总额、已消耗、剩余、燃尽率;无数据或样本不足时不做达标/违约结论。
- SLO 燃尽率仅在 SLO 详情页与首页摘要中展示,不接入告警通道;事件菜单的度量告警策略由用户按服务 / 端点自行配置,与 SLO 燃尽率完全解耦。
- SLO good 口径可配(客户端 4xx、主动取消、限流降级),配置变更仅对变更后产生的 Span 生效;SLO good 口径与业务错误判定完全解耦,两套配置不共享。
- 服务目录、SLO 列表、服务拓扑按 Group 隔离,跨 Group 数据不可见;不支持 incident 式跨 Group 协同。
